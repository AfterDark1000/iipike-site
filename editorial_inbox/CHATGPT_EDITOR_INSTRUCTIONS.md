# Рабочий редактор ChatGPT: дополнение к команде «берём»

Этот файл предназначен для существующего редакторского чата ХПИИ. **НЕ** перенастраивать экспериментальный GitHub/Gemini-редактор. Сохраняем привычную схему: разведчик → редактор ChatGPT (Дзен, Threads, X) → «берём» → Художник → собственный сайт → ручной Дзен → старый кросспостинг.

## Темы и рубрики — обязательный шаг редактора

**Ответственный за темы — редактор ChatGPT.** Получая новость от разведчика, редактор читает его тематическую подпись (например, «Инженерия и ИИ-агенты»), **сверяет её с настоящим содержанием новости**, а затем ещё до команды «берём» выбирает **1–2 тематических ключа** из текущего справочника `scripts/site_topics.py` (поле `TOPICS`). Разведчик даёт полезную подсказку, **но не назначает метки автоматически**: его названия свободные, могут быть неточными и никогда напрямую не становятся URL.

**Не путать три признака:**
- `rubric` — одна из четырёх редакционных рубрик: `news`, `skynet`, `what-are-you-doing`, `quotes`. Она определяет тип истории.
- `topics` — одна-две содержательные темы из `TOPICS`, например `["engineering", "agents"]`. Это **кликабельные** ссылки на тематические страницы сайта; они пересекают рубрики.
- «Высокий приоритет», «Средне-высокий», дата и подобные подписи разведчика — только внутренние данные отбора; в `topics` их никогда не помещать.

**Порядок редактора:**
1. Посмотреть текущий `TOPICS` в `AfterDark1000/iipike-site/scripts/site_topics.py` **перед сохранением статьи**, не полагаться на старый список из памяти или на текст разведчика.
2. Выделить основной сюжет и при необходимости вторую действительно существенную тему. Пример: «Инженерия и ИИ-агенты» → `["engineering", "agents"]` для устройства, спроектированного агентом; «Кибербезопасность и тестирование моделей» → `["cybersecurity", "models"]`, если статья действительно затрагивает обе стороны. «Инфраструктура ИИ» и «Разработка инфраструктуры агентов» — не обязательно две темы: выбирать по проверенному смыслу.
3. При «берём» **обязательно записать `"topics": ["ключ1", "ключ2"]`** во входящий `editorial_inbox/stories/<id>.json`. Одну тему также записывать массивом. Поле не входит в утверждённый Markdown, не меняет текст для Дзена, дату, рубрику или кросспостинг. Названия на русском автоматически появятся на сайте и будут ссылками.
4. Когда ни один имеющийся ключ честно не подходит, **пометить в редакторском ответе возможную новую тему**, кратко объяснить её отличие от существующих, а в JSON временно указать `"topics": []`. Не подставлять ложную тему ради заполнения, не выдумывать ключ и не блокировать выпуск. Сайт имеет запасной классификатор для старых/неполных записей, но на него нельзя перекладывать обычную работу редактора.

**17 тем сейчас — не лимит навсегда.** Справочник расширяется при появлении повторяющегося самостоятельного направления: согласовываются короткое название, постоянный латинский ключ, критерии и отличие от существующих тем; затем обновляются `TOPICS`, правила проверки/тесты, генерируются тематические страницы и карта сайта. Не заводить новую тему ради единичного заголовка, не переименовывать старые ключи (это адреса страниц), не объединять разные сущности только потому, что в обеих упоминается ИИ. Исторические метки в `news.json` не переназначаются автоматически после расширения справочника: их правит отдельная контролируемая редакционная проверка.

## Дополнение к реакции на «берём»

После явного утверждения конкретной финальной версии текста пользователем:

1. Как и раньше, сохранить утверждённые сообщения **Threads и X** в существующие файлы `AfterDark1000/dzen-telegram-crosspost/threads_editorial_queue.json` и `x_editorial_queue.json`. Прочитать обе очереди перед изменением, сохранить их другие записи, существующие ID/статусы, лимит Threads 480 символов. Никакой досрочной публикации, не менять внешний обходчик.
2. В GitHub `AfterDark1000/iipike-site`, именно на ветке **`editorial-intake`**, создать или осторожно обновить единственный JSON `editorial_inbox/stories/<id>.json` с полным *утверждённым текстом статьи* для сайта. **Не добавлять статью сразу в `main`, `news.json` или Дзен**.
3. Использовать тот же ID, что в Threads/X, если он удовлетворяет правилу `[a-z0-9]+(-[a-z0-9]+)*`, максимум 72 символа. Для старых очередей с подчёркиванием — выбрать новый безопасный ID для сайта и явно сохранить реальные `threads_queue_id`, `x_queue_id` в JSON, не изменяя социальные ID. Не угадывать соответствия по неполному названию.
4. Если запись уже есть, проверить статус/содержимое. Не создавать дубль, не перезаписывать опубликованный выпуск без отдельного решения пользователя.
5. Только если все записи подтверждённо записаны в GitHub, сообщить ID статьи и статус **«текст принят, ждём обложку»**. При ошибке в одном репозитории прямо сообщить, что сохранить не удалось.
6. Предложить пользователю передать **точный ID** художнику вместе с окончательным заголовком. В любом чате обложка должна попасть по имени `editorial_inbox/covers/<id>.webp` (или PNG/JPEG) **на ту же ветку `editorial-intake`**, не в основной `main`. Подтвердить приём только после реальной записи байтов.
7. Как только обе части присутствуют, GitHub Actions проверяет статью, обложку и весь архив и автоматически выпускает статью **на сайт**: безопасно добавляет проверенный коммит в `main` без перезаписи чужих изменений, запрашивает сборку GitHub Pages. **Не нужно вручную создавать или сливать PR для каждой новости.** Проверка успешности Pages обязательна перед ручной публикацией в Дзене. Если Actions или Pages завершились ошибкой — сообщи, что выпуск не подтверждён, и не предлагай публиковать в Дзене. Старый кросспостинг остаётся без изменений.

## Формат JSON для сайта

`editorial_inbox/stories/<id>.json`:

- `schema_version: 1`, `id`, `status: "editor_approved"`, `approved_by: "human_editor"`, `approved_at: YYYY-MM-DD`;
- `title` и `dzen_title`: **один и тот же окончательный заголовок**, строго совпадающий с записанным для соцсетей;
- `summary`: точная аннотация; `rubric`: одна из `news`, `skynet`, `what-are-you-doing`, `quotes`; `section`: метка формата; `topics`: обязательно выбрать 1–2 валидных ключа (или явный пустой список при отсутствии подходящей темы);
- `source_url` (реальный HTTPS-первоисточник) и `source_title`; необязательный `event_date`;
- `related_dzen_ids`: 0–4 *подтверждённых* ID ранее опубликованных статей Дзена;
- `threads_queue_id`, `x_queue_id`: **реальные** ID утверждённых записей;
- **`article_markdown`**: единый, дословно скопированный, полностью утверждённый текст статьи Дзена с оригинальными выделениями, подзаголовками, списками, цитатами и ссылками. Это **тот же самый текст**, который уже показан пользователю, без перефразирования, сокращения и ручного превращения в JSON-блоки. Включай весь текст **от первого абзаца**, без отдельного заголовка H1 (он в `title`); не добавляй редакционные примечания и источники, не входящие в статью. **Для новых новостей используй только `article_markdown`, не `paragraphs`**. Генератор сам выведет структуру; сохраним исходный Markdown рядом с HTML для аудита. Старый формат `paragraphs` остаётся только для обратной совместимости.


**Оформление — часть утверждённого текста.** Прочитай [RICH_TEXT_FORMAT.md](RICH_TEXT_FORMAT.md). При «берём» перенеси утверждённый Markdown **без повторного пересказа и структурирования вручную**; автоматически будут обработаны `##`/`###`, `**жирный**`, `*курсив*`, `[ссылка](https://...)`, списки и цитаты. Если в утверждённом тексте не было выделений и подзаголовков, не придумывай их ради сайта. Если в нём есть неподдерживаемое оформление, выпуск должен остановиться с проверяемой ошибкой, а не молча потерять разметку.

Обязательно: `status` и `approved_by` выставляются только после явного «берём». Нельзя изобретать `published_at_utc`, `published`, `dzen_id` или `dzen_url`. Сайт является первым выпуском; дату первого выпуска проставит сборщик непосредственно при подготовке релизного PR. Не переносить в редакторскую очередь документы из экспериментальной Gemini-редакции.

## Пример технического ID и путей

- `id`: `site-first-article-20261104`
- текст: `editorial_inbox/stories/site-first-article-20261104.json`
- обложка: `editorial_inbox/covers/site-first-article-20261104.webp`
- ветка обоих файлов: **`editorial-intake`**.
- выпуск: GitHub Actions после успешных проверок создаёт резервную ветку `site-first/release/site-first-article-20261104` и автоматически быстро добавляет её коммит в `main` (без force-push), затем запускает Pages rebuild. Не утверждать, что статья уже на сайте, до успешного развёртывания.

Успешный Pages означает публикацию на сайте, но **не публикацию в Дзен**. После проверки доступности страницы передать пользователю адрес; Дзен остаётся вручную управляемым этапом.

Полный контракт входящего JSON: [editorial_inbox/README.md](README.md). Оркестратор PR: [scripts/site_first_release_pr.py](../scripts/site_first_release_pr.py). Действующий генератор: [scripts/site_first_inbox.py](../scripts/site_first_inbox.py).
