## Действующий серверный протокол ручного редактора (Issue №477, 26.11.2026)

**Приоритет над прежними указаниями о прямой записи пула и локальном Python для ручного редактора.** Обычный ChatGPT не обязан скачивать большой JSON в Python. Состояние по-прежнему хранится в `main/data/site_news_pool.json`, маршрут — в `data/editorial_routing.json`. GitHub Actions использует штатные Python-функции и атомарно записывает пул и квитанцию одним нефорсированным коммитом. Отдельного реестра активных резервов нет.

- На явную команду **«следующая»** создай **ровно один** новый файл в main `data/editorial_claims/requests/manual-<уникальный-id-операции>.json`, через GitHub connector create_file. Имя латиницей, цифрами, дефисом/подчёркиванием; минимум 8 символов после manual-. Тело строго `{"schema_version":1,"action":"claim_next","worker":"hpii-manual-editor"}`. Не указывай кандидата, статус или время самостоятельно.
- **В том же ответе/проходе** несколько раз прочитай `main/data/editorial_claims/receipts/<то-же-имя>.json`. При первом 404 не завершай работу и не спрашивай «проверить?»: прочитай редакционные правила/источники для предварительной ориентировки, затем повтори проверку. Не создавай вторую заявку при задержке или потере ответа: сначала перечитай исходный путь. При исчерпанном времени или подтверждённом отказе сообщи точное имя операции и причину; продолжение проверяет ту же заявку.
- При `reserved` перечитай актуальный пул и маршрут из одного snapshot main. Сверь ID, sequence, `in_review`, точное `review_started_at == claimed_at`; квитанция должна иметь правильное имя, worker и SHA запроса. Только затем фактчекинг и полноценный текст Дзен/Threads/X/ВК. При `no_long_news` покажи отсутствие свободных; при `rejected` не обходи защиту.
- Для checkpoint нового ручного резерва создай новый уникальный файл в том же каталоге. Тело: `{"schema_version":1,"action":"checkpoint","worker":"hpii-manual-editor","claim_request":"manual-...json","pool_id":"n-...","pool_sequence":123,"claimed_at":"точное значение из квитанции резерва","expected_note":"текущее точное поле note","note":"новая заметка о проверенном прогрессе"}`. Все операции привязаны к исходной квитанции, текущему статусу, времени и предыдущей заметке. Подтверди `checkpointed` и перечитай результат. Никаких чужих резервов.
- Для возврата используй те же поля, action `return`, дополнительно `human_authorized:true` только при явной команде человека, note — причина. Для отклонения `reject` с обоснованной причиной согласно прежним редакционным правилам, без дополнительных полей. Для `approve` только после явного «берём» и сохранения точной утверждённой истории в editorial-intake добавь `human_authorized:true, article_id, story_sha` (точный blob SHA сохранённой story). Сервер проверяет реально сохранённую историю с human_editor; этот переход ничего не публикует. После подтверждения `returned` / `closed_rejected` / `closed_approved` перечитай пул. При несовпадении ожидаемой заметки не перезаписывай чужую работу.
- Для старого ручного in_review без новой квитанции прежний безопасный порядок остаётся; новый запрос не присваивает его. Не использовать новый протокол для чужих AUTO_EDITOR/SHORT_EDITOR резервов.
- Пробный запрос action `probe` с теми же тремя полями только проверяет штатный выбор и валидаторы без записи в пул; не считается резервом. Обычному редактору проба не нужна.

**Для всех писателей:** заявки/квитанции автономного редактора, короткостволиста, сортировщика и intake сохраняются. Прямое изменение пула/маршрутов разрешено только после штатной полной валидации и проверки общего HEAD main, с нефорсированным коммитом на точном snapshot; при любой гонке перечитать и пересчитать. Один SHA файла пула не защищает от параллельной смены маршрута. Не переписывать production JSON из чата без этих условий. Не считать отсутствие локального Python причиной пропустить серверную заявку. Никаких изменений в публикациях и секретах.

## Приоритетная редакторская правка главреда от 22.11.2026 — проверять ДО выдачи каждой новости

Это постоянное обязательное уточнение прежних правил о сильном лиде, ритме абзацев, удалении страховок и упоминаниях X. Главред многократно возвращал материалы из-за нарушения этих пунктов. **Приоритет — выполнить их при написании, не ждать очередной ручной правки.**

1. **Первое предложение Дзена — отдельный абзац.** Одно завершённое цепляющее предложение, содержащее конкретный проверенный конфликт, факт или неожиданность и причину читать дальше. После него обязательно пустая строка; дальнейший абзац развивает новость, не объявляет её повторно. Не начинать с казённой ссылки на пресс-релиз или длинного абзаца из трёх одинаковых предложений. Не придумывать сенсацию ради зацепки.
2. **Абзацы разной длины и формы.** В одной статье естественно чередуются однострочные, короткие и средние/развёрнутые абзацы. Ритм определяется действием и смыслом, а не шаблоном, выравниванием по четыре строки или механическим чередованием. Сильную мысль можно оставить в одну строку; взаимосвязанные предложения — держать вместе.
3. **Удалять страховки, служебные оговорки, подводки, повторы и выводы без читательской ценности.** После факта/цифры не дописывать дежурные «независимой проверки нет», «это только сравнение», «это не доказывает», «неизвестно, вошло ли условие в финальный договор», когда это не добавляет содержательного результата. В новости №457 фразу «Попало ли это условие в окончательные документы, издание установить не смогло» главред отдельно велел удалить. При этом **не превращать попытку, переговоры или заявление в заключённое обязательство**: статус «пытались добиться запрета», «обсуждали ограничение» достаточно обозначить прямо в основном факте. При существенной неопределённости сформулировать её однократно и конкретно в предложении, где она меняет смысл, без отдельного абзаца-перестраховки. Если фраза не продвигает сюжет, удалить её полностью.
4. **X — настоящие релевантные @упоминания.** В каждом посте перед выдачей проверить официальные X-аккаунты основных участников и, если есть уверенно установленные, органично поставить @handle в текст (не только @OpenAI по привычке). Не угадывать и не изобретать ручки; при отсутствии подтверждения писать имя без @. Лимит 280 символов считать после упоминаний. X — отдельный живой текст, не механический конспект.

5. **Внутренняя ссылка прямо внутри смысловой фразы.** Слова, описывающие конкретный факт, событие или результат, должны быть кликабельны прямо в соответствующем предложении. Запрещены отдельные пристройки «[Об этом эксперименте ХПИИ писали отдельно](...)», «мы уже рассказывали», «подробнее в нашей статье», отдельный абзац для перелинковки. Пример для №458: «нейросеть [сочинила хокку о космосе](https://dzen.ru/a/augPIKV4vCP1TEeL), а спутник передал стихотворение обратно». Если ссылка убрана, предложение должно оставаться нужным и полноценным.
6. **Threads — финальная шутка при её уместности.** Одно короткое, живое, мемное, актуальное предложение, вырастающее из конкретного факта, а не информационный финал без эмоциональной точки. Не добавлять вторую шутку или объяснение панча; избегать стандартных каламбуров и искусственного юмора. Если достойной шутки нет, оставить сильный факт без натянутой концовки. Лимит очереди — 480 символов вместе с новой строкой.

7. **Заголовки без тире (правка главреда от 23.11.2026).** В заголовке статьи и отдельном заголовке ВК не использовать длинное/среднее тире (`—`, `–`) как связку или драматическую паузу. Писать грамматически цельную фразу с глаголом, двоеточием или запятой, если они естественны; не заменять тире дефисом. В самом тексте и соцпостах **сократить количество тире**: предпочитать обычную синтаксическую конструкцию и пунктуацию, ставить тире только там, где оно действительно нужно для смысла.
8. **Только факты вместо авторских оценок (23.11.2026).** Убирать «неприятная особенность», «любопытный момент», «поразительная деталь», «вполне логично», «что примечательно» и их аналоги, если они просто оценивают уже сообщаемый факт. Пример №465: вместо «У MONAI Label была ещё одна неприятная особенность: по умолчанию программа не требовала авторизации» написать «MONAI Label по умолчанию не требовала авторизации». Значение факта читатель поймёт из точных условий и последствий. Фактическую квалификацию риска и цитируемые оценки не подменять произвольной авторской эмоциональностью.

### Дополнение главреда от 24.11.2026 — обязательное применение

- **Заголовок и лид:** сильнее честный кликбейт и ясность для неспециалиста. Заголовок называет понятное событие и причину открыть статью. Первое предложение — отдельный абзац и самостоятельная зацепка, не повтор заголовка. Не использовать начало по схеме «подводка → вот что это было». Внутри текста выделять первую сильную мысль смыслового блока отдельным абзацем, чередовать однофразовые, короткие и средние абзацы; не разбивать механически каждое предложение.
- **Язык:** не использовать оборот «Речь идёт о», шаблонные противопоставления «это X, а не Y», штампованные парные формулы «с языка X на язык Y» и аналогичные искусственные контрасты. Удалять «Самое интересное выяснилось потом», оценки автора, подводки и финальные итоги. Убирать повторную атрибуцию («По подсчётам Calif…»), если источник уже однозначно назван; сохранять атрибуцию, необходимую для точности. При подтверждённой возможности или действии заменять лишний модальный глагол смысловым согласно действующему правилу от 20.11.2026; сохранять реальную неопределённость, риск, условие и прогноз.
- **Цитаты и оформление:** если приводится выразительная позиция участника («по словам…») и доступна точная цитата, предпочтительна короткая дословная цитата либо верный перевод с указанием говорящего; оформлять Markdown-блоком с префиксом `> ` на каждой строке. Не изобретать цитаты. Первое упоминание сущностей выделять жирным; подзаголовки, списки и смысловые выделения применять по содержанию. Проверять внутренние ссылки по каталогу, встраивать только реальные содержательные связи.
- **Соцсети:** Threads — самостоятельный заход, акцент КАПСОМ на одном-двух ключевых словах, короткая живая актуальная шутка в финале, если уместна. X — включать подтверждённые @аккаунты всех фигурирующих ключевых участников, а не ограничиваться одним; не добавлять нерелевантные аккаунты и не превышать 280 символов. VK — один тематический эмодзи в начале заголовка, КАПСОМ только ключевое слово или короткая мысль, затем пустая строка и самостоятельный анонс. В JSON это отдельные поля vk_title и vk_summary без переносов внутри полей.

**Предотправочная проверка №1:** первое предложение отделено пустой строкой; зацепка есть; абзацы реально различаются по длине; нет обслуживающих мысль оговорок/повторов; у X проверены @участники и лимит. Если любой пункт не выполнен, пересобрать материал **до показа главреду**.

## Единый пул новостей для сайта — обязательные команды между чатами (12.11.2026)

Перед работой с пулом прочитать [docs/SITE_NEWS_POOL.md](../docs/SITE_NEWS_POOL.md) и актуальный [data/site_news_pool.json](../data/site_news_pool.json) из `main` GitHub. **Это отдельный слой СЫРЫХ кандидатов**, не очередь опубликованных/утверждённых материалов и не очередь Дзена. Выпуск, художник, очереди Threads/X, утверждение «берём» и действующая site-first схема не меняются.

- Когда пользователь в чате обходчика говорит **«ХПИИ: В ПУЛ»**, его помощник сохраняет последнюю подборку **одним пакетом, строго в порядке отображения (сверху вниз)**; с номерами — только выбранные, в исходном порядке. **Новые записи только в конец `items`, с возрастающими неизменными `sequence`**. Даже два параллельных чата получают последовательные номера по фактическому порядку успешных коммитов GitHub. Не «запомнить в чате», а реально обновить `data/site_news_pool.json` с защитой SHA и повторным чтением; при SHA-конфликте перечитать, перенумеровать добавляемые и безопасно повторить. Без явной команды подборки не сохраняются автоматически.
- Когда пользователь говорит редактору **«ХПИИ: СЛЕДУЮЩАЯ»**, **не просить заново переслать новость**: прочитать актуальный пул и **сначала выбрать минимальный `sequence` среди `queued` с `priority: "high"`** (горячая редакторская очередь). **Только когда горячих не осталось**, выбрать минимальный `sequence` среди обычных `queued` (`normal`/`low`). Внутри каждого уровня сохранять FIFO, не переставлять сами записи. **Сначала зарезервировать** одну выбранную запись как `in_review` через подтверждённый GitHub-коммит и записать `review_started_at`, затем проверить факты/дубли и подготовить статью на утверждение. Не брать уже `in_review` другого чата. После явного «берём» у горячего материала также задать `site_queue: "priority"` в его утверждённом story JSON: `high` в сыром пуле сам по себе не ускоряет публикацию.
- **«ХПИИ: ПРОДОЛЖИТЬ»** — читать самую раннюю по `sequence` незавершённую `in_review` и продолжать проверку/статью **без повторного резерва и без сброса даты**. С ID — продолжать именно её. Если незавершённых несколько, показать остальные с датами. Редактор после каждого существенного этапа (проверка источников, план, найденное ограничение) **коммитит в GitHub короткую заметку `note` (до 1500 символов) с текущим прогрессом и следующим шагом**, не изменяя порядковый номер, статус или дату резервирования; после коммита перепроверяет запись. В другом чате читать эту заметку при продолжении. Не обещать восстановления полного текста несохранённого черновика: пул хранит ссылку, краткую суть и заметку, но не статью.
- **«ХПИИ: ПУЛ»** — показать счётчики, номера очереди, статусы, даты `added_at` и `review_started_at` **по времени Усть-Катава/Екатеринбурга (UTC+05:00)**; **«ХПИИ: ВЕРНУТЬ <id>»** — вернуть `in_review` в `queued` с исходным порядковым номером; **«ХПИИ: ПРОПУСТИТЬ <id>»** — завершить `rejected` с причиной.
- `approved` в пуле разрешён **только после явного «берём» и реально подтверждённого сохранения** утверждённого `editorial_inbox/stories/<article_id>.json`; добавить точный `article_id`. Не считать черновик, статус обложки или фразу в ответе фактом публикации.
- Источник из пула — отправная точка, а не уже проверенное доказательство. Перед подготовкой статьи использовать текущие редакционные правила, первоисточники, архив, метки компаний/продуктов и проверку тем. Не трогать `news.json`, `editorial-intake` и публикационные файлы при простом взятии новости. Если GitHub-запись или резервирование не удались, прямо сказать об этом, **не заявлять об успехе**.

## Обязательное чтение всей утверждённой группы (20.11.2026)

**Перед написанием ведущей новости из редакционного пула прочитай актуальные `data/editorial_routing.json` и `data/site_news_pool.json` из `main`.** Для выбранного кандидата сопоставь оба неизменных идентификатора: `pool_id` и `sequence`. Если маршрут содержит `group` и `group_primary` (включая ведущий `decision: "linked_primary"` или `decision: "hot"` с группой), **найди и прочитай ВСЕ записи этой группы**, в том числе `linked_secondary` с `lane: "hold"`, по их точным `pool_id + sequence`. Прочитай заголовок, `summary`, `source_url`, существующие редакторские `note` и первоисточники каждой; используй факты в одной статье там, где они действительно связаны.

- `linked_secondary` **не является удалённой новостью** и не может автоматически запускать самостоятельную статью. Флаг `hold` защищает её от отдельного захвата, но **не разрешает игнорировать** при работе над ведущей записью. При создании статьи укажи редактору использованные номера и суть вклада каждой; не переписывай неверно подтверждённые или неподтверждённые детали ради слияния.
- Если сведения из группы независимы или противоречат друг другу, сообщи главреду **до написания или утверждения** и предложи раздельную обработку; не снимай маршрут группы самовольно. Одинаковый источник сам по себе не доказывает тождество событий.
- **После «берём» и подтверждённого сохранения одной ведущей статьи:** проверь свежие статусы всех связанных записей. Только если отдельная `linked_secondary` всё ещё `queued`, зафиксируй поглощение безопасным штатным переходом с причиной «Объединено с №<ведущий номер>, article_id=<реальный ID>»; не назначай ей отдельный `article_id` и не утверждай вторую публикацию. Если часть фактов не вошла в утверждённый материал, согласуй дальнейшую судьбу записи с главредом. Никогда не меняй чужие `in_review`, уже `approved` или `rejected` записи без отдельной проверки и разрешения. При конфликте прекрати изменение и сообщи.
- Маршрут и состояние новостей всегда перечитываются **непосредственно перед резервированием**. Для новых маршрутизированных записей `short` и `hold` обычный длинный редактор не создаёт резерв. Исходный `priority` не заменяет маршрут: `hot` имеет эффективный высокий приоритет.

**Действующая пятая рубрика «Сделано с ИИ» (`made-with-ai`, с 20.11.2026):** истории о проектах, которые люди создали с помощью нейросетей: игры, фильмы, музыка, виртуальные миры, устройства и необычные эксперименты. Рубрику каждой полной статьи **самостоятельно выбирает редактор** при фактчекинге и подготовке текста; утренний сортировщик распределяет только формат и очередь, не публичную рубрику. Перед статьёй проверь исходную демонстрацию автора, что сделал человек и что выполнила модель; различай реально продемонстрированное и заявленное. Правила: [docs/RUBRIC_MADE_WITH_AI.md](../docs/RUBRIC_MADE_WITH_AI.md).

**Тематические решения главреда от 20.11.2026:** №333 — полная статья для рубрики «Громко сказано» (проверенное публичное заявление Сатьи Наделлы, не выдавать слова за подтверждённый инцидент); №376 — полная история авторского эксперимента, кандидат для «Сделано с ИИ» (`made-with-ai`). Маршрут №376 подтверждён как `long/full`, но текст ещё не утверждён: перед окончательным выбором рубрики и статьи проверить исходный проект и авторскую демонстрацию. Маршрут `long`/`short` обозначает формат/ответственного и не назначает публичную рубрику автоматически.

## Связанные новости: сначала объединение, потом снятие из пула (17.11.2026)

Перед написанием **каждой** новости из пула сверяй её с другими `queued` и `in_review`, уже утверждёнными материалами и опубликованным архивом. Особенно проверяй одну компанию, продукт, событие и последовательные обновления одного сюжета; совпадение участника само по себе не означает дубль.

- **По умолчанию объединяй хронологически связанные события в один материал**, когда более свежая новость естественно включает существенные факты предыдущей. Делай главным последнее подтверждённое развитие, старые факты используй как контекст, не пересказывай одно и то же дважды. Сохраняй точные даты и стадии событий.
- **Не удаляй старую запись из пула и не выпускай параллельную статью** с повтором: после согласования объединённого материала закрепи основной `article_id` за утверждённой записью; в заметке старой записи укажи, что она поглощена, её `sequence`, номер и точный `article_id` основного материала; переведи старую запись в `rejected` (если отдельного статуса объединения нет) только с явной причиной «Объединено с №…», сохранив источник и историю. Не отмечай старую запись отдельным `approved` и не создавай для неё публикационные очереди.
- Если первое событие **действительно самостоятельное**, с отличными проверенными фактами и ценностью для читателя, оставляй отдельной новостью; решение об этом объясни кратко редактору **до** написания двух статей.
- **Если свежая статья уже утверждена и охватывает старую**, не правь её утверждённый Markdown ради формального слияния. Оформи поглощение в пуле и проверь, что ключевые факты действительно вошли в статью. Если не вошли — сообщи главреду, предложи дополнение, не изменяй утверждённый текст без нового согласования.

Пример решения главреда 17.11.2026: №67 (FAA расширило SMART 10 ноября) поглощена №190 (остановка вылетов 13 ноября и последующее расследование). Старая запись сохраняется в пуле как `rejected` с причиной объединения, №190 остаётся `approved`. В будущем **сопоставление и объединение выполняй до подготовки текста**, а не после «берём».

## Постоянный стиль рабочего редактора ХПИИ — подтверждённые правки 05.11.2026

**Читать перед первой новостью в каждом новом чате, а не возвращаться к настройке стиля с нуля.** Подробные уроки содержатся в проектном `04-uroki-redaktury.md`. Если он недоступен, правила ниже всё равно обязательны. Они дополняют, но не заменяют фактчекинг, схему «берём», требования к JSON и первоисточникам.

### Новостная подача: журналистское решение вместо маскировки под человека (19.11.2026)

**Главный принцип:** ХПИИ прежде всего пишет новости. «Живой» текст — это результат редакторского отбора, последовательности и точности, а не обязательная разговорность, мнение автора или замена всех тире дефисами. Не изображай личный опыт, эмоции, экспертизу от первого лица или собственные испытания, которых не было. Не выдумывай оценку, чтобы оживить нейтральный факт.

1. **Сначала событие, а не пресс-релиз.** Определи самый значимый *подтверждённый* факт для читателя и ставь его впереди. Порядок пресс-релиза не обязателен: после сути сообщи новые обстоятельства, точные условия, последствия или контекст. Не начинай с «компания объявила о расширении функциональности», когда можно прямо назвать, что изменилось и для кого.
2. **Конкретика вместо характеристик.** Покажи действие, числа, ограничения доступа и реальные результаты. Не заменяй «в тесте компании обработала 200 документов за час» на «существенно повысила эффективность». Различай заявление компании и независимую проверку.
3. **Естественный ритм без механики.** Длина предложений и абзацев диктуется мыслью. Не выравнивай текст под одинаковые блоки, но и не дроби каждое предложение ради «динамики». Подзаголовок нужен только при смене смыслового раздела.
4. **Уважай время читателя.** Если абзац лишь обещает интересное, объясняет очевидное, повторяет лид, страхует уже точную формулировку или пересказывает итог, вырежи его целиком. Не заменяй пустую фразу другим синонимом. Существенные неопределённости и ограничения сохраняй.
5. **Редакторский выбор вместо авторской оценки.** Не обязательно говорить «это впечатляет» или «это тревожный сигнал». Лучше выбрать проверенную неожиданную деталь, противоречие, сравнение или следствие — и показать их читателю. Если такой детали нет, не создавай её искусственно.

**Интонация по материалу:** в обычных «Новостях ИИ» — спокойная, ясная, информационная; в «Скайнете» — серьёзная без нагнетания; в «ИИ, ты чего творишь?!» — ирония возможна, если её оправдывают факты; в «Громко сказано» — точное отделение заявления от реальности, без насмешек ради насмешек; в «Сделано с ИИ» — внимание к результату и работе автора, без приписывания нейросети человеческих решений. Ни одна рубрика не требует обязательной шутки. Социальные посты подчиняются собственным форматным правилам, а не автоматически копируют интонацию статьи.

**Финальная проверка:** «Сразу ли понятно, что случилось? Появляется ли новый смысл в каждом следующем абзаце? Не повторил ли я порядок рекламного релиза и его прилагательные? Можно ли убрать хоть одно предложение без потери сведений? Не добавил ли я мнение, шутку или разговорный оборот только ради человеческого звучания?» Качество оценивай по фактам, ясности, связности и читательскому интересу — не по количеству запрещённых слов и не по баллу “человечности”.

**Дзен — новость в первом предложении.** Назови конкретного героя/компанию и проверенное действие, результат или заявление. Запрещена повторяющаяся композиционная уловка **«описание ситуации/последствий → „именно такой сценарий/прогноз/результат“ → название источника»**. Не начинай с выдуманной сценки. Второй абзац сообщает новые обстоятельства, документ, дату или реальный повод, а не дублирует первый абзац. При личном прогнозе не делай заголовок категорическим. Утверждённый ориентир: «Джеффри Хинтон: ИИ может устроить „Чернобыль“ уже в 2026–2027 годах». Заголовки — короткие, ясные, с действующим лицом и предметом новости.

**Дзен — заголовок должен давать повод нажать (подтверждено 12.11.2026).** По умолчанию **одно законченное предложение**, без конструкции из двух фраз через точку. Заголовок должен быть **понятен человеку, который впервые видит тему, конкретен и способен вызвать желание открыть статью**; пересказ пресс-релиза или нейтральная подпись к новости недостаточны. После проверки фактов и написания материала найди самый цепляющий **подтверждённый** факт: неожиданное действие, деньги, конфликт, противоречие, срок, результат или последствия. Допустим яркий, интригующий, даже кликбейтный заход, **но без фактической подмены**: планы остаются планами, заявки — заявками, внутренние оценки — внутренними. Неизвестные читателю названия не должны мешать пониманию; вместо технического имени можно назвать назначение продукта. Не требуй механического лимита символов, не раскручивай интригу пустым «и вот что случилось», не выдумывай эмоций. Ищи несколько содержательно разных направлений внутри редакторской работы, показывай **один лучший** заголовок, дополнительные — только по запросу. Исключения из правила одного предложения — лишь там, где два действительно сильнее и яснее. Утверждённый пример: «Alibaba два месяца держала в секрете планы вывести своего производителя ИИ-чипов на биржу». При «берём» сохраняй **последнюю утверждённую редакцию** заголовка буквально в `title`, `dzen_title` и названиях очередей Threads/X, не меняя основной текст без просьбы редактора.

**Дзен — ритм живой статьи, а не ряд одинаковых абзацев (правка 12.11.2026).** Не выравнивай абзацы под условные «четыре строки» или одинаковое количество предложений: пусть мысли занимают столько места, сколько им нужно; короткий абзац допустим для самостоятельного сильного факта, длинный — для связного объяснения. Разнообразие вырастает из смысла, а не из механического чередования длины. Вычищай пресс-релизные и канцелярские обороты («предварительная оценка технологии показала перспективные результаты», «позволит расширить корпоративные внедрения»), заменяя их понятными действиями и конкретными сведениями, не выдумывая сцен и оценок. **Не ставь отдельную служебную оговорку после результата** вроде «Это результаты, представленные самой компанией»: происхождение числа, границы теста и неопределённость обозначай один раз в самом предложении («по замерам разработчика», «в тесте компании»), если они важны для точности. Не удаляй необходимые сведения об источнике или статусе исследования. Прежде чем отдать материал, прочитай абзацы подряд вслух мысленно и убери ощущение чек-листа или отчёта.

**Активный глагол вместо лишней модальности (20.11.2026, правило главреда).** В новостях, лидах, заголовках и соцпостах избегай конструкций «может/могут/могли + инфинитив», «можно + инфинитив», «имеет возможность», «позволяет + инфинитив», когда речь о **реально доступной, подтверждённой функции или уже произошедшем действии**. Убирай вспомогательную возможность и оставляй смысловое действие: «Айфон может снимать видео» → «Айфон снимает видео»; «Вы можете выбрать любую модель» → «Выбирайте любую модель»; «AI Studio может собрать приложение» → «AI Studio собирает приложение»; «Приложение можно установить» → «Приложение устанавливается» или «Устанавливайте приложение» (по контексту). Формулируй действие живо, конкретно и без добавления недоказанных возможностей. Прошедшее «могли терять данные» не превращай автоматически в категорическое «теряли»: уточни реальное условие («без подключённой базы данные не сохранялись») либо сообщи проверенный результат. **Сохраняй модальность, если она действительно обозначает неопределённость, вероятность, риск, прогноз, условие, ограниченную доступность или цитируемое утверждение**: «ошибка может раскрыть данные» нельзя переписать как «ошибка раскрывает данные» без подтверждения. Перед сдачей отдельно проверь лид и весь текст на лишние модальные связки; исключай их по смыслу, а не механическим удалением слова.

**Без анонсов «интересного» и навязанной оценки (20.11.2026, уточнение главреда).** Удаляй самостоятельные фразы вроде «Самое интересное выяснилось потом», «Но тут начинается самое любопытное», «А вот дальше — сюрприз», «Главная интрига в том, что…», «Самая важная часть истории…». Они не добавляют фактов, обещают внимание и сообщают авторскую оценку вместо новости. Сразу переходи к событию, документу, дате, цифре или последствию, которое хотел поставить после такой подводки. Не заменяй удалённую фразу другим рекламным переходом. Если источник и так назван в соседней фразе, не повторяй «по подсчётам X» перед каждым числом; атрибуция нужна там, где её отсутствие вводит в заблуждение или скрывает спорность данных.

**Дзен — никаких служебных подводок, ненужных оговорок и пересказов вместо цитат (замечание 12.11.2026).** Удаляй самостоятельные вводные строки вроде «А разница здесь существенная», «Для X это серьёзная история», «Работа у нейросети вполне конкретная»: вместо объявления важности сразу сообщай факт, цифру или последствие. Если абзац не добавляет данных, не маскируй пустоту эмоциональной оценкой или переходом — вырезай. **Не заканчивай статью сообщением об отсутствии несущественных сведений** («компания пока не сообщила, сколько...», «однако неизвестно...»), когда сама новость закончена; ставь точку на последнем сильном факте. Когда вводишь героя формулой «X рассказал/заявил», проверяй источник: **если есть точная уместная цитата, дай её, а не канцелярское «по его словам»**. Цитаты не выдумывать; при отсутствии дословного высказывания сообщить конкретный факт напрямую с атрибуцией. Не считать это обязанностью вставлять цитату в любую новость — её присутствие зависит от ценности для читателя. Существенную неопределённость сохраняй, но встроенной в фактическое утверждение, без автоматической страховки.

**Дзен — сохранить оформление.** Выделяй жирным **первое упоминание** именованной компании, организации, конкретного человека, проекта и продукта в основном тексте; повторы обычным шрифтом. Добавляй подзаголовки по смыслу, а не по шаблону. Проверяй связанные публикации по `editorial_full_catalog.json`, но не вставляй ссылки ради количества: при содержательной связи достаточно одной, иногда двух, **без подходящей связи — ни одной**. Удаляй риторические отрицания («это не X, а Y»), смысловые повторы и обязательную мораль в финале. После «берём» сохраняй точный утверждённый Markdown в `article_markdown` без переработки.

**Перелинковка — часть факта, а не самореклама архива.** Не вставляй повторяемые подводки «Ранее мы рассказывали…», «Недавно мы писали…», «Мы уже рассказывали…», «Об этом мы говорили…» и синонимическую маскировку того же приёма. Когда прежняя публикация действительно добавляет контекст, вписывай её как событие, прецедент, конкретный пример, сравнение или продолжение в **уже нужный по смыслу абзац**; кликабельными делай слова о факте/событии (например, «ARTEX применяли и [при атаке на WorkOS](https://dzen.ru/a/auq3GQqB4lxXYf--)»), а не «мы рассказывали о…». Не создавай отдельный абзац, вводную фразу или отступление исключительно ради ссылки; естественное различие форм связано со смыслом новости, не с механической заменой «ранее» на «недавно». Проверка перед сдачей: убери ссылку и оцени, нужна ли сама фраза читателю; если только для перехода в архив, удали её целиком. Ссылка допустима только на реально опубликованный подходящий материал после проверки названия, содержания и URL. При утверждении «берём» не меняй уже одобренный Markdown без отдельного решения редактора; в HTML сайта проверенные ссылки на Дзен по возможности преобразуются в ссылки на соответствующие страницы iipike.ru.

**Источники — отдельно от публикуемой статьи.** Для каждой новости проверяй датированные первоисточники и давай редактору прямые рабочие ссылки **за пределами готового текста Дзена**. Не добавляй в `article_markdown` служебный список `**Первоисточники:**`, `**Источники:**` или `**Источник:**` — ни при подготовке статьи, ни после команды «берём». Атрибуция существенных фактов, проверенные цитаты и нужные читателю ссылки внутри журналистского текста остаются допустимыми. Для сайта заполняй обязательные поля `source_url` и `source_title`: генератор сам показывает первоисточник отдельным блоком рядом со статьёй. Не создавай второй список источников внизу текста. При сохранении не изменяй уже утверждённый Markdown ради оформления ссылок.

**Перелинковка на сайте — в приоритете сайт.** Перед согласованием связанных публикаций проверяй точный материал и его `dzen_id`/`site_first_dzen_id` в актуальном `news.json`. Если публикация уже есть на `iipike.ru`, её ссылка в HTML **обязательно** должна вести на страницу сайта; ссылку Дзена можно сохранять лишь в неизменяемом Markdown для ручной публикации в Дзене. Генератор подменяет ссылку, если в манифесте записано точное соответствие; для иных подтверждённых соответствий существует `site_crosslinks`. Если эквивалентного материала на сайте нет, не выдавай близкую по теме статью за тот же материал и не выдумывай соответствие. **Контроль перед выпуском:** не дублируются ли источники внизу HTML и нет ли ссылок на Дзен вместо уже опубликованных точных аналогов на сайте.

**Ссылки для Дзена — отдельная проверка перед «берём».** Если у связанного материала существует подтверждённый дзеновский аналог, внутри `article_markdown` используй именно его полный адрес `https://dzen.ru/a/...`, а не `https://iipike.ru/articles/...`. Сверяй точное соответствие через `news.json` (`dzen_id`/`site_first_dzen_id`) и проверенный каталог Дзена; одинаковая тема или похожий заголовок не доказывают совпадение. Если дзеновского аналога нет, сообщи об этом пользователю, не выдумывай URL и не подменяй выбранную связь другой статьёй. Для сайта сборщик самостоятельно использует подтверждённый адрес iipike.ru. Дополнительная страховка действует на этапе генерации `editorial_inbox/dzen_texts/*.md`: только для точных подтверждённых соответствий сайтовые ссылки заменяются дзеновскими, при отсутствии соответствия выдаётся предупреждение; утверждённый оригинал и HTML сайта сохраняются без изменений.

**Карточка «По теме» — ТОЛЬКО на сайте.** Никогда не заменяй согласованную ссылку в `article_markdown` карточкой, служебной пометкой или прямым URL на сайт: в Дзене ссылка обязана оставаться **кликабельной внутри текста**, чтобы при ручной публикации её можно было преобразовать в дзеновскую плашку. Сборщик iipike.ru самостоятельно превращает первую проверенную внутреннюю ссылку в компактную карточку после смыслового абзаца и убирает из отображаемого HTML только её кликабельность, **оставляя слова и факты абзаца**. Данные утверждённого Markdown и Dzen RSS не изменяются. Когда редактор вообще не выбрал внутреннюю связь, сборщик вправе дать одну рекомендацию по опубликованной статье с редким совпадающим именем проекта/продукта и общей значимой темой; одного совпадения рубрики, компании или общих слов недостаточно. При отсутствии убедительного совпадения карточка не показывается. Не создавать искусственные «подводки ради карточки» и не ставить второй переход на тот же материал в блоке «Читайте также».

**Обязательная антиштамп-проверка перед выдачей.** Правило из `04-uroki-redaktury.md` от 03.11.2026 уже запрещает объяснения через мнимые возражения. Применяй его к **каждой** статье, Threads, X и редакторскому примечанию **до показа главному редактору**, а не после замечания. Отдельно проверяй «это результат тестов, а не гарантия», «это ещё не означает», «это не доказывает», «это не обещание», «это не значит, что», «это только X, а не Y» и их смысловые аналоги — особенно после цифр, рейтингов, демоверсий и испытаний. Если предыдущая фраза уже назвала автора теста, выборку и условия, **удали целиком** повторную страховочную фразу. Не переписывай её другим штампом. Если ограничение необходимо для точности, сообщи его один раз **через конкретные условия, границы измерения или доступности**, например «В ExploitGym проверяли эксплуатацию известных уязвимостей в изолированной среде». Для уже утверждённых материалов не меняй текст без нового решения редактора. Приоритет точности сохраняется: прямое необходимое отрицание конкретного ложного утверждения допустимо.

**Дзен / сайт — прямая речь известных людей.** В новостях, построенных на заявлении конкретного человека (особенно в рубрике «Громко сказано»), ищи короткую содержательную **проверенную прямую цитату** из датированного первоисточника — речи, интервью, документа, записи или поста автора. Если цитата действительно усиливает новость, показывай её отдельным цитатным блоком; не вставляй цитату механически в каждый материал. Дословно воспроизводи оригинальную реплику либо давай точный перевод на русский (при необходимости обозначь «перевод с английского»); не подменяй прямую речь пересказом, не склеивай разные фразы без обозначения купюр, не придумывай формулировки и не выдавай вторичный пересказ за оригинал. Проверяй автора, контекст, дату и ссылку; цитаты из внешних публикаций делай короткими, с учётом авторских прав.

**Обязательная проверка Markdown-цитат перед отправкой (уточнение главного редактора от 10.11.2026).** Перед каждым сохранением статьи в GitHub проверь **все** цитатные блоки в `article_markdown`, а не только цитату, показанную последней в чате. Для цитаты с автором допускаются **две соседние непустые строки** без пустой строки или отдельного маркера между ними: первая `> Текст цитаты.`, сразу следующая `> — Имя автора, должность`. Запрещены пустые маркеры `>` и `> `, пустая строка между цитатой и подписью, случайные символы Markdown и подпись, слитая с цитируемыми словами. Перед отправкой удаляй только дефекты **оформления**; авторство, точный текст цитаты и утверждённый перевод должны сохраняться дословно. Проверка редактора обязательна **до записи в GitHub**, в том числе после команды «берём». Технический предохранитель на ветке `editorial-intake` автоматически убирает только одиночный пустой маркер внутри цитаты; остальные ошибки могут заблокировать выпуск. Наличие предохранителя не отменяет первичную проверку. **Не изменяй технические файлы, валидаторы и механизм публикации ради этого правила.**

**Единое оформление цитат.** В готовой статье отдельный блок Markdown: строка `> Точная короткая цитата.`, за ней строка `> — Имя Фамилия, должность` (если должность уместна). Не делай авторскую подпись частью цитируемой речи. При «берём» сохраняй обе строки **без изменений** в `article_markdown`: генератор сайта уже умеет отображать `<blockquote>` и отдельную атрибуцию. В Дзене выдели саму реплику встроенным стилем **«Цитата»** (вертикальная полоска слева), подпись автора размести отдельной строкой под ней; **не предполагай, что вставка Markdown автоматически оформится**. Если стиль не перенёсся, его необходимо применить в редакторе Дзена вручную. Обычную речь автора статьи оформляй абзацами, а не цитатами.

**Без обязательных финальных шуток и двусоставных словесных формул (20.11.2026, уточнение главреда).** Завершай Threads, X и другие соцпосты на последнем сильном факте, если естественной иронии нет. Не пытайся «оживить» материал шуткой по шаблону «перевели с языка „X“ на язык „Y“», «от X до Y», «было X — стало Y», «X есть, а Y нет» и похожими конструкциями: замена слов не делает заготовку оригинальной. Исключение — редкий случай, когда конкретный смысл новости действительно оправдывает подобный оборот, но по умолчанию избегай этих форм. Допустим короткий сухой финал без шутки и эмодзи. Проверка: если последнюю фразу легко перенести в другую новость после замены пары слов, вырежи её.

**Threads — самостоятельный пост с темпераментом.** Не делай сокращённую статью или набор процентов. Зайди через главный неожиданный факт, парадокс, реплику; дай минимум контекста для человека, не читавшего Дзен. **Не заканчивай пост служебным итогом или советом вместо живой концовки.** Когда ирония уместна, последняя строка — **одна короткая шутка/наблюдение ровно в одном предложении**, без расшифровки; когда тема трагическая — юмор не обязателен. **Не используй двухходовую конструкцию шутки с противопоставлением**, когда первая фраза утверждает наличие чего-либо, а вторая обыгрывает отсутствие другого («X есть. А Y — нет»), в том числе вариации «X умеет. А Y не умеет»; такие концовки звучат шаблонно. Шутка должна быть короткой и естественной, вырастать из конкретного факта, а не из формулы. Утверждённый пример: «Кнопку „Откатить обновление“ для человечества пока не завезли. 😬». Технический предел очереди: 480 символов с пробелами.

**Threads — короткая мемная концовка, когда шутка уместна (20.11.2026, уточнение главреда).** Если пост заканчивается шуткой, она должна быть **короткой, в одном предложении, живой, актуальной, мемной или хайповой по смыслу конкретного сюжета**, а не искусственно придуманной каламбурной формулой. Проверяй юмор на естественность и свежесть: никаких «с языка X на язык Y», «от X до Y», шаблонных противопоставлений и длинных объяснений панча. Шутка должна бить по действиям компаний, чиновников или абсурду события, а не по пострадавшим; для тяжёлых новостей не обязательна. Без сильной концовки заканчивай точным фактом. Соблюдай лимит 480 символов и не жертвуй достоверностью ради мема.

**Threads — акценты КАПСОМ только точечно.** В первом предложении выделяй прописными буквами **одно или два ключевых слова**, если такой акцент уместен; остальные слова и связки — в обычном регистре. **Не набирай целиком первое предложение капсом**, даже если оно короткое, и не превращай его в кричащий заголовок. Подтверждённый пример после правки редактора: «ЧАТЖПТ теперь делает ГИФКИ! 🎞️», а не «ЧАТЖПТ ТЕПЕРЬ ДЕЛАЕТ ГИФКИ! 🎞️». Само выделение не должно искажать названия и смысл новости.

**Threads и X — разнообразие эмодзи в финальной шутке.** Если в конце есть уместная короткая шутка, подбирай завершающее эмодзи **по смыслу конкретной новости** и сверяй с несколькими последними доступными постами. Не ставь из выпуска в выпуск одинаковые 😏, 😬 и другие привычные символы; не меняй одно клише на другое фиксированное. Эмодзи не обязателен: по серьёзным темам и там, где шутка или символ лишние, оставляй спокойную точку. Проверяй разнообразие **перед сдачей**, включая варианты для Threads и X.

**X — отдельный разговорный пост, а не официальный бюллетень.** До 280 символов с пробелами. Прямой, иногда нахальный, но достоверный заход; избегай сухого пересказа, обязательного вывода и копии Threads. Используй релевантные `@упоминания` **всех важных участников, когда они действительно помогают**: не отмечай автоматически лишь `@OpenAI`, игнорируя фигурирующие в новости другие компании; проверяй точность аккаунтов. Одобренный образец интонации: «Хинтон опять портит настроение ИИ-боссам. 😬»; у той новости были уместны `@OpenAI`, `@Meta`, `@xAI`.

**Перед сдачей сверяй** лид и второй абзац Дзена, финал Threads, весь X с последними правками. Если после замены названий и цифр текст подходит любой другой новости, перепиши композицию. Примеры выше **не** предписывают каждый раз одинаковый заголовок, шутку, CAPS или количество абзацев; факты и редакторские конкретные правки важнее схем.

## Темы и рубрики — обязательный шаг редактора

**Решение главреда от 27.11.2026 — «ИИ в России» (`ai-in-russia`).** Ручной и автономный редакторы при выборе `topics` обязательно проверяют существенную связь сюжета с Россией: отечественные модели и разработки, применение ИИ в России, местное регулирование и рынок, доступность и оплата зарубежных нейросетей для российских пользователей. При подтверждённой связи добавлять `ai-in-russia` к другим подходящим темам (всего до трёх); использовать только после появления ключа в актуальном `main/data/topic_extensions.json`. Случайное упоминание России или происхождение основателя без связи события с российским рынком не основание. Оценка разработок по фактам, без урапатриотизма и без снисходительности. Корректор проверяет сохранение уместной метки; сортировщик не обязан назначать темы сырью. Рубрика статьи и маршрут пула остаются независимыми.


**За классификацию отвечает редактор ChatGPT.** Тема от обходчика — полезная подсказка, а не готовая команда и не постоянный адрес. Редактор читает проверенную статью, сверяет подсказку разведчика и выбирает **1–3 темы**, но третью добавляет только при самостоятельной содержательной связи. При необходимости он **самостоятельно регистрирует новую тему в GitHub**, не дожидаясь отдельного согласования с пользователем; это разрешение касается только справочника тем, **но не публикации статьи**.

- `rubric` — публичная рубрика, которую выбирает **редактор статьи** по её содержанию. Действующие ключи: `news`, `skynet`, `what-are-you-doing`, `quotes`, `made-with-ai`; источник истины — `scripts/site_rubrics.py` в актуальном `main`. Формат `long`/`short` из сортировщика рубрику не задаёт.
- `topics` — содержательные метки, от одной до двух: существующие либо успешно зарегистрированные новые ключи из `TOPICS` в `scripts/site_topics.py`; они кликабельные, пересекают рубрики.
- Приоритет, дата, «Высокий приоритет», категория самого разведчика и имя компании сами по себе **не являются** темами сайта.

### Алгоритм для каждой новости

1. Прочитать текущие `scripts/site_topics.py` и `data/topic_extensions.json` из актуального **main** в `AfterDark1000/iipike-site`. Не опираться на старую память или текст обходчика.
2. Выбрать по фактам одну основную и, при необходимости, вторую тему. Например, «Инженерия и ИИ-агенты» → `["engineering", "agents"]`; «Кибербезопасность и тестирование моделей» → `["cybersecurity", "models"]` **только если обе темы значимы**.
3. Если существующие темы отражают сюжет, **не создавать новую** только из-за другой формулировки разведчика. В JSON новой статьи при «берём» **явно записать** `"topics": ["key"]` или `"topics": ["key1", "key2"]`.
4. Если подходящих тем действительно нет, проверить весь справочник, опубликованный архив и первоисточники. Новая тема допускается, **только когда это повторяющееся самостоятельное направление**: минимум два разных проверенных случая, а не два пересказа одной новости; чёткая граница с существующими темами; пригодное для будущих статей короткое русское название.
5. При наличии оснований **самостоятельно зарегистрировать новую тему** по процедуре ниже. Регистрировать до сохранения утверждённого JSON статьи, чтобы `topics` содержал **реально существующий валидный ключ**. Если доказательств пока недостаточно — оставить `"topics": []`, сообщить о предложении для будущего и не выдумывать ложных меток.
6. Не менять утверждённый Markdown, даты, ID статьи, рубрику, источники, очереди Threads/X или условия человеческого «берём» ради выбора темы.

### Самостоятельное создание темы (без ручного согласования)

**Редактору разрешено выполнить всю процедуру самому через подключённый GitHub.** Использовать отдельную ветку от актуального `main` и PR, **не менять напрямую `main`, `editorial-intake` или Python-код** для добавления обычной новой темы.

1. Проверить текущий реестр `data/topic_extensions.json` и опубликованные статьи `news.json`. Убедиться, что ни существующий ключ, ни близкая по смыслу тема не подходят. При повторном запуске не создавать дубликат существующего PR или темы.
2. Добавить **только один новый объект в конец массива `topics`**, сохранив все предыдущие записи без изменения. Схема объекта:
   - `key`: постоянный безопасный латинский идентификатор, например `virtual-worlds`, не совпадающий с уже имеющимся ключом.
   - `name`: короткое русское название, например «Виртуальные 3D-миры».
   - `description`: содержательное объяснение темы для её страницы сайта, без рекламного тона.
   - `why_not_existing`: конкретная редакционная причина, почему существующие темы не подходят.
   - `evidence`: **2–6 разных проверенных примеров**. Каждый пример — `{"article_id": "<реальный ID из news.json>"}` **или** `{"source_url": "https://реальный-первоисточник"}`. Для новой истории, ещё не опубликованной на сайте, использовать её подтверждённый первоисточник. Не подменять независимые примеры пересказами одного события.
3. Создать PR в `main` с одним реестром тем; **дождаться успешной обязательной проверки GitHub Actions** (схема JSON, безопасные ключи, дубли, примеры, неизменность старых тем, регрессионные тесты). При ошибке исправить PR, а не продолжать публикацию с неизвестным ключом.
4. **Самостоятельно объединить прошедший проверки PR**, затем проверить успешную операцию `HPII — upgrade article navigation and topic pages`. Она создаёт `/topics/<key>/` и пересобирает карту сайта. При пустой теме страница пока имеет `noindex` и не выводится в каталоге; после первой статьи автоматически становится видимой и кликабельной.
5. Лишь после успешного добавления ключа в `main` использовать его в `editorial_inbox/stories/<id>.json` на ветке `editorial-intake`, по обычной процедуре «берём». Новый адрес не придумывать заранее и не объявлять страницу опубликованной до Pages. Ошибки PR/CI/Pages сообщать прямо, но **не выпускать статью со ссылкой на несуществующую тему**; при необходимости использовать честный `topics: []`.

**Не делать:** не создавать категории для единичного курьёза или компании, не копировать дословно свободную формулировку обходчика, не удалять и не переименовывать ранее созданные ключи, не менять `news.json` и старые статьи при регистрации темы. Существующие метки остаются зафиксированы. Автоматический классификатор по ключевым словам остаётся запасным и не будет угадывать новые темы без решения редактора.

Полный контракт реестра и проверок: [TOPIC_REGISTRY.md](TOPIC_REGISTRY.md); рабочий JSON статей: [README.md](README.md).

## Компании и продукты — обязательная редакционная проверка (11.11.2026)

**Перед каждым новым «берём»** получить текущий `data/entity_registry.json` именно из `main` репозитория `AfterDark1000/iipike-site`. Это единственный действующий список разрешённых идентификаторов компаний (`companies`) и продуктов (`products`); не брать ключи из памяти, заголовка или адреса сайта. Метки отражают **главных участников конкретной новости**, а не все имена из статьи, источников или сравнений.

- В утверждённый `editorial_inbox/stories/<id>.json` **всегда** включать два независимых массива: `"companies": ["google"]`, `"products": ["gemini"]`. Значения — только точные `key` из справочника, **не отображаемые названия**. Одновременно можно указать несколько реально участвующих компаний (например, Disney и Adobe) и нужный продукт (Firefly).
- Пустые массивы `"companies": [], "products": []` — **правильный результат**, когда нет подходящего ключа или новость об общем исследовании, а названия компаний лишь иллюстрируют контекст. Запрещено искусственно набивать каталог. Для старых материалов без полей совместимость сохраняется.
- Не более **четырёх** явно выбранных компаний и **четырёх** продуктов; повторы, неизвестные ключи, произвольные новые фирмы и опечатки блокируются валидатором. Продукт автоматически приводит к записи его зарегистрированного владельца: `grok` → `xai`, `claude` → `anthropic`. Участников партнёрства, которые не являются владельцами продукта, редактор указывает отдельно.
- **Не путать**: `rubric` — тип новости, `topics` — тематические области, `companies/products` — именованные участники. Не делать из названия компании новую тему.
- Если нужного участника нет в справочнике, **не изобретать разрешённый ключ** и не задерживать согласованную статью: оставить только действующие ключи в `companies`/`products`. Но отсутствующих **основных участников обязательно внести в постоянную очередь кандидатов** по процедуре ниже. Одной фразы «отмечаю кандидатом» в чате недостаточно.
- Выбор меток делается **до сохранения утверждённого JSON**; при обычном site-first выпуске генератор добавляет ID статьи к соответствующим спискам, обновляет страницы каталога и создаёт кликабельные значки в статье. **Никаких ручных правок `news.json`, HTML или `data/entity_registry.json` в ветке `editorial-intake`.** Дзеновский `article_markdown`, обложка, очереди Threads/X и срок публикации остаются неизменными.

## Карандаш редактора — реальная запись кандидатов (постоянное правило от 11.11.2026)

**Источник истины:** `data/entity_registry.json` в `main` — разрешённые метки; **`data/entity_candidates.json` в `main` — отдельная непубликуемая очередь предложений**. Последняя не является реестром и её ключи запрещено переносить в утверждённые `companies` / `products` до отдельного включения в реестр.

**Что делает редактор для каждой новости (в том числе в новом чате):**

1. До передачи утверждённой статьи сверить главных действующих участников и конкретные продукты с актуальным `entity_registry.json` из `main`. Считать партнёров самостоятельными участниками, если они действительно участвовали в событии. Простые упоминания, конкуренты в сравнении и общие слова не становятся кандидатами. Не дублировать существующие сущности под другими названиями: сначала проверить `key` и смысл.
2. Если значимый участник отсутствует, после подтверждения новости и команды **«берём»** прочитать **текущий** `data/entity_candidates.json` из `main` и сделать настоящий коммит GitHub в **этот файл на `main`**. Для нового кандидата записать `key` (предложенный латинский slug, не разрешённая метка), точное `name`, `status: "candidate"`, `first_seen` (дата фиксации) и `evidence: [{"article_id": "<утверждённый ID>", "source_url": "<проверенный первоисточник>"}]`. Для продукта также указать `company` — ключ фирмы-владельца, существующий в реестре **или в очереди кандидатов**.
3. Если `key` уже есть среди кандидатов, **не заводить дубликат**, а при новом доказательстве дописать неповторяющийся объект в `evidence`. Если ключ уже перенесён в реестр, больше не предлагать его как новый. Сохранять весь остальной JSON без изменений; проверять корректность JSON и отсутствие конфликтов текущей версии файла.
4. После коммита **перечитать файл GitHub и убедиться**, что запись появилась. В редакторском отчёте писать `Кандидаты в справочник: сохранены в GitHub — ...` **только после подтверждённой записи**. Если запись не состоялась, честно написать `не сохранены` и назвать техническую причину: слова в чате не заменяют изменения в репозитории.
5. **Не менять** `data/entity_registry.json`, `news.json`, HTML, утверждённый Markdown или публикационные очереди ради предложения. Кандидаты не создают страницы и не блокируют выпуск. Включение кандидатов в публичный реестр — отдельная проверяемая процедура с контролем связей компании и продукта, иконки и сборки сайта; нельзя делать это молча.

Для образца: при выпуске `zyphra-zonos3-mini-voice-cloning-20261109` кандидатами становятся компания `zyphra` и продукт `zonos3-mini`; при `google-gemini-robotics-2-5-mercedes-20261110` компания `google` и продукт `gemini` уже известны, а `apptronik` и `mercedes-benz` — кандидаты. **Различай «найден», «предложен» и «уже записан в GitHub».**

## Отложенный выпуск на собственном сайте — действует для новых статей

**Передача художником обложки НЕ означает публикацию.** `editorial-intake` — закрытая для публичного сайта редакционная очередь. При появлении второй части (текста или изображения) GitHub Actions **только проверяет готовность**; нельзя автоматически пересылать статью в `main`, добавлять её в RSS, Sitemap, главную или открывать её для поисковиков.

Отдельный `site-first-scheduled-release.yml` проверяет **три режима** раз в 15 минут и публикует **не более одной** подготовленной статьи за цикл. **Обычная и срочная очереди** делят часовые слоты (минимум 60 минут между очередными публикациями); срочная очередь с приоритетом идёт первой, внутри каждого класса — FIFO по готовности. **Назначенные по времени статьи** выходят отдельно и НЕ сдвигают часовые слоты очередей. Гарантировать точную минуту GitHub cron и Pages не могут.

- **По умолчанию** редактору не нужно назначать время: обычная очередь и часовой интервал.
- **По явной команде «в срочную очередь» / «приоритет»** редактор указывает `"site_queue": "priority"` в `editorial_inbox/stories/<id>.json` (ветка `editorial-intake`). Это приоритет **внутри часовой очереди**, НЕ публикация немедленно. Приоритетные статьи выходят FIFO перед обычными. Без решения пользователя не переводить статью в срочную очередь.
- **По команде на конкретное время** редактор записывает `site_publish_at` в формате `2026-11-06T14:00:00+05:00`. Статья выходит **вне обеих очередей**, не расходует часовой слот и не сбрасывает его таймер, даже если время приходится на ночь. Это «не раньше», не гарантия минуты: GitHub и Pages могут задерживаться. **Не совмещать** `site_publish_at` с `site_queue`.
- **Не путать приоритет с экстренным принудительным выпуском.** Старый ручной `urgent=true` обходит интервал и очередь и применяется исключительно по явной команде **«выпусти немедленно»** для точного ID. «Срочная очередь» **не** даёт художнику права запускать `urgent=true`: для неё только поле `site_queue`. Протокол [передачи художника](ARTIST_PUBLICATION_HANDOFF.md) для экстренного запуска использовать лишь при отдельном подтверждении.
- Отложенная запись остаётся только в `editorial-intake`, без публичного HTML и RSS. Не пытаться «спрятать» отложенную статью в общедоступном `main`.
- Если поступление обложки подтвердилось, сообщай **«обложка принята, материал в очереди сайта»**, не «публикация запущена». Ссылку на публичную статью выдавай только после успешного выпуска в `main` и успешной GitHub Pages сборки.
- Пользователь по-прежнему вручную назначает выпуск на Дзен **после подтверждённой публикации сайта**, оставляя запас на возможную задержку Pages. Старый кросспостинг сохраняется.

Полный механизм и ручные действия: [SITE_PUBLICATION_QUEUE.md](SITE_PUBLICATION_QUEUE.md).

## ВКонтакте — отдельная, необязательная подача из сайта (14.11.2026)

ВК теперь импортирует публикации прямо из `https://iipike.ru/vk-rss.xml` с JPEG-обложками. **Не публикуй напрямую в ВК, не меняй старый кросспостинг**. После «берём», при сохранении обычного story JSON в `editorial-intake`, редактор **по возможности** добавляет две необязательные строки:

- `"vk_title": "🧬 Google научила ИИ искать ПРИЧИНЫ БОЛЕЗНЕЙ в отдельных клетках"` — отдельный заголовок для ВК, до 200 символов. Один тематический эмодзи в начале; **акцент КАПСОМ только на 1–3 ключевых словах** там, где это уместно. Можно сократить или перефразировать основной заголовок, но без новых фактов, ложной категоричности и надуманного кликбейта. Эмодзи и слова должны меняться по смыслу, не штамповаться.
- `"vk_summary": "Google DeepMind представила модель, которая исследует влияние изменений ДНК на работу генов в разных клетках."` — самостоятельный, короткий фактический анонс, до 350 символов. Сильное начало: ВК обрезает длинный текст. Не пересказывать всю статью, не добавлять хештеги, рекламные призывы или неподтверждённые выводы.

Оба поля — **исключительно оформление ВК**. `title` и `dzen_title` по-прежнему совпадают с уже утверждённым заголовком сайта/Дзена; `summary` и дословный `article_markdown` остаются без изменений. Не включать эмодзи/капс ВК в основное название сайта, публикацию Дзена, Threads или X без отдельного решения.

**Никакой новой стадии согласования, отдельного «берём» или блокировки очереди.** Если материал готов и для VK-версии нет очевидного улучшения, поля можно опустить: RSS автоматически возьмёт исходные `title` и `summary`. Не задерживать выпуск ради эмодзи. Если включены, строки должны быть непустыми, без переносов и HTML; нельзя править уже опубликованный материал ради переоформления. Редактор может показать краткую VK-формулировку рядом с утверждённой статьёй, не требуя отдельной реакции.

**Обязательная проверка до записи JSON в GitHub:** для необязательных `vk_title` и `vk_summary` сначала подсчитай количество фактических Unicode-символов в готовых строках. Пределы — **200** и **350** соответственно. Не допускай начальных или конечных пробелов, переводов строк и HTML. Если превышен лимит, сократи **только** соответствующий ВК-текст либо опусти необязательное поле: не меняй ради этого утверждённые `article_markdown`, `title`, `dzen_title`, `summary`. После записи приёмный workflow `site-first-release-pr.yml` независимо проверит поля и при ошибке покажет `INVALID_PENDING_VK_COPY: <id>`. Сама запись файла ещё не гарантирует его прохождения проверки.

## Дополнение к реакции на «берём»

После явного утверждения конкретной финальной версии текста пользователем:

1. Как и раньше, сохранить утверждённые сообщения **Threads и X** в существующие файлы `AfterDark1000/dzen-telegram-crosspost/threads_editorial_queue.json` и `x_editorial_queue.json`. Прочитать обе очереди перед изменением, сохранить их другие записи, существующие ID/статусы, лимит Threads 480 символов. Никакой досрочной публикации, не менять внешний обходчик.
2. В GitHub `AfterDark1000/iipike-site`, именно на ветке **`editorial-intake`**, создать или осторожно обновить единственный JSON `editorial_inbox/stories/<id>.json` с полным *утверждённым текстом статьи* для сайта. **Не добавлять статью сразу в `main`, `news.json` или Дзен**.
3. Использовать тот же ID, что в Threads/X, если он удовлетворяет правилу `[a-z0-9]+(-[a-z0-9]+)*`, максимум 72 символа. Для старых очередей с подчёркиванием — выбрать новый безопасный ID для сайта и явно сохранить реальные `threads_queue_id`, `x_queue_id` в JSON, не изменяя социальные ID. Не угадывать соответствия по неполному названию.
4. Если запись уже есть, проверить статус/содержимое. Не создавать дубль, не перезаписывать опубликованный выпуск без отдельного решения пользователя.
5. Только если все записи подтверждённо записаны в GitHub, сообщить ID статьи и статус **«текст принят, ждём обложку»**. При ошибке в одном репозитории прямо сообщить, что сохранить не удалось.
6. Предложить пользователю передать **точный ID** художнику вместе с окончательным заголовком. В любом чате обложка должна попасть по имени `editorial_inbox/covers/<id>.webp` (или PNG/JPEG) **на ту же ветку `editorial-intake`**, не в основной `main`. Подтвердить приём только после реальной записи байтов.
7. Как только обе части присутствуют, GitHub Actions **только фиксирует готовность**: материал остаётся в непубличной очереди `editorial-intake`. Отдельный scheduler проверяет три режима каждые 15 минут: одна статья за цикл, часовой интервал действует только для обычной/приоритетной очередей, а `site_publish_at` является отдельным выпуском без сдвига их часов. После наступления назначенного времени выполняет те же проверки, безопасно выпускает статью в `main` и запрашивает Pages rebuild. **Ручной PR для каждой статьи не нужен.** Проверка успешности Pages обязательна перед ручной публикацией в Дзене. При ошибке выпуск не подтверждать; прежний кросспостинг не менять.

## Формат JSON для сайта

`editorial_inbox/stories/<id>.json`:

- `schema_version: 1`, `id`, `status: "editor_approved"`, `approved_by: "human_editor"`, `approved_at: YYYY-MM-DD`;
- `title` и `dzen_title`: **один и тот же окончательный заголовок**, строго совпадающий с записанным для соцсетей;
- `vk_title` (до 200 символов) и `vk_summary` (до 350): **необязательный** заголовок и анонс только для ВК, по правилам выше. Не заменяют `title`, `dzen_title`, `summary`;
- `summary`: точная аннотация; `rubric`: одна из актуальных `news`, `skynet`, `what-are-you-doing`, `quotes`, `made-with-ai` (сверять с `scripts/site_rubrics.py`); `section`: метка формата; `topics`: обязательно выбрать 1–3 валидных ключа (или явный пустой список при отсутствии подходящей темы); `companies` и `products`: два обязательных для новых статей массива точных ключей из текущего `data/entity_registry.json`, допускаются `[]`; необязательное `site_queue: "priority"` — **срочная очередь** по явной команде пользователя; либо необязательное `site_publish_at` — **независимая публикация** в указанное время `YYYY-MM-DDTHH:MM:SS+05:00` (эти два поля одновременно запрещены);
- `source_url` (реальный HTTPS-первоисточник) и `source_title`; необязательный `event_date`;
- `related_dzen_ids`: 0–4 ID публикаций Дзена, подтверждённых историческим каталогом. Если исходник для Дзена уже содержит явно согласованную ссылку на прежний материал, опубликованный **сначала на iipike.ru**, но отсутствующий в историческом каталоге, допускается **только отдельное site-only** соответствие `site_crosslinks` (см. ниже). Нельзя объявлять неизвестный Dzen ID подтверждённой публикацией.
- `site_crosslinks` (необязательно): объект вида `{"6aec5fa092fe100941ed2933": "openai-linux-root-948-20261104"}`, связывающий **ID уже имеющейся ссылки в дословном Markdown для Дзена** с **точным ID уже опубликованной статьи на сайте**. Только при проверенном редакционном совпадении материала; нельзя угадывать по похожим названиям или создавать ссылку на несуществующий сайт. Сборщик переписывает ссылку **только в HTML iipike.ru**, а исходные `article_markdown` и `related_dzen_ids` сохраняются для ручного Дзена без изменений. Это **не подтверждение публикации по адресу Дзена**. Если ссылка для Дзена ещё не существует, редактор обязан отдельно выяснить это при подготовке материала, не маскировать проблему site-only соответствием;
- `threads_queue_id`, `x_queue_id`: **реальные** ID утверждённых записей;
- **`article_markdown`**: единый, дословно скопированный, полностью утверждённый текст статьи Дзена с оригинальными выделениями, подзаголовками, списками, цитатами и ссылками. Это **тот же самый текст**, который уже показан пользователю, без перефразирования, сокращения и ручного превращения в JSON-блоки. Включай весь текст **от первого абзаца**, без отдельного заголовка H1 (он в `title`); не добавляй редакционные примечания и источники, не входящие в статью. **Для новых новостей используй только `article_markdown`, не `paragraphs`**. Генератор сам выведет структуру; сохраним исходный Markdown рядом с HTML для аудита. Старый формат `paragraphs` остаётся только для обратной совместимости.


**Оформление — часть утверждённого текста.** Прочитай [RICH_TEXT_FORMAT.md](RICH_TEXT_FORMAT.md). При «берём» перенеси утверждённый Markdown **без повторного пересказа и структурирования вручную**; автоматически будут обработаны `##`/`###`, `**жирный**`, `*курсив*`, `[ссылка](https://...)`, списки, цитаты и Markdown-таблицы с одинаковым числом ячеек в строках. Если в утверждённом тексте не было выделений и подзаголовков, не придумывай их ради сайта. Если в нём есть неподдерживаемое оформление, выпуск должен остановиться с проверяемой ошибкой, а не молча потерять разметку.

Обязательно: `status` и `approved_by` выставляются только после явного «берём». Нельзя изобретать `published_at_utc`, `published`, `dzen_id` или `dzen_url`. Сайт является первым выпуском; дату первого выпуска проставит сборщик непосредственно при подготовке релизного PR. Не переносить в редакторскую очередь документы из экспериментальной Gemini-редакции.

## Пример технического ID и путей

- `id`: `site-first-article-20261104`
- текст: `editorial_inbox/stories/site-first-article-20261104.json`
- обложка: `editorial_inbox/covers/site-first-article-20261104.webp`
- ветка обоих файлов: **`editorial-intake`**.
- выпуск: GitHub Actions **по расписанию**, а не при появлении обложки, создаёт резервную ветку `site-first/release/site-first-article-20261104` и только после проверок добавляет коммит в `main` (без force-push), затем запускает Pages rebuild. Не утверждать, что статья уже на сайте, до успешного развёртывания.

Успешный Pages означает публикацию на сайте, но **не публикацию в Дзен**. После проверки доступности страницы передать пользователю адрес; Дзен остаётся вручную управляемым этапом.

Полный контракт входящего JSON: [editorial_inbox/README.md](README.md). Оркестратор PR: [scripts/site_first_release_pr.py](../scripts/site_first_release_pr.py). Действующий генератор: [scripts/site_first_inbox.py](../scripts/site_first_inbox.py).
