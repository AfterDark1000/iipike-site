# ХПИИ — единый редакционный вход: сайт первым

**Основной редактор — ChatGPT.** Экспериментальные Gemini/FLUX workflow не участвуют. Это актуальные правила для новых статей после пилотного выпуска Astra 4 ноября 2026 года.

## Рабочий порядок

1. Агент-разведчик присылает подборки; человек отправляет интересную новость редактору ChatGPT.
2. Редактор проверяет первоисточники, оформляет **одну полную статью для Дзена** и отдельные Threads/X-посты. После решения человека «берём» сохраняет Threads/X в прежние очереди репозитория `AfterDark1000/dzen-telegram-crosspost` и **дословный утверждённый Markdown** статьи в `AfterDark1000/iipike-site`, ветка `editorial-intake`, путь `editorial_inbox/stories/<id>.json`.
3. Художник из своего чата записывает оригинальную картинку (реальные байты WebP/PNG/JPEG, 16:9) в `editorial_inbox/covers/<id>.webp` **той же ветки**. Только точный ID связывает статью и изображение. Если байты недоступны инструментам, нельзя заявлять о передаче.
4. При появлении обеих частей GitHub Actions **только проверяет и ставит материал в непубличную очередь**. Статья ещё **не создаётся в публичном `main`**. `site-first-scheduled-release.yml` проверяет очередь каждые 15 минут и публикует не более одного готового материала с интервалом минимум **60 минут** после предыдущей site-first публикации. Учитывает назначенное редактором `site_publish_at` в часовом поясе Усть-Катава/Екатеринбурга (`+05:00`). Перед выпуском проверяются утверждение, оригинал статьи, источник, обложка, отсутствие дублей и весь архив; только затем собираются HTML, RSS, Sitemap, главная и рубрики. Создаётся контрольная ветка `site-first/release/<id>`, выполняется безопасный fast-forward `main` (без `--force`). Ручной PR **для каждой новости не нужен**.
5. Поскольку коммит GitHub Actions не запускает обычную пересборку Pages, scheduler **явно запрашивает Pages rebuild через GitHub API**. Только после успешного развёртывания статья становится доступна на `iipike.ru`. Не путать завершение записи в `main` с успешным деплоем.
6. После появления новой статьи на сайте человек **вручную** публикует тот же материал с обложкой в Дзене. Затем старый внешний обходчик активирует существующий кросспостинг в Telegram, VK, Threads, X и другие площадки. Новый сайт-конвейер сам в Дзен и социальные сети не отправляет.

**Разрешение на сайт-публикацию:** явное «берём» + успешная доставка обложки + наступление времени очереди (не раньше указанного `site_publish_at`, если оно есть, и не чаще одного материала за 60 минут). Приём обложки **не запускает публикацию**. Вручную можно инициировать выпуск конкретной готовой статьи с `urgent=true` только по явному решению пользователя. При отсутствующем компоненте, ошибке проверки, новых коммитах в `main` или недоступном Pages API выпуск останавливается с ошибкой; резервная ветка остаётся для диагностики. Система не перезаписывает чужие изменения.

## Контракт нового редактора

Один файл `editorial_inbox/stories/<id>.json`, где `id` — малые латинские буквы, цифры и дефисы, длина до 72. Источник всегда реальный HTTPS. `status=editor_approved` выставлять исключительно после решения человека «берём».

~~~json
{
  "schema_version": 1,
  "id": "example-verified-ai-news-20261104",
  "status": "editor_approved",
  "approved_by": "human_editor",
  "approved_at": "2026-11-04",
  "title": "Точный окончательный заголовок для Дзена и сайта",
  "dzen_title": "Точный окончательный заголовок для Дзена и сайта",
  "summary": "Короткая точная аннотация новости.",
  "rubric": "news",
  "section": "НОВОСТИ ИИ",
  "topics": ["agents", "engineering"],
  "site_publish_at": "2026-11-06T14:00:00+05:00",
  "source_url": "https://example.org/verified-primary-source",
  "source_title": "Подтверждённый первоисточник",
  "related_dzen_ids": [],
  "threads_queue_id": "example-verified-ai-news-20261104",
  "x_queue_id": "example-verified-ai-news-20261104",
  "article_markdown": "Полный **утверждённый текст** статьи, точно как у редактора.\n\n## Первый раздел\n\nТот же текст, без переписывания и сокращений."
}
~~~

`article_markdown` — **единственный оригинал статьи**, тот же, что редактор уже показал пользователю для Дзена. Без повторного заголовка H1 и без самостоятельного Markdown-разбора редактором. Включает реальные абзацы, `##`/`###`, жирный, курсив, HTTPS-ссылки, маркированные/нумерованные списки и цитаты, если они действительно присутствуют в утверждённом тексте. **Не придумывать оформление, которого не было**, и не терять имеющееся. Полный формат и пример: [RICH_TEXT_FORMAT.md](RICH_TEXT_FORMAT.md).

Скрипт `scripts/site_rich_text.py` автоматически выводит HTML-блоки, а исходный Markdown сохраняется и при переносе в `content/approved/<id>.json`. Производственный publisher проверяет их точное соответствие. **Нельзя передавать для новой статьи и `article_markdown`, и `paragraphs` одновременно.** Устаревшие одобренные записи с `paragraphs` продолжают работать ради совместимости с историческим архивом.

## Темы статей — дополнительная навигация

**Рубрик по-прежнему четыре.** В шапке страницы отображается только ссылка на рубрику; `section` сохраняется для редакционных данных, но больше не дублирует её название и не выдаёт служебное «ИСТОРИЧЕСКИЙ АРХИВ» читателю.

**Редактор ChatGPT назначает темы при подготовке каждой утверждённой статьи.** `topics` — массив из 1–3 ключей (третий — при отдельной содержательной связи) из **актуального** `TOPICS` в `scripts/site_topics.py` (17 встроенных + валидированные расширения `data/topic_extensions.json`). Тематические подписи обходчика — подсказки, а не готовые ключи; приоритет, дата, имя компании не становятся темой. Если существующие категории не описывают сюжет и есть **два разных проверенных случая**, редактор **сам создаёт новую тему через PR в GitHub**, проверяет CI и объединяет PR без отдельного согласования; затем передаёт новый ключ в утверждённый JSON на ветку `editorial-intake`. Когда доказательств недостаточно, допустим явный `"topics": []` и предложение будущей темы. Человеку не нужно вручную сортировать новости. Полная процедура и ограничения: [TOPIC_REGISTRY.md](TOPIC_REGISTRY.md). Резервный классификатор по заголовку и аннотации оставлен для старых/неполных записей.

Текущие ключи (17, **не жёсткий потолок**): `agents` (ИИ-агенты), `safety` (Безопасность и контроль), `cybersecurity` (Кибербезопасность), `development` (Разработка и код), `infrastructure` (Инфраструктура ИИ), `engineering` (Инженерия и устройства), `models` (Модели и исследования), `video` (Генерация видео), `images` (Генерация изображений), `audio` (Голос и звук), `business` (ИИ в бизнесе), `society` (Законы и общество), `search` (ИИ-поиск и веб), `health` (Медицина и биотехнологии), `science` (Наука и экология), `finance` (Деньги и инвестиции), `apps` (Приложения и сервисы). **Источник истины — непосредственно `TOPICS` в коде**, а не этот текст, который может устареть.

Метки **кликабельны** и ведут на самостоятельные страницы `/topics/<key>/`; каталог тем находится по адресу `/topics/`. Темы пересекают рубрики: материалы из «Новости ИИ» и «Скайнет просыпается» могут иметь одинаковую тему `agents`.

**Как расширяем справочник:** редактор проверяет уже существующие темы и архив, подтверждает как минимум два независимых случая, дописывает новый объект **только** в `data/topic_extensions.json` в отдельной ветке, открывает PR, дожидается зелёных проверок и сам объединяет его. GitHub автоматически создаёт тематическую страницу и обновляет карту сайта; после публикации первой статьи по новой теме страница появляется в каталоге. Ключи старых тем и ссылки не меняются. Подробности: [TOPIC_REGISTRY.md](TOPIC_REGISTRY.md).

Для существующего архива назначение тем производится один раз скриптом `scripts/upgrade_article_navigation.py`, после чего фиксируется в `news.json`; будущие изменения словаря не должны автоматически переименовать все исторические статьи. Для исправления ошибки используется явная корректировка `topics` в метаданных и пересборка страниц, **не изменение утверждённого текста или дат**.

Доступные рубрики: `news`, `skynet`, `what-are-you-doing`, `quotes`. Связи `related_dzen_ids` — максимум четыре, только проверенные. `threads_queue_id`/`x_queue_id` должны ссылаться на **реальные** записи старых очередей. Заголовок Дзена при сохранении и ручной публикации не должен самовольно меняться, иначе кросспостинг не найдёт соответствие.

Не записывать во входящий JSON `published`, `published_at_utc`, `dzen_url`, `dzen_id` и выдуманные даты. Дата утверждения — не дата первого выпуска. Дата сайта ставится в момент подготовки реального публикационного коммита.

## Отложенная публикация

По умолчанию редактор не обязан устанавливать время: сайт возьмёт следующий свободный слот с интервалом **не менее часа** между выходами, проверяя очередь каждые 15 минут. Точное время, заданное человеком, передаётся необязательным полем `site_publish_at`: только полная запись `YYYY-MM-DDTHH:MM:SS+05:00` (например, `2026-11-06T14:00:00+05:00`). Это **нижняя граница**, не гарантия выхода с точностью до минуты: GitHub Actions и Pages могут задерживаться. При изменении расписания достаточно отредактировать `site_publish_at` в соответствующем непубличном JSON **до публикации**; текст и обложка остаются прежними.

Срочную новость можно отправить из GitHub Actions вручную через `HPII — site-first scheduled hourly queue`, заполнив точный `story_id` и `urgent=true`. Этот обход интервала и заданного времени допускается **только по явной просьбе пользователя**. Подробности и диагностика: [SITE_PUBLICATION_QUEUE.md](SITE_PUBLICATION_QUEUE.md).

## Приём обложки из любого чата

Настоящая бинарная обложка должна появиться в GitHub `editorial-intake` по точному имени `editorial_inbox/covers/<id>.<ext>`. Поддерживаются WebP/PNG/JPEG, горизонтальный формат 16:9, минимум 780×430, максимум 16 MiB. Для выгрузки оригинальных байтов использовать GitHub Blob API (base64), Git tree/commit/ref; обычная запись UTF-8 текста и ссылка на интерфейс ChatGPT **не являются передачей изображения**. Не перезаписывать прежнюю обложку без явного согласия.

Художественное качество, соответствие новости и читаемость русского заголовка остаются редакционной обязанностью Художника и человека: технический валидатор не способен автоматически обнаруживать все визуальные дефекты.

## Автоматическое связывание с Дзеном после ручной публикации

После публикации сайта человек вручную размещает **тот же заголовок** в Дзене. Новый независимый workflow `.github/workflows/site-first-dzen-links.yml` проверяет публичный подтверждённый каталог `AfterDark1000/dzen-telegram-crosspost/editorial_full_catalog.json` раз в два часа (доступен и ручной `workflow_dispatch`). При **однозначном совпадении** утверждённого заголовка и подтверждённой даты появления статьи после сайта он дописывает в **`news.json`** отдельные поля `site_first_dzen_id` и `site_first_dzen_url` (не смешивая их с историческими `dzen_id/dzen_url`) и пересобирает только затронутые HTML-страницы внутренних ссылок. Источник `content/approved/<id>.json`, исходный Markdown, даты, обложки, очереди и социальные публикации **не изменяются**. Непроверенные, неподходящие или неоднозначные совпадения пропускаются; сбой чтения чужого каталога не должен затрагивать сайт. После коммита требуется отдельный запрос GitHub Pages rebuild, потому что push с `GITHUB_TOKEN` не запускает его автоматически.

Проверка без изменений: `python3 scripts/sync_site_first_dzen.py --catalog /path/to/editorial_full_catalog.json`. С `--apply` обновляются только `news.json` и HTML утверждённых статей. До публикации в Дзене никаких фиктивных ссылок не создаётся.

## Диагностика и безопасность

- `python3 scripts/site_first_inbox.py --audit` — просмотр состояния входящих материалов; может показывать `AWAITING_COVER`, `READY`, `COVER_AWAITING_ARTICLE` и `ALREADY_PUBLISHED`.
- `.github/workflows/site-first-release-pr.yml` — **только проверка готовности** после получения текста или обложки (никакой публикации).
- `.github/workflows/site-first-scheduled-release.yml` — реальный выпуск **одной готовой статьи** по расписанию; при ошибках смотреть журнал Actions и резервную ветку.
- `site-first/release/<id>` — резервная ветка со всеми собранными файлами; сохраняется после публикации и на случай отказа.
- `news.json`, `feed.xml`, `sitemap.xml`, главная, рубрики — обновляются генератором, а не руками редактора.
- Запрещена автопубликация экспериментальных черновиков и любых материалов без явного «берём».
