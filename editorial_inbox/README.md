# ХПИИ — единый редакционный вход: сайт первым

**Основной редактор — ChatGPT.** Экспериментальные Gemini/FLUX workflow не участвуют. Это актуальные правила для новых статей после пилотного выпуска Astra 4 ноября 2026 года.

## Рабочий порядок

1. Агент-разведчик присылает подборки; человек отправляет интересную новость редактору ChatGPT.
2. Редактор проверяет первоисточники, оформляет **одну полную статью для Дзена** и отдельные Threads/X-посты. После решения человека «берём» сохраняет Threads/X в прежние очереди репозитория `AfterDark1000/dzen-telegram-crosspost` и **дословный утверждённый Markdown** статьи в `AfterDark1000/iipike-site`, ветка `editorial-intake`, путь `editorial_inbox/stories/<id>.json`.
3. Художник из своего чата записывает оригинальную картинку (реальные байты WebP/PNG/JPEG, 16:9) в `editorial_inbox/covers/<id>.webp` **той же ветки**. Только точный ID связывает статью и изображение. Если байты недоступны инструментам, нельзя заявлять о передаче.
4. При появлении обеих частей GitHub Actions **автоматически** выполняет полную проверку утверждения, оригинала статьи, источника, картинки, отсутствия дублей, собирает статью, главную, рубрики, RSS и Sitemap. Прогоняет тесты исторического архива. Затем сохраняет отдельную контрольную ветку `site-first/release/<id>` и делает безопасный fast-forward `main` (без `--force`). Отдельный ручной PR **для каждой новости не нужен**.
5. Поскольку коммит GitHub Actions не запускает обычную пересборку Pages, workflow **явно запрашивает Pages rebuild через GitHub API**. Только после успешного развёртывания страница доступна на `iipike.ru`. Не считать один лишь коммит успешным деплоем. GitHub-бот успешно проверен на `push --dry-run` в `main` и реальном запросе пересборки текущего Pages.
6. После появления новой статьи на сайте человек **вручную** публикует тот же материал с обложкой в Дзене. Затем старый внешний обходчик активирует существующий кросспостинг в Telegram, VK, Threads, X и другие площадки. Новый сайт-конвейер сам в Дзен и социальные сети не отправляет.

**Разрешение на сайт-публикацию:** явное «берём» + успешная доставка соответствующей обложки. Повторного ручного слияния PR нет. При отсутствующем компоненте, ошибке проверки, новых коммитах в `main` или недоступном Pages API выпуск останавливается с ошибкой; уже созданная релизная ветка остаётся для диагностики. Система не перезаписывает чужие изменения.

## Контракт нового редактора

Один файл `editorial_inbox/stories/<id>.json`, где `id` — малые латинские буквы, цифры и дефисы, длина до 72. Источник всегда реальный HTTPS. `status=editor_approved` выставлять исключительно после решения человека «берём».

~~~json
{
  "schema_version": 1,
  "id": "example-verified-ai-news-20261104",
  "status": "editor_approved",
  "approved_by": "human_editor",
  "approved_at": "2026-11-04",
  "title": "Точный окончательный заголовок для Дзена и сайта",
  "dzen_title": "Точный окончательный заголовок для Дзена и сайта",
  "summary": "Короткая точная аннотация новости.",
  "rubric": "news",
  "section": "НОВОСТИ ИИ",
  "source_url": "https://example.org/verified-primary-source",
  "source_title": "Подтверждённый первоисточник",
  "related_dzen_ids": [],
  "threads_queue_id": "example-verified-ai-news-20261104",
  "x_queue_id": "example-verified-ai-news-20261104",
  "article_markdown": "Полный **утверждённый текст** статьи, точно как у редактора.\n\n## Первый раздел\n\nТот же текст, без переписывания и сокращений."
}
~~~

`article_markdown` — **единственный оригинал статьи**, тот же, что редактор уже показал пользователю для Дзена. Без повторного заголовка H1 и без самостоятельного Markdown-разбора редактором. Включает реальные абзацы, `##`/`###`, жирный, курсив, HTTPS-ссылки, маркированные/нумерованные списки и цитаты, если они действительно присутствуют в утверждённом тексте. **Не придумывать оформление, которого не было**, и не терять имеющееся. Полный формат и пример: [RICH_TEXT_FORMAT.md](RICH_TEXT_FORMAT.md).

Скрипт `scripts/site_rich_text.py` автоматически выводит HTML-блоки, а исходный Markdown сохраняется и при переносе в `content/approved/<id>.json`. Производственный publisher проверяет их точное соответствие. **Нельзя передавать для новой статьи и `article_markdown`, и `paragraphs` одновременно.** Устаревшие одобренные записи с `paragraphs` продолжают работать ради совместимости с историческим архивом.

Доступные рубрики: `news`, `skynet`, `what-are-you-doing`, `quotes`. Связи `related_dzen_ids` — максимум четыре, только проверенные. `threads_queue_id`/`x_queue_id` должны ссылаться на **реальные** записи старых очередей. Заголовок Дзена при сохранении и ручной публикации не должен самовольно меняться, иначе кросспостинг не найдёт соответствие.

Не записывать во входящий JSON `published`, `published_at_utc`, `dzen_url`, `dzen_id` и выдуманные даты. Дата утверждения — не дата первого выпуска. Дата сайта ставится в момент подготовки реального публикационного коммита.

## Приём обложки из любого чата

Настоящая бинарная обложка должна появиться в GitHub `editorial-intake` по точному имени `editorial_inbox/covers/<id>.<ext>`. Поддерживаются WebP/PNG/JPEG, горизонтальный формат 16:9, минимум 780×430, максимум 16 MiB. Для выгрузки оригинальных байтов использовать GitHub Blob API (base64), Git tree/commit/ref; обычная запись UTF-8 текста и ссылка на интерфейс ChatGPT **не являются передачей изображения**. Не перезаписывать прежнюю обложку без явного согласия.

Художественное качество, соответствие новости и читаемость русского заголовка остаются редакционной обязанностью Художника и человека: технический валидатор не способен автоматически обнаруживать все визуальные дефекты.

## Автоматическое связывание с Дзеном после ручной публикации

После публикации сайта человек вручную размещает **тот же заголовок** в Дзене. Новый независимый workflow `.github/workflows/site-first-dzen-links.yml` проверяет публичный подтверждённый каталог `AfterDark1000/dzen-telegram-crosspost/editorial_full_catalog.json` раз в два часа (доступен и ручной `workflow_dispatch`). При **однозначном совпадении** утверждённого заголовка и подтверждённой даты появления статьи после сайта он дописывает в **`news.json`** её настоящий `dzen_id` и `dzen_url` и пересобирает только затронутые HTML-страницы внутренних ссылок. Источник `content/approved/<id>.json`, исходный Markdown, даты, обложки, очереди и социальные публикации **не изменяются**. Непроверенные, неподходящие или неоднозначные совпадения пропускаются; сбой чтения чужого каталога не должен затрагивать сайт. После коммита требуется отдельный запрос GitHub Pages rebuild, потому что push с `GITHUB_TOKEN` не запускает его автоматически.

Проверка без изменений: `python3 scripts/sync_site_first_dzen.py --catalog /path/to/editorial_full_catalog.json`. С `--apply` обновляются только `news.json` и HTML утверждённых статей. До публикации в Дзене никаких фиктивных ссылок не создаётся.

## Диагностика и безопасность

- `python3 scripts/site_first_inbox.py --audit` — просмотр состояния входящих материалов; может показывать `AWAITING_COVER`, `READY`, `COVER_AWAITING_ARTICLE` и `ALREADY_PUBLISHED`.
- `.github/workflows/site-first-release-pr.yml` — автоматический выпуск при доставке обеих частей; состояние GitHub Actions нужно проверять при любых ошибках.
- `site-first/release/<id>` — резервная ветка со всеми собранными файлами; сохраняется после публикации и на случай отказа.
- `news.json`, `feed.xml`, `sitemap.xml`, главная, рубрики — обновляются генератором, а не руками редактора.
- Запрещена автопубликация экспериментальных черновиков и любых материалов без явного «берём».

Необходимые инструкции рабочего чата: [CHATGPT_EDITOR_INSTRUCTIONS.md](CHATGPT_EDITOR_INSTRUCTIONS.md). Документ для формата без потерь: [RICH_TEXT_FORMAT.md](RICH_TEXT_FORMAT.md). Код site-first: [scripts/site_first_inbox.py](../scripts/site_first_inbox.py), [scripts/site_first_release_pr.py](../scripts/site_first_release_pr.py).
