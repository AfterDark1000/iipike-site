# ХПИИ — очередь и отложенная публикация сайта

## Разделение приёма и публичного выпуска

- **Редактор** после явного «берём» записывает JSON в `editorial_inbox/stories/<id>.json` ветки `editorial-intake`; **художник** загружает обложку `editorial_inbox/covers/<id>.<ext>` в ту же ветку.
- `.github/workflows/site-first-release-pr.yml` при получении второй части **только проверяет готовность**. Она не выпускает статью, не трогает `main`, RSS и карту сайта. Статья остаётся в редакционной очереди.
- `.github/workflows/site-first-scheduled-release.yml` каждые 15 минут проверяет очередь и публикует **максимум одну** проверенную статью, не раньше **60 минут** после последней site-first публикации. Выбирает по времени готовности последнего компонента (текст или обложка); неопубликованные старые новости не теряются. Статья с назначенным сроком в будущем не блокирует другие готовые.
- В момент выбора скрипт переносит одобренный JSON и оригинальные байты обложки из `editorial-intake` во временную ветку на актуальной базе `main`, запускает полные тесты и сборщик, делает безопасный fast-forward `main` и запрашивает Pages rebuild. **До этого момента публичного HTML статьи нет.**
- Когда Pages успешно развернул сайт, пользователь может публиковать ту же утверждённую статью в Дзене по своему графику. Поскольку cron и GitHub Pages могут запаздывать, между плановым выпуском на сайте и Дзене нужно оставлять разумный резерв.

## Ручное назначение времени (Усть-Катав / Екатеринбург)

Утверждённый JSON может иметь необязательное поле:

```json
"site_publish_at": "2026-11-06T14:00:00+05:00"
```

Поле означает **«НЕ РАНЬШЕ»**, не обещание выпуска ровно в указанную секунду. Без поля — автоматический следующий доступный часовой слот. Редактор меняет поле в `editorial-intake` **только до публикации**, по поручению пользователя. Приоритет по умолчанию — порядок готовности статей, не порядок отправки команд разведчиком.

Настроенные пользователем отложенные публикации Дзена **не переносятся автоматически**: Дзен остаётся отдельной ручной площадкой; контент сначала становится доступен на iipike.ru. Если пользователь хочет совпадения дат, нужно учитывать часы/дни и задержку Pages.

## Внеочередная срочная статья

По явной просьбе пользователя запустить в GitHub Actions `HPII — site-first scheduled hourly queue` (workflow_dispatch) с **точным ID** и `urgent=true`. Обходится временная граница и часовой интервал, **но не** проверка наличия редакционного одобрения, текста, обложки, дубликатов, безопасного кода и публикационных тестов. В обычном автоматическом запуске `urgent` невозможен.

Ручной запуск с ID и `urgent=false` допустим, но **не** обходит очередь и 60 минут. Успешный запуск сборщика и push в main — только «запрошена публикация»; фактическая доступность подтверждается Pages и URL.

## Диагностика

- **READY_IN_PRIVATE_QUEUE** — обе части лежат в `editorial-intake`, но публичная страница ещё не создавалась.
- **QUEUE_READY** — проверенный список ожидающих статей, полученный из Git-дерева, без доверия к неполным webhook-полям.
- **SPACING_WAIT** — не истекли 60 минут после последней site-first статьи.
- **FUTURE_SLOT** — для статьи задан более поздний `site_publish_at`.
- **NO_DUE_STORY** — нет публикаций на этот цикл.
- **SCHEDULED_RELEASE** — запущена полная подготовка выбранной одной статьи.
- **ONE_RELEASE_REQUESTED** — проверенный выпуск записан в `main`, Pages rebuild запрошен; проверять итоговый deploy.
- **EXISTING_RELEASE_REVIEW_REQUIRED** — резервная ветка от предыдущей попытки существует; система ничего не переписывает автоматически, требуется диагностика.

Сохранение материалов в `editorial-intake` не означает, что они представлены на публичной главной, в тематических страницах, Sitemap или RSS. Статический GitHub Pages не умеет скрывать HTML по дате, поэтому нельзя размещать отложенную страницу в публичном `main` до срока.

**Резервное восстановление:** после ошибки изучить журнал запуска и резервную ветку `site-first/release/<id>`; не переотправлять новость вручную в основной сайт без исправления причины. Публикация старого материала идёт по обычному утверждённому конвейеру. Никакой Дзен/соцсети workflow scheduler сам не трогает.
