# Восстановление очереди Gemini

## Где возник перерыв

Последний запуск сборщика по расписанию 19 ноября начался в **14:28:12 по Екатеринбургу**. Оба задания завершились успешно, включая запись `commenting/queue.json` в `commenting-data`. Поле `updated_at` равно **14:28:44**. В перепроверке после 18:34 GitHub показывал успешный тестовый запуск PR и по-прежнему ни одного нового запуска этого workflow от `schedule`. В истории нет упавшего, отменённого или ожидающего планового запуска после 14:28. [Запуск, записавший данные](https://github.com/AfterDark1000/iipike-site/actions/runs/44496694602) · [История workflow](https://github.com/AfterDark1000/iipike-site/actions/workflows/commenting-queue.yml)

Workflow зарегистрирован как `active`, cron `7,37 * * * *` в основной ветке не менялся с добавления 8 ноября. Между последними двумя успешными плановыми запусками уже был разрыв около восьми часов. Во время нового перерыва GitHub API показал 282 запуска по репозиторию до 18:31, включая семь запусков других workflows по расписанию. Отдельная проверка настроек Actions через API получила HTTP 403 из-за прав интеграции, поэтому административные настройки из этого запроса неизвестны. [Коммит с cron](https://github.com/AfterDark1000/iipike-site/commit/4458ab6d0cef70d9a51374d5effa1f02e1d95f71) · [Пример успешного планового запуска другого workflow](https://github.com/AfterDark1000/iipike-site/actions/runs/44528567444)

Подтверждён разрыв до появления очередного run, поэтому в этот период сборщик и его RSS-парсер не запускались по расписанию. Внутренняя причина, по которой события не превратились в run, из истории репозитория не видна. GitHub документирует задержки и возможный пропуск запусков под нагрузкой, но данных для привязки этого сбоя к нагрузке нет. В опубликованной истории состояния GitHub не найден сопоставимый инцидент Actions за 19 ноября на время проверки. [Правила GitHub для `schedule`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) · [GitHub Status](https://www.githubstatus.com/history)

## Что подготовлено в черновике

- Сохранить исходный cron. Использовать завершение существующего watchdog на `main` как резервное событие. Оно читает только `updated_at` рабочего JSON. При возрасте более 90 минут оставляет предупреждение в Actions и запускает тот же сборщик с его существующими лимитами, ключом и записью в прежнюю ветку данных. Свежий JSON пропускает сбор. Очередь обновлений остаётся последовательной, а тесты черновых PR вынесены в свою группу конкурентности. [Workflow](../.github/workflows/commenting-queue.yml) · [Проверка возраста](../scripts/commenting_recovery.cjs)
- Резерв опирается на реальные события, которые приходили и во время сбоя. При проверке истории первый успешный подходящий watchdog после порога 90 минут завершился в 16:01:22. Это ретроспективная проверка условия, поскольку патч тогда не был активен. Резерв зависит от событий watchdog и не гарантирует точную минуту при отсутствии таких событий. [Запуск watchdog](https://github.com/AfterDark1000/iipike-site/actions/runs/44510940314)
- Браузер показывает предупреждение после 90 минут без обновления JSON и проверяет тот же файл каждые пять минут, пока вкладка видима. [Версия с предупреждением](https://htmlpreview.github.io/?https://github.com/AfterDark1000/iipike-site/blob/42f53add1d04c0c6f7d4365dce3b00486485a237/lab/dzen-first-car/index.html)

## МК и проверка восстановления

В рабочем снимке у МК был `ParseError`, но у остальных пяти лент статус был `ok`, генератор тоже завершился с `ok`. Публичная RSS-лента МК в 18:29 отдала HTTP 200 и валидный UTF-8 XML с 75 записями. Тот же парсер обработал ответ без ошибки. Подходящих по теме и возрасту заголовков было ноль. Исходное тело ответа от 14:28 в журнале отсутствует, поэтому конкретный дефект XML из того запуска неизвестен. В патче следующий `ParseError` запишет строку и позицию из исключения без текста ответа. Отдельный тест доказал, что плохой XML МК не мешает подготовить реплику для исправного источника. [Лента МК](https://www.mk.ru/rss/index.xml) · [Последний рабочий JSON](https://github.com/AfterDark1000/iipike-site/blob/bb994c68fe122694c4c84e76c5da55d49b1cc880/commenting/queue.json)

Изолированный прогон фактического сборщика в 18:33:56 прочитал все шесть действующих RSS-лент со статусом `ok` и записал обновлённый JSON локально. Gemini был отключён в этом прогоне. Сохранено 34 готовых реплики из входного файла, из них три подходили под браузерное окно в 24 часа. Chromium сначала получил настоящий старый JSON из GitHub и показал предупреждение. В изолированной проверке этого же интерфейса ответ заменён на файл из прогона сборщика. На следующем автоматическом чтении по таймеру браузер показал новое время и снял оба предупреждения без нажатия «Обновить». [Тест ветки в GitHub Actions](https://github.com/AfterDark1000/iipike-site/actions/runs/44534867445)

Ветка `main` и рабочая очередь остались без изменений. В запуске чернового PR прошли тесты, задание записи очереди пропущено. Для отдельного восстановления после утверждения достаточно перенести изменения сборщика и workflow в основную ветку и выполнить один ручной `workflow_dispatch` на `main`. Проверка на рабочем источнике тогда состоит из двух независимых наблюдений: новый успешный `update-queue` и более свежий `updated_at` в сыром JSON. [Черновой PR #216](https://github.com/AfterDark1000/iipike-site/pull/216)
