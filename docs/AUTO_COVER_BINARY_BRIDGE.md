# ХПИИ — проверенная передача WebP из автономной задачи в GitHub

**Этот документ устраняет техническую границу:** генератор ChatGPT Images и Python видят локальный файл изображения, а GitHub-коннектор принимает JSON/текстовые аргументы, не системный путь `/mnt/data/*.webp`. Простая фраза «загрузи бинарный файл» не превращает путь в байты.

**Мы уже доказали способ на кроссовке r3-v2:** настоящий WebP 232262 байта был передан как Base64 в `mcp__GitHub__create_blob({encoding:"base64"})`, получил Git blob SHA `c02889e80647bddb6a4bccfb6c553a68182cd105`, вошёл в Git tree/commit и был проверен повторным чтением. Для каждой новой обложки это надо повторить с её **собственными** байтами. Нельзя повторно использовать этот SHA и этот рисунок для другой статьи.

## Обязательный маршрут: успешно повторён 26.11.2026

Проверен также **в обычном чате ChatGPT**, без Work и без FLUX: изображение Minecraft подготовлено в WebP 1600×900, 166208 байт; его 221612 символов Base64 были переданы через временный текстовый файл ChatGPT Library в `mcp__GitHub__create_blob(encoding:"base64")`. GitHub вернул ровно ожидаемый Git blob SHA `33d1659eb6c25eaddf0ca714e55f447d05b30cc0`. Через `create_tree`, `create_commit`, `update_ref(expected_sha,force:false)` в `editorial-intake` сохранены **оба** новых файла `legendu-minecraft-otpravili-sorevnovatsya-s-ii-ag-4026a4cf1fa73bf7-r2-v1.webp` и одноимённый JSON. Коммит `7450a065ad305f483dc653172d7a1835e09ebc4b`; повторно проверены SHA обоих файлов, статус `ready_for_cover_review`, точный SHA текста и решения. Этот SHA и эти байты — **только свидетельство**, никогда не использовать их для других сюжетов.

**Передача является обязательной частью одной работы художника, а не необязательной попыткой.** После успешной генерации нельзя штатно остановиться на PNG, WebP, резерве, манифесте, blob без коммита или описании препятствия. Если инструменты доступны, пройти все этапы до проверки двух файлов. Не говорить «GitHub не принимает бинарные файлы» — для него используется Base64 Git blob.

Проверенный способ преодолеть раздельные среды Python/Files/GitHub:
1. Получить **фактический путь** изображения ChatGPT Images, проверить пиксели, превратить в 16:9 WebP 1600×900 (до 800000 байт). Вычислить Git blob SHA локально: SHA-1 от `b"blob "+str(len(data)).encode()+b"\\0"+data`. Записать `*.webp.b64` — Base64 *только этого файла*; заранее проверить длину и ожидаемый SHA.
2. Если нет прямого способа передать локальный файл GitHub-инструменту, загрузить **временный текстовый** `*.webp.b64` с помощью `files__manage_library({operations:[{operation:"upload",container_path:"<реальный путь>",destination_path:"/<уникальное имя>.webp.b64"}]})`. Взять из ответа реальный `file_id`, а не придумывать идентификатор. Через `files__read` (режим `full`, `include_images:false`, диапазоны до последней строки) собрать содержимое **не печатая Base64**. Убедиться, что `has_more===false`, число строк и символов совпадает с манифестом. Внутри **того же** `functions.exec` соединить строки, удалить только пробельные символы `s.replace(/\\s/g,"")`, проверить `/^[A-Za-z0-9+/]*={0,2}$/`, вызвать `tools.mcp__GitHub__create_blob({repository_full_name:"AfterDark1000/iipike-site",content:s,encoding:"base64"})` и сравнить `result.sha` с заранее рассчитанным SHA. Нельзя отправлять путь, заголовок, ссылку, фрагмент или демонстрационный Base64 вместо реальных байтов.
3. Получить свежие HEAD и SHA его базового дерева Git, сверить актуальную ревизию, исходный draft SHA, text decision SHA (или null), существующий **резерв** и отсутствие целевых WebP, JSON, cover decision/handoff. Пара `create_tree(base_tree_sha, tree_elements:[{path:".../<stem>.webp",mode:"100644",type:"blob",sha:<проверенный SHA>},{path:".../<stem>.json",mode:"100644",type:"blob",content:<полный JSON>}])` → `create_commit(parent_sha:HEAD,tree_sha:...)` → `update_ref(expected_sha:HEAD,force:false)`. JSON должен иметь статус `ready_for_cover_review` и фактические поля `image_blob_sha`, `source_draft_blob_sha`, `source_decision_blob_sha`, размеры, технику, заголовок, время.
4. **Вызовы GitHub разделять по шагам при внутренней ошибке GraphQL/тайм-ауте**; разрыв между `create_tree`, `create_commit`, `update_ref` не означает невозможности передачи. Перед повтором проверить фактический HEAD и наличие целевых файлов; при гонке пересоздать дерево и коммит от свежего HEAD, никогда не форсировать, не затирать уже созданного кандидата. Объект blob хранится отдельно от ветки и не требует загрузки тех же байтов повторно.
5. После успешного update_ref перечитать HEAD, дерево и JSON кандидата. Сверить SHA WebP с созданным blob, размер, существование JSON, сохранённые source SHA и статус. Для подписи RIFF/WEBP и размеров использовать локальный WebP; если доступен реальный бинарный fetch/валидатор — проверить и им. Не утверждать, что валидатор запускался, если не запускался. Удалить временный Base64 из Library **только после** подтверждения коммита. Сообщать о сохранении только после этой проверки.

**При неисправности отдельного этапа** сообщить точный шаг и ошибку; если картинка создана — показать её в чате и предложить ручную загрузку через `/admin/auto-editor/`. Не создавать ложный JSON, не рисовать второй раз по зарезервированному stem. Для повторной передачи уже созданного рисунка в другом проходе требуется реально доступный исходный файл, совпадение сюжета и актуальной ревизии, без новой генерации и без переноса старого утверждения.

## 1. Проверить исходник и сделать переносимый payload

**Не рисовать заново**, если в текущем запуске уже есть доступ к созданному изображению. Использовать его действительный файл/asset. Файл может называться PNG, JPEG или WebP; требуемая форма вывода — 16:9 WebP, фактический размер не более 800000 байт.

При наличии исполнения Python:

```bash
python3 -m pip install pillow
python3 scripts/prepare_auto_cover_transfer.py \
  --source /mnt/data/<ACTUAL_IMAGE_FILE>.png \
  --out-dir /mnt/data/hpii-cover-transfer \
  --stem <EXACT_ARTICLE_ID>-r<EXACT_TEXT_REVISION>-v<EXACT_COVER_VERSION>
```

`<ACTUAL_IMAGE_FILE>` — **реальный**, проверенный путь из результата генерации, не выдуманный пример. Скрипт сохраняет:
- `<stem>.webp` — реальные пиксели, проверенные Pillow, 1600×900;
- `<stem>.webp.b64` — **ASCII Base64 содержимого** WebP с переносами каждые 512 символов; это транспортный текст, не файл публикации;
- `<stem>.transfer.json` — `git_blob_sha`, `sha256`, `image_bytes`, `base64_chars`, `base64_line_count` и размеры.

Все три файла локальные; это **ещё не сохранённая обложка в GitHub**. Не подменять реальный результат генерации изображением другого сюжета.

## 2. Передать Base64 в GitHub-коннектор

**Самый короткий вариант:** если доступная связка инструментов может прочитать ASCII-файл и передать его содержимое как строку в Github API, передать непрерывный Base64 без пробелов и переносов:

```js
const result = await tools.mcp__GitHub__create_blob({
  repository_full_name: "AfterDark1000/iipike-site",
  content: base64OfActualWebP,
  encoding: "base64"
});
if (result.result.sha !== manifest.git_blob_sha) throw Error("Binary SHA mismatch");
```

Важно: `base64OfActualWebP` **не может быть путём** и **не может быть иллюстративной строкой**. Это все символы реально подготовленного файла `.webp.b64` без пробельных символов. Пользователь не должен вставлять в чат гигантский Base64.

**Проверенный мост, когда Python и GitHub используют разные среды:** временно экспортировать именно текстовый `.webp.b64` в Files Library при наличии `files__manage_library`; получить точный `file_id` через `files__list`; считать текст `files__read({read:[{ref_id:"<ACTUAL_FILE_ID>",mode:"full",start_line:1,max_lines:100}]})` и следующие диапазоны до `base64_line_count`. В `functions.exec` можно объединить все `result.content`-строки через `join("")`, удалить только `\\s`, проверить символы `/^[A-Za-z0-9+/]*={0,2}$/` и `base64_chars`, а затем в **том же исполнении** вызвать `mcp__GitHub__create_blob`. **Не выводить Base64 пользователю, в логи или Markdown.** Временный файл Library удалить после успешной проверки сохранения в GitHub. Если эти инструменты недоступны — честно зафиксировать невозможность; не говорить «канал GitHub не может» до проверки поддержки `create_blob`.

При ошибке `create_blob`, несовпадении ожидаемого blob SHA, неполном чтении какого-либо диапазона или непроверенном содержимом — **остановиться**, ничего не коммитить, ничего не утверждать.

## 3. Атомарная запись только кандидата в `editorial-intake`

**Актуальный параллельный режим (24.11.2026, решение главреда).** Художник работает независимо от утверждения текста. Выбирать актуальный полноценный `ready_for_review` автодрафт, если по этой ревизии решения нет или есть точное `approve_text`. Не брать отклонённую, возвращённую на доработку, заблокированную или уже переданную ревизию. Сначала замечания к обложкам, затем очередь свободных готовых текстов по `pool_sequence`. Кандидат строго привязан к `article_id`, ревизии, `updated_at` и SHA исходного автодрафта. В существующей схеме v1 поле `source_decision_blob_sha` равно точному SHA действующего approve_text, если он существует на момент регистрации; если решения нет — явно `null`. Никогда не выдумывать SHA. При одобрении обложки до текста `source_text_decision_blob_sha` в человеческом решении может быть `null`; два настоящих утверждения для одной актуальной ревизии всё равно обязательны для handoff. Смена текста аннулирует пригодность старой обложки для текущей ревизии: художник сравнивает сюжет, бриф и изображение, при соответствии может повторно использовать проверенные реальные байты старого WebP как новый кандидат rN-v1 с новыми метаданными, не перенося старое одобрение. Если смысл изменился — новое изображение. Не перерисовывать автоматически и не перепривязывать молча. Сверять SHA и отсутствие запрещающего решения до и после сохранения. Пять кандидатов/генераций в 24 часа, максимум один кандидат за проход; считать все записи и уже сделанные попытки консервативно. Эти правила выбора имеют приоритет над историческим требованием approve_text до начала рисунка в плагинном зеркале. Художественный стандарт, бинарный мост, запрет утверждения и публикации не меняются.

До коммита перечитать ветку `editorial-intake`:
1. Актуальный готовый черновик `editorial_inbox/auto_drafts/<article_id>.json` и наличие/отсутствие решения `auto_decisions/<article_id>-r<revision>.json`; проверить точный SHA текста, ревизию, дату. При отсутствии решения `source_decision_blob_sha=null`, при наличии только совпадающий `approve_text`.
2. Нет существующих файлов для **точной** `vN`, нет решения/передачи, запрещающих новую версию. Для v2+ имеется соответствующее `revise_cover` предыдущей версии.
3. Получить текущий HEAD ветки `editorial-intake` и SHA базового дерева HEAD через GitHub API. `create_tree` с **двумя** путями: `editorial_inbox/auto_covers/<stem>.webp` с полученным `blob.sha` и `editorial_inbox/auto_covers/<stem>.json` с метаданными (`ready_for_cover_review`, `image_blob_sha`, `source_draft_blob_sha`, `source_decision_blob_sha`, `width`, `height`, `headline`, `concept`, `artist_notes`, `created_at`).
4. `create_commit(tree_sha, parent_sha=oldHead)`, затем `update_ref(branch_name:"editorial-intake",sha:newCommit,expected_sha:oldHead)`. Не использовать `force` и не перезаписывать ничего при гонке.
5. **Повторно прочитать** `.webp` и `.json` из ветки: сверить реальный Git blob SHA, размер, WebP-сигнатуру и решение. Штатный валидатор: `scripts/check_auto_cover_pilot.py`.

Только **после** подтверждённого `update_ref` и повторного чтения можно писать: «Кандидат сохранён, ждёт решения главреда в админке». Никогда не выставлять самостоятельно `approve_cover`, не писать в `editorial_inbox/covers/` или `stories/` и не запускать публикацию.

## 4. Если бинарный мост недоступен в автономной задаче

Это отдельный честный исход: **генерация работает, сохранение в GitHub заблокировано**. Не тратить каждый следующий почасовой запуск на повторную генерацию одного и того же сюжета без нового пути передачи. Не создавать пустой WebP, текстовый Base64 под расширением .webp или JSON `ready_for_cover_review`.

Для текущей работы есть **безопасный ручной запасной путь без FLUX**: главред скачивает именно изображение, созданное художником в чате его задачи; в `https://iipike.ru/admin/auto-editor/` выбирает утверждённую статью → «Загрузить обложку v1» → свой PNG/WebP. Существующий защищённый Cloudflare Worker конвертирует/принимает реальные байты и сохраняет кандидат; затем главред отдельно утверждает **обложку**. Ручная загрузка не доказывает полной автономности и не должна выдаваться за её достижение.

**Нельзя выдавать старые обложки про 72 яйца из YouTube Shorts или другого выпуска за новый рисунок автономного художника.** У них иной сюжет, композиция или формат.

## 5. Контроль против повторов

Проверка отсутствия кандидата до генерации обязательна. Если исходник создан в прошлом запуске, но не сохранён, из нового запуска он может быть недоступен; **не предполагать**, что его байты автоматически доступны другим чатам/задачам. При недоступности — зафиксировать причину и предложить ручную загрузку, а не рисовать по кругу без изменения возможностей.
