# Очередь комментариев ХПИИ

Экран: https://iipike.ru/admin/commenting/ (ссылка «Комментинг» в текущей админке).

Первая версия читает RSS iXBT, 3DNews, Overclockers и МК, отбирает заголовки по
тематике ИИ за последние 48 часов, читает полную статью на сайте издания и готовит
одну самостоятельную реплику. Конфигурация: `data/commenting_sources.json`.
Адреса каналов взяты из ссылок самих изданий; `channel_reference` хранит источник.

## Фактическая граница первой версии

**Сбор именно публикаций Дзена пока не реализован.** Облачный браузер при проверке
перешёл к входу VK, доступ к которому заблокирован политикой браузера. Сборщик
не обходит это ограничение, не читает Дзен через сторонние прокси, не входит в
аккаунты и не получает куки. Он запрашивает только разрешённые сайты изданий.

Публикация в RSS издания не подтверждает публикацию или возможность комментирования
в его канале Дзена. Поэтому все три даты/состояния различаются:

- `published_at`: дата публикации на сайте из RSS, с известным часовым поясом;
- `first_seen_at`: первое обнаружение сборщиком;
- `dzen_url`: только явное зеркало этой статьи из `NewsArticle.sameAs` либо
  `<link rel="alternate">`; обычная ссылка в навигации зеркалом не считается.

При отсутствии прямой ссылки экран показывает «Прямой ссылки в Дзен нет» и кнопку
**«Найти в Дзене»**, а не выдуманный адрес публикации. Найденную вручную ссылку
можно сохранить в карточке. По умолчанию комментарий основан на оригинале издания;
версия в Дзене могла отличаться. Доступность комментариев и статистика аудитории
не проверены; просмотры/число комментариев остаются `null`.

Это рабочий сбор изданий и очередь черновиков, но ещё не полностью автоматический
сценарий «обнаружить новую статью именно в Дзене и открыть её в один клик».

## Обновление и хранение

Workflow `commenting-queue.yml` запускается в :07 и :37 каждого часа (UTC),
допускает ручной запуск и стартует после изменения сборщика в main. GitHub может
задерживать cron. Кнопка «Обновить» перечитывает последний результат, не запускает
модель и не вызывает публикацию.

Для генерации используется существующий `GEMINI_API_KEY` и тот же
`gemini-3.5-flash-lite`, что в редакционном пилоте. Ключ не попадает в браузер.
Один запрос на запуск, максимум три статьи и 24 попытки за местный день
Asia/Yekaterinburg. Ошибки учитываются в лимите, повтор для одной статьи возможен
через шесть часов, не более двух попыток. Платного запасного провайдера нет;
тарификацию существующего ключа этот код не меняет и не определяет.

Данные пишутся только в **ветку `commenting-data`**, файл `commenting/queue.json`.
Основная ветка, статьи, editorial-intake и очереди соцсетей сборщиком не меняются.
Сохраняются метаданные, короткий комментарий и причина отбора, без полного текста
чужой статьи. Старые записи хранятся семь дней, до 300 карточек. Рабочий список
показывает только свежие; старые ручные отметки учитываются отдельно.

Страница публичная по прямой ссылке и помечена noindex. Отметки «Разместил» и
«Пропустить», правки и вручную добавленные ссылки — только в localStorage текущего
браузера. Экспорт/импорт сохраняет их между браузерами вручную. Копирование не
означает публикацию; автоматической отправки комментариев нет.

## Диагностика

Сбой одной ленты не мешает другим. Вместо нуля показывается ошибка, а последняя
успешная проверка сохраняется. Ошибки чтения статьи и генерации не превращаются
в готовый комментарий. Очередь старше двух часов помечается как устаревшая.
На сбое загрузки интерфейс сохраняет уже загруженные данные с предупреждением.

Проверка сборщика без модели:

```sh
python3 scripts/commenting_queue.py --no-model --output /tmp/commenting-probe.json
python3 -m unittest discover -s tests -p 'test_commenting_queue.py' -v
node --test tests/commenting.test.cjs
```

Первый реальный результат генерации надо проверить после запуска workflow:
открыть `commenting-data/commenting/queue.json`, проверить `sources`, `generator`
и наличие `draft_ready`. Зелёный workflow означает сохранение диагностики, а не
гарантию готовых комментариев или получения подписчиков.
