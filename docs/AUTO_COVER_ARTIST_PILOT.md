# ХПИИ — автономный художник: пилот создания и сохранения обложек

Статус: первоначальный ручной пилот Carbon выполнен. **Теперь повторяемый художник действует отдельно** по `scripts/auto_cover_worker.py` и `.github/workflows/hpii-auto-cover-worker.yml` для любого нового утверждённого текста. Источник истины — `AfterDark1000/iipike-site`, ветка `editorial-intake`. **Никогда не публиковать статьи.**

## Вход

1. Читать все `editorial_inbox/auto_drafts/*.json` и решения `editorial_inbox/auto_decisions/<article_id>-r<revision>.json`.
2. Брать только последнюю неизменённую ревизию, где `decision.action="approve_text"`, `decision.status="text_approved_cover_pending"`, `decision.draft_blob_sha` совпадает с текущим SHA черновика и совпадают `article_id`, `revision` и `updated_at`.
3. До генерации проверить, что для этой ревизии уже нет готового кандидата в `editorial_inbox/auto_covers/`. При наличии такого кандидата не создавать дубль и не заявлять, что работа сделана заново. Изменения текста после утверждения блокируют генерацию до нового решения.
4. Для **исторического ручного** пилота первой была Carbon r4. Новый автоматический исполнитель ищет следующую неизменённую ревизию с явным `approve_text` и без `v1`-кандидата; первый следующий кандидат — одобренная версия статьи про кроссовок (r3). Никаких списков жёстко прописанных ID и самостоятельного одобрения текста.

## Художественное задание

Прочитать весь `content.article_markdown`, `content.title`, `cover_brief`, первоисточники. Выполнить художественную, авторскую горизонтальную обложку 16:9 на русском языке; заголовок короткий, грамотно набранный, крупный и читаемый. Сверять факты с текстом, не вводить в заблуждение относительно цены, доступа и статуса preview. Выбрать самостоятельную визуальную метафору; художественные направления чередовать **по смыслу**, а не механически. Если предыдущие обложки доступны для визуального просмотра, сравнить с несколькими последними; если доступны только имена файлов — честно так и сказать.

Не делать по умолчанию роботов, цифровые головы, голографические мозги, неоновые серверные, потоки кода, экраны с карточками, корпоративную бело-синюю графику, однотипные красно-чёрные плакаты. Проверить достоверность, читаемость и композицию 16:9. Если генератор не дал подходящее изображение, не считать материал готовым.

## Проверка сохранения РЕАЛЬНЫХ байтов

Важнейшая часть пилота — доказать, что исполнитель может прочитать **реальные байты** созданного изображения и передать их в GitHub, не путая URL/описание и сам файл.

- Исходный файл на первом пилоте: **WebP**, размеры 16:9, реальные пиксели. Исходный PNG/JPEG сначала преобразовать в WebP качеством около 84 (при необходимости 76–84), желательно 1600×900 и до 400 КБ. Исходный PNG/JPEG в GitHub не загружать. Сохранить отдельно в `editorial_inbox/auto_covers/<article_id>-r<revision>-v1.webp` на `editorial-intake`. При необходимости использовать преобразование/кадрирование до 16:9. Ни в коем случае не сохранять JSON, Markdown, data URL или placeholder под расширением .webp.
- Разрешённое средство GitHub, если есть доступ к байтам: `create_blob(content=<base64 реальных байтов>, encoding="base64")` → `create_tree` с базовым SHA дерева ветки → `create_commit` → `update_ref` с ожидаемым текущим SHA. Альтернатива — доступный инструмент, который действительно загружает бинарные байты и подтверждает их в GitHub. Установка blob сама по себе **ещё не означает**, что он включён в ветку.
- После commit **повторно прочитать** этот файл из GitHub или проверить его тип и реальную сигнатуру WebP с размером 16:9. Если какой-то шаг невозможен, честно сообщить «изображение создано, но не сохранено», не создавать метаданные `ready_for_cover_review` и не считать этап завершённым.
- Лишь после доказанного сохранения WebP добавить боковой файл `editorial_inbox/auto_covers/<article_id>-r<revision>-v1.json` с полями:
  `schema_version=1`, `article_id`, `text_revision`, `text_updated_at`, `source_draft_blob_sha`, `source_decision_blob_sha`, `status="ready_for_cover_review"`, `image_path`, `image_blob_sha`, `width`, `height`, `concept`, `headline`, `artist_notes`, `created_at`.
- Если не удалось установить ширину/высоту и подтвердить WebP по реальному изображению, не создавать статус готовности. Не писать в боевой `editorial_inbox/covers/` ни при каких обстоятельствах.

## Дальнейшие действия

После настоящего сохранения нужна отдельная безопасная кнопка главреда «Утвердить обложку» или «Переделать» и контроль версий изображения. Пока кнопка не введена, обложка — только кандидат. **Одобрение текста + кандидат обложки никогда не означают разрешения выпускать сайт.**

Честно отмечать инструментальные ограничения. Не дублировать изображение и уведомление на следующем проходе. При отсутствии работы проход заканчивать без сообщения.

## Решение человека по обложке

Результат сохраняется **только** через авторизованный `POST /api/cover-review` Worker после явного нажатия главреда в `/admin/auto-editor/`. Кнопки доступны после загрузки и проверки изображения в браузере.

Файл решения `editorial_inbox/auto_cover_decisions/<article_id>-r<text_revision>-v1.json` в `editorial-intake`. Два действия: `approve_cover` → `cover_approved_handoff_pending`, `revise_cover` → `cover_revision_requested` (обязательное замечание). Утверждается одна неизменённая версия: Writer повторно сверяет SHA текущего WebP, метаданные, одобренный текст и его ревизию; повторное решение не перезаписывается. Новый вариант после `revise_cover` потребует отдельно согласованного version=2 — текущая пилотная кнопка сама его не создаёт.

**Ни один вариант решения по обложке не публикует статью и не кладёт файлы в боевую очередь или `editorial_inbox/covers/`.** Вызов только фиксирует решение главреда. Следующий этап — независимая подготовка полного редакционного комплекта и отдельная контрольная проверка.

## Новый повторяемый исполнитель (18 ноября 2026)
- Автономный художник запускается в отдельном GitHub Actions `hpii-auto-cover-worker.yml`: при изменении собственного кода, вручную через Actions или 5 раз в день по UTC. Это **не новая задача ChatGPT**. Один проход — максимум одна обложка; без утверждённых текстов не делает внешних запросов.
- Используется **только** существующая интеграция Cloudflare Workers AI `@cf/black-forest-labs/flux-2-klein-4b` с секретами `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`, без платной альтернативы и без повторов при 429. Если интеграция недоступна, задача не выдаёт фиктивную обложку и фиксирует ошибку в GitHub Actions. Вычисление концепции и композиции ведётся по `cover_brief`, фактам, заголовку и семейству художественных приёмов; кириллический заголовок накладывается Pillow, а не доверяется генератору.
- Скрипт предварительно сверяет Git blob SHA черновика и решения, редакционное `approve_text`, отсутствие готовой обложки, сохранённого решения и хэнд-оффа. Создаёт реальный WebP 1600×900 и JSON `ready_for_cover_review` **только** в `editorial_inbox/auto_covers/` ветки `editorial-intake`, проверяет файлы независимым валидатором, коммитит только два разрешённых пути.
- Через `/admin/auto-editor/` главред по-прежнему утверждает или отклоняет **точную версию v1**. Статус `revise_cover` пока **не генерирует v2**: до расширения админки и защищённого Worker повторный вариант не следует публиковать как якобы готовый. Это отдельный следующий этап.
- Автоматизация не переносит статью в `editorial_inbox/stories/`, не пишет `news.json`, не запускает Дзен и соцсети, не помечает `cover_approved` за человека. Это делает уже существующий подтверждающий путь после решения главреда.
- Offline тесты: `python3 -m unittest discover -s tests -p test_auto_cover_worker.py -v`. Пилот смотрим в GitHub Actions и через админку, а не по одному только статусу run.

## Известное ограничение первого автоматического прогона
При первом успешном выпуске кандидата r3 про кроссовок, технический WebP был корректен, но FLUX нарисовал псевдотекст на самой сцене. Такой кандидат **не должен утверждаться без визуального просмотра главредом**. Исправлен арт-промпт для *будущих* изображений: факт и предметная сцена вместо слов «плакат», «надпись» и предоставления генератору текста заголовка. Версия уже созданной картинки не перезаписывается задним числом. Полноценный цикл `revise_cover → v2` остаётся отдельной задачей с обновлением версии в админке и проверок Worker.
