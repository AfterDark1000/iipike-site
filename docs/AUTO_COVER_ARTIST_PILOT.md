# ХПИИ — автономные обложки: восстановление правильного исполнителя

**Актуальный параллельный режим (24.11.2026, решение главреда).** Художник работает независимо от утверждения текста. Выбирать актуальный полноценный `ready_for_review` автодрафт, если по этой ревизии решения нет или есть точное `approve_text`. Не брать отклонённую, возвращённую на доработку, заблокированную или уже переданную ревизию. Сначала замечания к обложкам, затем очередь свободных готовых текстов по `pool_sequence`. Кандидат строго привязан к `article_id`, ревизии, `updated_at` и SHA исходного автодрафта. В существующей схеме v1 поле `source_decision_blob_sha` равно точному SHA действующего approve_text, если он существует на момент регистрации; если решения нет — явно `null`. Никогда не выдумывать SHA. При одобрении обложки до текста `source_text_decision_blob_sha` в человеческом решении может быть `null`; два настоящих утверждения для одной актуальной ревизии всё равно обязательны для handoff. Смена текста аннулирует пригодность старой обложки для текущей ревизии: художник сравнивает сюжет, бриф и изображение, при соответствии может повторно использовать проверенные реальные байты старого WebP как новый кандидат rN-v1 с новыми метаданными, не перенося старое одобрение. Если смысл изменился — новое изображение. Не перерисовывать автоматически и не перепривязывать молча. Сверять SHA и отсутствие запрещающего решения до и после сохранения. Пять кандидатов/генераций в 24 часа, максимум один кандидат за проход; считать все записи и уже сделанные попытки консервативно. Эти правила выбора имеют приоритет над историческим требованием approve_text до начала рисунка в плагинном зеркале. Художественный стандарт, бинарный мост, запрет утверждения и публикации не меняются.

**Актуальное решение (18 ноября 2026):** обычный художник — чат ChatGPT с подключённым плагином `ХПИИ — Художник`; автономная задача может работать без доступа к плагину, поэтому **полные художественные инструкции из версии 1.5.2 перенесены дословно** в [docs/artist_plugin/README.md](artist_plugin/README.md). Запуск задачи должен начинаться с [docs/ARTIST_AUTONOMOUS_AGENT.md](ARTIST_AUTONOMOUS_AGENT.md). Перенос инструкций сам по себе **не выбирает Sol 6.2**, не подтверждает доступ к ChatGPT Images и не включает задачу. Не заменять её FLUX.

Случайно введённый `hpii-auto-cover-worker.yml` вместе с `scripts/auto_cover_worker.py` удалён. Он неверно использовал Cloudflare FLUX, предназначенный только для отдельной экспериментальной ветки с Gemini. Некачественный кандидат для статьи про кроссовок (r3 v1) удалён из `editorial-intake`, **текст `r3` остаётся утверждённым**. Ни один художественный плагин не вызывается автоматически простой записью GitHub: между очередью и ChatGPT-художником требуется честный механизм запуска.

**Правильная схема передачи и команды существующему художнику:** [AUTO_ARTIST_HANDOFF.md](AUTO_ARTIST_HANDOFF.md). В ней сохранены раздельные одобрения текста и изображения, отдельное хранилище `auto_covers`, без прямой публикации и без создания копии художественного стандарта.

# ХПИИ — автономный художник: пилот создания и сохранения обложек

Статус: эксперимент. Источник истины — `AfterDark1000/iipike-site`, ветка `editorial-intake`. **Никогда не публиковать статьи.**

## Вход

1. Читать все `editorial_inbox/auto_drafts/*.json` и решения `editorial_inbox/auto_decisions/<article_id>-r<revision>.json`.
2. Брать последнюю готовую неизменённую ревизию `ready_for_review`, с отсутствующим решением или точным `approve_text` (совпадающие `article_id`, `revision`, `updated_at`, SHA).
3. До генерации проверить, что для этой ревизии уже нет готового кандидата в `editorial_inbox/auto_covers/`. При наличии такого кандидата не создавать дубль и не заявлять, что работа сделана заново. Изменения текста требуют кандидата для новой актуальной ревизии, с проверкой пригодности старой обложки; утверждение текста не требуется.
4. Исторический первый пилот — Carbon r4; настоящее задание выбирается по свежим готовым черновикам и возвратам из editorial-intake, без фиксированного ID. Актуальный контракт — docs/ARTIST_AUTONOMOUS_AGENT.md. Обложку v2 про кроссовок не повторять, пока главред не вынес решение.

## Художественное задание

Прочитать весь `content.article_markdown`, `content.title`, `cover_brief`, первоисточники. Выполнить художественную, авторскую горизонтальную обложку 16:9 на русском языке; заголовок короткий, грамотно набранный, крупный и читаемый. Сверять факты с текстом, не вводить в заблуждение относительно цены, доступа и статуса preview. Выбрать самостоятельную визуальную метафору; художественные направления чередовать **по смыслу**, а не механически. Если предыдущие обложки доступны для визуального просмотра, сравнить с несколькими последними; если доступны только имена файлов — честно так и сказать.

Не делать по умолчанию роботов, цифровые головы, голографические мозги, неоновые серверные, потоки кода, экраны с карточками, корпоративную бело-синюю графику, однотипные красно-чёрные плакаты. Проверить достоверность, читаемость и композицию 16:9. Если генератор не дал подходящее изображение, не считать материал готовым.

## Проверка сохранения РЕАЛЬНЫХ байтов

Важнейшая часть пилота — доказать, что исполнитель может прочитать **реальные байты** созданного изображения и передать их в GitHub, не путая URL/описание и сам файл.

- Исходный файл на первом пилоте: **WebP**, размеры 16:9, реальные пиксели. Исходный PNG/JPEG сначала преобразовать в WebP качеством около 84 (при необходимости 76–84), желательно 1600×900 и до 400 КБ. Исходный PNG/JPEG в GitHub не загружать. Сохранить отдельно в `editorial_inbox/auto_covers/<article_id>-r<revision>-v1.webp` на `editorial-intake`. При необходимости использовать преобразование/кадрирование до 16:9. Ни в коем случае не сохранять JSON, Markdown, data URL или placeholder под расширением .webp.
- Разрешённое средство GitHub, если есть доступ к байтам: `create_blob(content=<base64 реальных байтов>, encoding="base64")` → `create_tree` с базовым SHA дерева ветки → `create_commit` → `update_ref` с ожидаемым текущим SHA. Альтернатива — доступный инструмент, который действительно загружает бинарные байты и подтверждает их в GitHub. Установка blob сама по себе **ещё не означает**, что он включён в ветку.
- После commit **повторно прочитать** этот файл из GitHub или проверить его тип и реальную сигнатуру WebP с размером 16:9. Если какой-то шаг невозможен, честно сообщить «изображение создано, но не сохранено», не создавать метаданные `ready_for_cover_review` и не считать этап завершённым.
- Лишь после доказанного сохранения WebP добавить боковой файл `editorial_inbox/auto_covers/<article_id>-r<revision>-v1.json` с полями:
  `schema_version=1`, `article_id`, `text_revision`, `text_updated_at`, `source_draft_blob_sha`, `source_decision_blob_sha`, `status="ready_for_cover_review"`, `image_path`, `image_blob_sha`, `width`, `height`, `concept`, `headline`, `artist_notes`, `created_at`.
- Если не удалось установить ширину/высоту и подтвердить WebP по реальному изображению, не создавать статус готовности. Не писать в боевой `editorial_inbox/covers/` ни при каких обстоятельствах.

## Дальнейшие действия

После настоящего сохранения нужна отдельная безопасная кнопка главреда «Утвердить обложку» или «Переделать» и контроль версий изображения. Пока кнопка не введена, обложка — только кандидат. **Одобрение текста + кандидат обложки никогда не означают разрешения выпускать сайт.**

Честно отмечать инструментальные ограничения. Не дублировать изображение и уведомление на следующем проходе. При отсутствии работы проход заканчивать без сообщения.

## Решение человека по обложке

Результат сохраняется **только** через авторизованный `POST /api/cover-review` Worker после явного нажатия главреда в `/admin/auto-editor/`. Кнопки доступны после загрузки и проверки изображения в браузере.

Файл решения `editorial_inbox/auto_cover_decisions/<article_id>-r<text_revision>-v1.json` в `editorial-intake`. Два действия: `approve_cover` → `cover_approved_handoff_pending`, `revise_cover` → `cover_revision_requested` (обязательное замечание). Утверждается одна неизменённая версия: Writer повторно сверяет SHA текущего WebP, метаданные, актуальный текст и его ревизию, отсутствие отклоняющего решения; повторное решение не перезаписывается. Новый вариант после `revise_cover` потребует отдельно согласованного version=2 — текущая пилотная кнопка сама его не создаёт.

**Ни один вариант решения по обложке не публикует статью и не кладёт файлы в боевую очередь или `editorial_inbox/covers/`.** Вызов только фиксирует решение главреда. Следующий этап — независимая подготовка полного редакционного комплекта и отдельная контрольная проверка.

## Возврат на переделку: v2–v5 (18 ноября 2026)

- `POST /api/cover-review` записывает `action=revise_cover`, `status=cover_revision_requested` и дословное `note` главреда в `editorial_inbox/auto_cover_decisions/<article_id>-r<revision>-vN.json`. **Это ещё не запускает ChatGPT-плагин художника**.
- Действующий `ХПИИ — Художник` (плагин `hpii-artist`) по команде прочитывает текущую версию решения и замечания, делает новый **самостоятельный художественный вариант**, сохраняет `auto_covers/<article_id>-r<revision>-v(N+1).webp` и такой же `.json`. Ветка `editorial-intake`, исходный текст не меняется, старая версия не перезаписывается.
- Актуальная админка теперь ищет `v1 → ... → v5`, показывает **последний кандидат**, а при `cover_revision_requested` выводит комментарии и ожидаемую следующую версию. Появившуюся новую версию главред утверждает или вновь отклоняет отдельно. При отсутствии следующей версии защищённая форма позволяет загрузить готовый PNG/WebP прямо в очередной номер версии.
- Worker `admin-auth-worker/src/index.mjs` требует для `v2+` существующее **именно отклонённое** решение предыдущей версии, а также неизменность исходного текста и WebP SHA. После утверждения v2 штатный `scripts/auto_editor_handoff.py` уже поддерживает версионный путь.
- **Развёртывание:** PR/коммит GitHub обновляет исходники Worker, но **не развёртывает** его на `hpii-admin-gateway.svuktablet.workers.dev`. До реального redeploy v2-кнопка может возвращать `invalid_cover_review` или `invalid_cover_upload`. Включение новой версии сервера должен подтвердить deploy с проверкой `/api/session` и боевых действий; никакие секреты не пересылать в чат.
- Не путать возврат художественной картинки с новой ревизией **текста**. Для одного утверждённого `text_revision` может существовать до пяти художественных версий; `approved` и публикация никогда не возникают из одного нажатия «Переделать».
