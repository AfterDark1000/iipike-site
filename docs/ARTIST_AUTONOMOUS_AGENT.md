# ХПИИ — автономный художник: диспетчер вместо ручного обхода очереди

**Актуальный режим от 25.11.2026.** Обычный ChatGPT, действующая задача `6afc408992f08191810f60872d211636`. Work не включать. Этот раздел заменяет старый обязательный обход всех каталогов художником, но не художественный стандарт и не проверку публикационных границ.

## Диспетчер (GitHub Actions, без ИИ)

`scripts/auto_artist_dispatch.py` и `.github/workflows/auto-artist-dispatch.yml` раз в час на :45 UTC и после изменений диспетчера читают актуальные локальные Git-файлы, проверяют очередь, возвраты, SHA, ручные решения, опубликованные материалы, лимит 5 за скользящие 24 часа. Параллельный выбор до approve_text допускается только после проверки живого health API. Диспетчер ничего не рисует и не публикует. В ветке editorial-intake он записывает только `editorial_inbox/auto_artist_dispatch/current.json` с одним готовым заданием (либо idle/quota_full), сроком годности, фактическим текстом и брифом, замечанием к предыдущей обложке, кратким журналом недавних концепций и контрольными SHA. Никаких внешних генераторов или новых подписок.

## Один проход художника

1. Прочитать current.json. Если задания нет, срок истёк или quota_full, не рыться в очереди и не рисовать. Использовать только одно указанное задание; не подбирать своё.
2. До генерации создать неизменяемый резерв попытки в job.claim_path. Он не является кандидатом и не утверждает работу. Файл schema_version=1, stem, state="generation_reserved", reserved_at (реальное UTC), ticket_sha, article_id, revision, version, source_draft_blob_sha. Это одна учитываемая попытка, даже если генератор или передача затем не сработают. Запись create-only, не перезаписывать и не удалять автоматически.
3. Для записи резерва одним коротким техническим проходом получить актуальный HEAD через GET /git/ref/heads/editorial-intake, его дерево через GET /git/trees/<HEAD>?recursive=1. Не читать JSON остальных статей. Проверить, что дерево не усечено; SHA current.json точно совпадает с прочитанным; SHA auto_drafts/<id>.json и auto_decisions/<id>-rN.json (null при отсутствии) совпадают с job; SHA поддеревьев auto_covers и auto_artist_dispatch/claims совпадают с guard (null при отсутствии). Нет claim_path, целевого .webp/.json, решения по целевой версии и handoff для актуальной ревизии. При возврате также проверить точный SHA решения, предыдущего JSON и WebP из job.previous. Создать Git tree с одним новым claim_path (mode 100644, type blob, content JSON), commit с родителем проверенного HEAD и update_ref с expected_sha=HEAD, force=false. При гонке перечитать только current.json и тот же контрольный снимок, не рисовать до подтверждения записи. Если запись уже существует — не рисовать повторно. Подтвердить резерв повторным чтением. Указанные в guard SHA — SHA деревьев каталогов, не SHA коммитов.
4. Рисовать через штатный ChatGPT Images строго по актуальному зеркалу художественного стандарта (все семь файлов из раздела ниже). При неизменной версии и если они уже полностью доступны в контексте задачи, повторно их не читать. Использовать текст и бриф из задания. Сравнить с реально доступными обложками; записи recent_artwork помогают не повторять концепции, но не заменяют визуальный просмотр. Короткий русский заголовок, 16:9, разнообразие, достоверность. Один результат за проход. Не использовать FLUX или Gemini. Если исходник от прошлого запуска не удаётся восстановить, не рисовать его снова по умолчанию.
5. По возможности передать реальные байты по AUTO_COVER_BINARY_BRIDGE.md с повторной сверкой ревизии, решения, версии, SHA и атомарной записью только новой пары WebP+JSON. Если в обычной среде передать файл не удаётся, показать реальное изображение в чате, строку «Стиль: …», article_id и rN-vN, точный шаг ошибки. В админке /admin/auto-editor/ владелец может вручную загрузить результат в нужную версию. Сохранённый резерв оставляет эту версию в ожидании загрузки, **не блокируя другие задания**. Никакой фиктивной метаинформации ready_for_cover_review.
6. Никаких approve_cover, approve_text, handoff, stories, публикации или изменений расписания. Не делать повторное изображение после записи резерва. Если генерация не состоялась, честно указать это. Повтор конкретной неудачной попытки допускается только по отдельному решению главреда и учёту квоты; штатный диспетчер никогда не снимает резерв сам.

## Квота и незавершённые попытки

Резерв и сохранённый кандидат с одинаковым stem считаются одним элементом, с более поздним временем для консервативного расчёта. Исторические attempts учитываются отдельно, если попадают в окно. Даже просроченный по квоте резерв не разрешает повторять тот же рисунок автоматически. `data/auto_artist_holds.json` хранит неопределённые незавершённые попытки из прежнего контура (NVIDIA r2-v2); время записи — консервативное резервирование лимита, не доказательство генерации. Ручная загрузка закрывает ожидание; новая ревизия текста имеет новый stem. Не переписывать историю попыток для освобождения квоты. При необходимости повторить именно ту же версию сначала согласовать с главредом и технически оформить отдельный учтённый повтор.

# ХПИИ — Автономный художник: инструкции для существующей задачи

**Актуальный параллельный режим (24.11.2026, решение главреда).** Художник работает независимо от утверждения текста. Выбирать актуальный полноценный `ready_for_review` автодрафт, если по этой ревизии решения нет или есть точное `approve_text`. Не брать отклонённую, возвращённую на доработку, заблокированную или уже переданную ревизию. Сначала замечания к обложкам, затем очередь свободных готовых текстов по `pool_sequence`. Кандидат строго привязан к `article_id`, ревизии, `updated_at` и SHA исходного автодрафта. В существующей схеме v1 поле `source_decision_blob_sha` равно точному SHA действующего approve_text, если он существует на момент регистрации; если решения нет — явно `null`. Никогда не выдумывать SHA. При одобрении обложки до текста `source_text_decision_blob_sha` в человеческом решении может быть `null`; два настоящих утверждения для одной актуальной ревизии всё равно обязательны для handoff. Смена текста аннулирует пригодность старой обложки для текущей ревизии: художник сравнивает сюжет, бриф и изображение, при соответствии может повторно использовать проверенные реальные байты старого WebP как новый кандидат rN-v1 с новыми метаданными, не перенося старое одобрение. Если смысл изменился — новое изображение. Не перерисовывать автоматически и не перепривязывать молча. Сверять SHA и отсутствие запрещающего решения до и после сохранения. Пять кандидатов/генераций в 24 часа, максимум один кандидат за проход; считать все записи и уже сделанные попытки консервативно. Эти правила выбора имеют приоритет над историческим требованием approve_text до начала рисунка в плагинном зеркале. Художественный стандарт, бинарный мост, запрет утверждения и публикации не меняются.

**Исполнитель:** существующая задача ChatGPT «ХПИИ — Автономный художник» (ID `6b006e412d0c819087720c8e244405cd`). Не новый FLUX-генератор, не новый плагин, не новый слот задачи. Расписание/включённость регулируются отдельно и **не изменяются** этим документом.

## Один безопасный проход

1. Прочитать актуальные `editorial_inbox/auto_drafts/*.json`, `auto_decisions/*.json`, `auto_covers/`, `auto_cover_decisions/`, `auto_handoffs/` в ветке `editorial-intake`.
2. **Сначала возвраты с замечаниями:** найти `cover_revision_requested` по версии `vN`, сопоставить файл решения с SHA изображения и метаданных и с неизменённой актуальной готовой ревизией текста. Подготовить исключительно следующую `vN+1` (максимум `v5`) с дословным учётом замечаний. Если таких нет — взять наиболее ранний по pool_sequence свободный готовый текст и подготовить `v1`.
3. Если в следующей версии уже есть кандидат, если текст изменился, если есть handoff либо не совпадают исходные SHA — **не генерировать дубль**, не перезаписывать файлы и не менять текст.
4. Полноценно подготовить художественную концепцию **по зеркалу стандарта**, не просто по одному `cover_brief`. Результат — авторская 16:9-обложка, короткий корректный русский заголовок, проверка смысла и антиповторов. Никаких FLUX, экспериментального Gemini-контурa или замены изображения шаблонной цветной типографикой.
5. Важно: задача может не иметь выбранной в ручном Work-чате модели Sol 6.2. **Не утверждать, что работала на Sol 6.2, если это не подтверждено текущей средой.** GitHub-инструкция не способна переключить модель выполнения. Использовать только реально доступный штатный генератор ChatGPT Images; при его отсутствии — безопасно остановиться с понятной причиной.
6. **Обязательно выполнить [технический маршрут бинарной передачи](AUTO_COVER_BINARY_BRIDGE.md), а не останавливаться на словах «GitHub не принимает локальный файл».** Проверенный способ: реальный WebP → ASCII Base64 → `mcp__GitHub__create_blob` с `encoding="base64"` → проверка Git blob SHA → атомарный `create_tree`/`create_commit`/`update_ref` → повторное чтение. Для получения Base64 из отдельной среды доступен `scripts/prepare_auto_cover_transfer.py` и временный текстовый экспорт через Files. Только после получения и проверки фактических байтов сохранить новую версию `editorial_inbox/auto_covers/<id>-r<text_revision>-v<version>.webp` и одноимённую `.json` в `editorial-intake`, сверив SHA черновика, действующего решения (если есть) и файла до и после записи. **Если нет доступа к исходному изображению или Files-транспорту, честно остановиться и предложить ручную загрузку в админке.** Не подменять невозможную передачу бинарного файла ссылкой на изображение в чате.
7. Кандидат ждёт отдельного решения владельца в `/admin/auto-editor/`; автономная задача **не ставит approve_cover**, не формирует `editorial_inbox/stories/`, не передаёт в боевую очередь и не публикует статью, Дзен, соцсети.
8. За один проход — максимум один осмысленный кандидат. Если новых работ нет — без повторных сообщений. При ошибке доступа не обещать фонового продолжения и не имитировать успешный результат.
