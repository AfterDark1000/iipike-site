# ХПИИ — единый пул новостных кандидатов для сайта

**Рабочий файл:** [data/site_news_pool.json](../data/site_news_pool.json), ветка **main** репозитория `AfterDark1000/iipike-site`. Пул — **только сырьё**, а не список утверждённых статей. Он **не** запускает выпуск, не создаёт страницы, не меняет RSS, очередь Дзена, Threads, X, публикационные слоты, обложки или редакторскую очередь `editorial-intake`.

Репозиторий публичный: в карточках оставлять только публичные названия, краткие описания и URL. Никаких секретов, приватной переписки и закрытых материалов.

## Команды для человека (в любом чате ХПИИ)

- **`ХПИИ: В ПУЛ`** — сохранить **все подходящие новости из последней показанной подборки этого чата, строго сверху вниз**. Если задано `В ПУЛ № 2, 5, 9` — сохранить эти позиции **в порядке 2 → 5 → 9**, даже если в команде номера перечислены иначе. При команде `В ПУЛ: <список>` использовать этот явный список по порядку перечисления. Не требовать переносить новости по одной.
- **`ХПИИ: ПУЛ`** — посмотреть количество ожидающих, находящихся в работе, утверждённых и отклонённых; вывести номера поступления, статусы, даты добавления и взятия в работу по времени Усть-Катава/Екатеринбурга (UTC+05:00).
- **`ХПИИ: СЛЕДУЮЩАЯ`** — редактор **сразу резервирует строго самого раннего ожидающего** по `sequence` (FIFO), проверяет первоисточники, ищет дубль в архиве и готовит статью по постоянным редакторским правилам. Никакого выбора «на вкус» или перескакивания через очередь по `priority`. Не запрашивает повторную передачу новости из другого чата.
- **`ХПИИ: ПРОДОЛЖИТЬ`** — открыть **самую раннюю незавершённую** запись `in_review` по `sequence` и продолжить проверку/редактуру. С указанным ID (`ХПИИ: ПРОДОЛЖИТЬ n-...`) открыть именно её. **Новый резерв не создаётся, дата первого взятия в работу не меняется.** Если незавершённых несколько, указать остальные и их даты; не выдавать чужую текущую редактуру за законченную. Пул хранит состояние, URL и краткую суть, **не полный черновик**: после разрыва чата редактор восстанавливает факты из источников и существующего утверждённого GitHub-материала (если он уже есть), не выдумывает потерянный текст.
- **`ХПИИ: ВЕРНУТЬ <id>`** — вернуть взятую, но не утверждённую новость в ожидающие.
- **`ХПИИ: ПРОПУСТИТЬ <id>`** — закрыть неподходящий сюжет с краткой причиной.
- **`берём`** — только после явного утверждения статьи пользователем и успешной записи настоящего утверждённого материала в `editorial-intake/stories/<article_id>.json` отметить исходный кандидат `approved` и связать с `article_id`. Слово «берём» само по себе **не публикует** новость.

Русские команды распознаются по смыслу и без точного регистра; это протокол для ChatGPT-агентов, а не встроенные GitHub slash-команды. Если содержимое новости недоступно в текущем чате и не сохранено в пуле, нельзя выдумывать заголовок или ссылку.

## Протокол записи из чата обходчика (обязателен)

1. **Только по явной команде пользователя.** Плановый разведчик по-прежнему просто докладывает находки, ничего автоматически в пул не выгружает.
2. Получить из GitHub актуальные `data/site_news_pool.json` (ветка `main`) **вместе с blob SHA**. Не полагаться на кеш чата. Для отбора дубликатов проверить также `news.json` сайта и по возможности существующие утверждённые истории `editorial_inbox/stories` ветки `editorial-intake`.
3. Из последней подборки сформировать **один упорядоченный пакет**: позиции идут **в том же порядке, в котором пользователь их видел**. Для каждой необходимы название и реальная `https://`-ссылка на исходную публикацию/первоисточник. `summary` — краткая, непроверенная пока суть; `origin` — название обходчика/чата, без персональных данных; `priority` — `high`, `normal`, `low` (по умолчанию `normal`) **только информационная пометка, никогда не меняющая очередь**. **Не принимать источник, URL которого отсутствует**; сообщить сколько пропущено. Не выдавать такую запись за проверенную.
4. Проверить дубли по нормализованному URL (параметры `utm_*` и типичные трекеры не считаются различием) и по нормализованному **одинаковому заголовку**; отдельные статьи об одном направлении разрешены, если события разные. Пропустить дубликаты из пула, уже опубликованные и уже утверждённые для сайта. Существующие записи **не перезаписывать и не возвращать из статуса `in_review` / `approved` в `queued`**. При сомнительном семантическом дубле сообщить, не сливать разные новости вслепую.
5. **Только дописывать в конец массива `items`**, никого не переставлять. Каждому новому элементу последовательно присвоить `sequence = максимальный существующий sequence + 1` (1, 2, 3...). Внутри одной подборки сохранять последовательность сверху вниз, между чатами — порядок **фактически успешных GitHub-коммитов**. Всё записать **одним обновлением файла** через GitHub Contents API с текущим SHA. При конфликте параллельных записей заново перечитать, объединить, **пересчитать порядковые номера по свежему максимуму** и повторить безопасно; никогда не перезаписывать чужой пакет по устаревшему SHA. После успешного коммита **перечитать GitHub и проверить ID, `sequence` и порядок**.
6. Отчитаться конкретно: `Добавлено N; номера от X до Y; уже было M; без ссылок K; всего ожидают Q`. Если что-то пропущено, нумерация остальных всё равно идёт подряд, без дыр. Не говорить «сохранено», пока не подтверждён реальный коммит.

**Образец одной записи** (реальные записи добавлять, а не копировать этот пример):

~~~json
{
  "id": "n-<16 hex символов SHA256 нормализованного URL>",
  "sequence": 1,
  "title": "Проверяемый заголовок новости",
  "source_url": "https://example.org/news",
  "summary": "Что разведчик обнаружил; ещё не проверено редактором.",
  "origin": "ХПИИ — добытчик новостей",
  "priority": "normal",
  "status": "queued",
  "added_at": "2026-11-12T07:00:00+00:00",
  "review_started_at": null,
  "closed_at": null,
  "article_id": null,
  "note": ""
}
~~~

**Важно:** `id` рассчитывается алгоритмом `candidate_id()` из [scripts/site_news_pool.py](../scripts/site_news_pool.py), а не берётся из произвольного slug. Точное множество полей и переходы статусов проверяются скриптом. Любой помощник может прочитать код/документ, получить текущий файл и сделать запись через подключённый GitHub.


## Неподвижный порядок и даты

Порядок всех записей определяется **не временем статьи и не приоритетом**, а порядковым номером `sequence`, присваиваемым один раз при добавлении. Старые записи остаются на местах независимо от статуса. Команда `СЛЕДУЮЩАЯ` **пропускает уже занятые, утверждённые и отклонённые**, берёт только первую `queued`. При ручном возврате в `queued` исходный номер не меняется, поэтому вернувшаяся старая новость снова становится следующей перед более новыми. Если первая подборка дала 1–20, а второй чат позже сохранил 21–25, порядок будет именно 1–25. Параллельные операции упорядочены моментом **успешного коммита в GitHub**, а не временем отправки команды в чат.

Для каждой карточки сохраняются технические поля `added_at` (когда реально записана) и `review_started_at` (когда зарезервирована). В файле даты ISO-8601 с UTC offset, в отчётах — **дд.мм.гггг чч:мм, Усть-Катав/Екатеринбург (UTC+05:00)**. У `queued` нет текущей даты резерва; после возврата этот показатель сбрасывается, но `added_at` и `sequence` остаются исходными. Не выдумывать даты исходной публикации и не путать их с поступлением в пул.

## Протокол редактора: «следующая»

1. Сначала получить **актуальную** очередь из `main`. Брать **только `queued` с самым маленьким `sequence`**. Порядок строго **FIFO по моменту записи в GitHub**, а не по дате самой новости, её важности, источнику или желанию редактора. `high/normal/low` остаётся справочной характеристикой, не сортировкой. Не удалять и не переносить элементы, не менять `sequence`.
2. **До фактчекинга** изменить статус ровно **одной** записи на `in_review`, установить `review_started_at` с часовым поясом и коммитом GitHub с SHA. Перечитать итог. При конфликте повторить выбор по свежей очереди, чтобы два чата не взяли одну запись.
3. Теперь проверить реальную дату события, первоисточники, дополнительные подтверждения, актуальный архив сайта, `editorial-intake`, а при нужной дедупликации — каталог Дзена. Отсутствие доказательств — повод отклонить кандидата или вернуть в пул, а не сочинить статью. Исходный `source_url` — **отправная точка для исследования, а не автоматически доказанный первоисточник**.
4. Подготовить полноценную статью по действующим инструкциям редактора; показать текст пользователю на утверждение. Пока материал не утверждён и не сохранён, запись остаётся `in_review`. Нельзя отмечать `approved` только за написанный черновик.
5. После явного «берём» и **подтверждённой GitHub-записи** утверждённой статьи указать `status: "approved"`, `closed_at`, реальный `article_id`. Неподходящий/дублирующийся сюжет → `rejected`, краткая причина в `note`, `closed_at`, без `article_id`. Для возврата → `queued`, `review_started_at: null`, `closed_at: null`, `article_id: null`.
6. Если нет `queued`, но есть `in_review`, команда `СЛЕДУЮЩАЯ` не отбирает чужой резерв: показать незавершённые с датами и предложить `ПРОДОЛЖИТЬ` (или вернуть конкретный ID). Команда `ПРОДОЛЖИТЬ` читает самую раннюю `in_review`, не меняя GitHub-файл или первоначальное время резерва; с ID открывает конкретную запись. Если редактор замечает, что другой чат параллельно работает над ней, не записывать конкурирующее решение без проверки актуального состояния. Автоматического снятия резерва по таймеру нет.

`approved` означает **утверждённую статью, сохранённую редактором**, но ещё не выход на сайте. Фактическое опубликование по-прежнему определяет только существующая site-first очередь. Сам пул никогда не пишет в `editorial-intake`, не делает `editor_approved` и не трогает сайт без отдельного подтверждённого процесса.

## Проверка и ручные офлайн-инструменты

- `python3 scripts/site_news_pool.py --validate` — проверка текущей JSON-очереди;
- `python3 -m unittest discover -s tests -p 'test_site_news_pool.py' -v` — локальные тесты;
- `python3 scripts/site_news_pool.py --list` — содержимое очереди с `sequence` и временем поступления/резерва в UTC+05:00;
- `python3 scripts/site_news_pool.py --add /tmp/news.json` — пакетное **локальное** добавление из массива объектов с `title`, `source_url` и необязательными `summary`, `origin`, `priority`;
- `python3 scripts/site_news_pool.py --next` — локальное резервирование самой ранней ожидающей (`sequence`); 
- `python3 scripts/site_news_pool.py --continue-item [ID]` — **только чтение** самой ранней незавершённой (или указанной) без изменения дат;
- `--return-item ID`, `--approve ID --article-id SLUG`, `--reject ID --note "причина"` — локальные переходы.

**Локальный CLI не отправляет ничего в GitHub.** В чатах реальное действие — чтение и SHA-защищённое обновление через подключённый GitHub, затем повторное чтение. Автоматическая проверка GitHub Actions только валидирует файл и не публикует ничего.
