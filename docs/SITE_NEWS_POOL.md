## Действующий серверный протокол ручного редактора (Issue №477, 26.11.2026)

**Приоритет над прежними указаниями о прямой записи пула и локальном Python для ручного редактора.** Обычный ChatGPT не обязан скачивать большой JSON в Python. Состояние по-прежнему хранится в `main/data/site_news_pool.json`, маршрут — в `data/editorial_routing.json`. GitHub Actions использует штатные Python-функции и атомарно записывает пул и квитанцию одним нефорсированным коммитом. Отдельного реестра активных резервов нет.

- На явную команду **«следующая»** создай **ровно один** новый файл в main `data/editorial_claims/requests/manual-<уникальный-id-операции>.json`, через GitHub connector create_file. Имя латиницей, цифрами, дефисом/подчёркиванием; минимум 8 символов после manual-. Тело строго `{"schema_version":1,"action":"claim_next","worker":"hpii-manual-editor"}`. Не указывай кандидата, статус или время самостоятельно.
- **В том же ответе/проходе** несколько раз прочитай `main/data/editorial_claims/receipts/<то-же-имя>.json`. При первом 404 не завершай работу и не спрашивай «проверить?»: прочитай редакционные правила/источники для предварительной ориентировки, затем повтори проверку. Не создавай вторую заявку при задержке или потере ответа: сначала перечитай исходный путь. При исчерпанном времени или подтверждённом отказе сообщи точное имя операции и причину; продолжение проверяет ту же заявку.
- При `reserved` перечитай актуальный пул и маршрут из одного snapshot main. Сверь ID, sequence, `in_review`, точное `review_started_at == claimed_at`; квитанция должна иметь правильное имя, worker и SHA запроса. Только затем фактчекинг и полноценный текст Дзен/Threads/X/ВК. При `no_long_news` покажи отсутствие свободных; при `rejected` не обходи защиту.
- Для checkpoint нового ручного резерва создай новый уникальный файл в том же каталоге. Тело: `{"schema_version":1,"action":"checkpoint","worker":"hpii-manual-editor","claim_request":"manual-...json","pool_id":"n-...","pool_sequence":123,"claimed_at":"точное значение из квитанции резерва","expected_note":"текущее точное поле note","note":"новая заметка о проверенном прогрессе"}`. Все операции привязаны к исходной квитанции, текущему статусу, времени и предыдущей заметке. Подтверди `checkpointed` и перечитай результат. Никаких чужих резервов.
- Для возврата используй те же поля, action `return`, дополнительно `human_authorized:true` только при явной команде человека, note — причина. Для отклонения `reject` с обоснованной причиной согласно прежним редакционным правилам, без дополнительных полей. Для `approve` только после явного «берём» и сохранения точной утверждённой истории в editorial-intake добавь `human_authorized:true, article_id, story_sha` (точный blob SHA сохранённой story). Сервер проверяет реально сохранённую историю с human_editor; этот переход ничего не публикует. После подтверждения `returned` / `closed_rejected` / `closed_approved` перечитай пул. При несовпадении ожидаемой заметки не перезаписывай чужую работу.
- Для старого ручного in_review без новой квитанции прежний безопасный порядок остаётся; новый запрос не присваивает его. Не использовать новый протокол для чужих AUTO_EDITOR/SHORT_EDITOR резервов.
- Пробный запрос action `probe` с теми же тремя полями только проверяет штатный выбор и валидаторы без записи в пул; не считается резервом. Обычному редактору проба не нужна.

**Для всех писателей:** заявки/квитанции автономного редактора, короткостволиста, сортировщика и intake сохраняются. Прямое изменение пула/маршрутов разрешено только после штатной полной валидации и проверки общего HEAD main, с нефорсированным коммитом на точном snapshot; при любой гонке перечитать и пересчитать. Один SHA файла пула не защищает от параллельной смены маршрута. Не переписывать production JSON из чата без этих условий. Не считать отсутствие локального Python причиной пропустить серверную заявку. Никаких изменений в публикациях и секретах.

**Маршрутизация редакторов после утверждения 19 ноября:** для исходных 184 свободных материалов смотри `data/editorial_routing.json` и `docs/EDITORIAL_TRIAGE_ROUTING.md`. `next_item()` пропускает короткие и удерживаемые сюжеты, используя утверждённый приоритет `hot`. Автономный редактор не забирает `hot`. Короткий редактор использует отдельный `claim_short` с заявкой/квитанцией. Четыре исходных состояния пула не меняются; отметка маршрута не утверждает статью. Новые материалы вне реестра по умолчанию остаются в длинной очереди до нового разбора.

# ХПИИ — единый пул новостных кандидатов для сайта

**Рабочий файл:** [data/site_news_pool.json](../data/site_news_pool.json), ветка **main** репозитория `AfterDark1000/iipike-site`. Пул — **только сырьё**, а не список утверждённых статей. Он **не** запускает выпуск, не создаёт страницы, не меняет RSS, очередь Дзена, Threads, X, публикационные слоты, обложки или редакторскую очередь `editorial-intake`.

Репозиторий публичный: в карточках оставлять только публичные названия, краткие описания и URL. Никаких секретов, приватной переписки и закрытых материалов.

## Команды для человека (в любом чате ХПИИ)

- **`ХПИИ: В ПУЛ`** — сохранить **все подходящие новости из последней показанной подборки этого чата, строго сверху вниз**. Если задано `В ПУЛ № 2, 5, 9` — сохранить эти позиции **в порядке 2 → 5 → 9**, даже если в команде номера перечислены иначе. При команде `В ПУЛ: <список>` использовать этот явный список по порядку перечисления. Не требовать переносить новости по одной.
- **`ХПИИ: ПУЛ`** — посмотреть количество ожидающих, находящихся в работе, утверждённых и отклонённых; вывести номера поступления, статусы, даты добавления и взятия в работу по времени Усть-Катава/Екатеринбурга (UTC+05:00).
- **`ХПИИ: СЛЕДУЮЩАЯ`** — редактор сначала резервирует **первую ожидающую горячую новость** (`priority: "high"`, FIFO по `sequence` внутри горячей очереди). Когда горячих нет, берёт первую обычную `queued` по `sequence` (FIFO). Далее проверяет источники и архив и готовит статью. Не запрашивает повторную передачу новости из другого чата. Приоритет сырья не запускает публикацию и не заменяет `site_queue: "priority"` после утверждения.
- **`ХПИИ: ПРОДОЛЖИТЬ`** — открыть **самую раннюю незавершённую** запись `in_review` по `sequence` и продолжить проверку/редактуру, учитывая сохранённую заметку `note`. С указанным ID (`ХПИИ: ПРОДОЛЖИТЬ n-...`) открыть именно её. **Новый резерв не создаётся, дата первого взятия в работу не меняется.** Если незавершённых несколько, указать остальные и их даты; не выдавать чужую текущую редактуру за законченную. Пул хранит состояние, URL, краткую суть и заметку о прогрессе, **не полный черновик**: после разрыва чата редактор восстанавливает факты из источников и существующего утверждённого GitHub-материала (если он уже есть), не выдумывает потерянный текст.
- **`ХПИИ: ВЕРНУТЬ <id>`** — вернуть взятую, но не утверждённую новость в ожидающие.
- **`ХПИИ: ПРОПУСТИТЬ <id>`** — закрыть неподходящий сюжет с краткой причиной.
- **`берём`** — только после явного утверждения статьи пользователем и успешной записи настоящего утверждённого материала в `editorial-intake/stories/<article_id>.json` отметить исходный кандидат `approved` и связать с `article_id`. Слово «берём» само по себе **не публикует** новость.

Русские команды распознаются по смыслу и без точного регистра; это протокол для ChatGPT-агентов, а не встроенные GitHub slash-команды. Если содержимое новости недоступно в текущем чате и не сохранено в пуле, нельзя выдумывать заголовок или ссылку.

## Способ по умолчанию: GitHub-входящие без скачивания всего пула

**Для чатов ХПИИ, где Python не может прочитать GitHub, это основной способ.**
Не надо скачивать полный `data/site_news_pool.json` в Python, вычислять SHA-256 вручную или формировать ID, последовательность и служебные даты в чате. Вместо этого после явной команды «В пул» помощник создаёт **один небольшой входящий JSON-файл** через GitHub `create_file` в `main`:

`data/site_news_intake/requests/<уникальное-имя>.json`

Имя состоит из латинских строчных букв, цифр, точки, дефиса или подчёркивания, заканчивается на `.json`, например `20261116-082000-7-selected-news.json`. **Только создание нового файла** — никогда не `update_file` существующего запроса. Без персональных данных и секретов. Пакет максимум 40 записей (64 КиБ); записи идут **строго в порядке выбранных пользователем новостей**, без пропущенных номеров. Пример файла:

~~~json
{
  "schema_version": 1,
  "records": [
    {
      "title": "Первая самостоятельно проверяемая новость",
      "source_url": "https://example.org/original",
      "summary": "Короткая суть без домыслов.",
      "origin": "ХПИИ — добытчик новостей",
      "priority": "normal"
    }
  ]
}
~~~

Для каждой записи обязательны `title` и настоящая HTTPS `source_url`; остальные разрешённые поля — только `summary`, `origin` и `priority` (`high`/`normal`/`low`). **Не добавлять** `id`, `sequence`, `status`, `added_at` или любые произвольные поля — их создаёт сам GitHub-процессор.

После создания запроса автоматически запускается непубликующий workflow `.github/workflows/hpii-news-intake.yml`. Он читает **актуальный** пул в GitHub Actions, выполняет штатные `add()` и `validate()`, пропускает точные дубли по заголовку, учитывает разные новости с одним URL, сохраняет FIFO по фактическому порядку коммитов создания запросов и записывает **только** `data/site_news_pool.json` плюс квитанции в `data/site_news_intake/receipts/`. При параллельных обновлениях перечитывает `main` и повторяет расчёт. Никаких публикаций на сайте, в Дзене или соцсетях.

**Обязательное подтверждение:** помощник читает квитанцию с **тем же именем файла** из `data/site_news_intake/receipts/` в `main`. В ней есть `status: imported` / `rejected`, `added` с настоящими ID и последовательными номерами, `duplicates`, `request_sha256` и возможная ошибка. Пока квитанции нет, следует честно сообщить «Запрос передан, импорт ещё не подтверждён», а не «Новости добавлены». При `rejected` ничего не переписывать втихую, показать ошибку и передать техническому штабу. Ошибка записи в GitHub — тоже **не сохранено**.

**Дубли:** перед созданием заявки по возможности сверить подборку с текущим пулом, `news.json` и утверждёнными материалами; сервер проверяет совпадающие заголовки и ID, но не заменяет смысловой антидубль редактора. Повторное создание файла с новыми именем и тем же содержанием не продублирует уже существующие заголовки. Обработанные заявки хранятся с квитанциями ради трассировки.

Если нужен старый прямой способ записи `site_news_pool.json`, он разрешён **только** когда агент действительно может выполнить локально Python-проверку `validate()` полного будущего файла до коммита. Если не может — использовать входящие, а не пытаться обойти валидацию. Плановая разведка **никогда** не создаёт заявку без явной команды пользователя.

## Резервный способ: прямая запись пула (только с локальной Python-валидацией)

1. **Только по явной команде пользователя.** Плановый разведчик по-прежнему просто докладывает находки, ничего автоматически в пул не выгружает.
2. Получить из GitHub актуальные `data/site_news_pool.json` (ветка `main`) **вместе с blob SHA**. Не полагаться на кеш чата. Для отбора дубликатов проверить также `news.json` сайта и по возможности существующие утверждённые истории `editorial_inbox/stories` ветки `editorial-intake`.
3. Из последней подборки сформировать **один упорядоченный пакет**: позиции идут **в том же порядке, в котором пользователь их видел**. Для каждой необходимы название и реальная `https://`-ссылка на исходную публикацию/первоисточник. `summary` — краткая, непроверенная пока суть; `origin` — название обходчика/чата, без персональных данных; `priority` — `high` для горячей редакторской очереди, `normal` или `low` для обычной (по умолчанию `normal`); **определяет порядок выбора редактором, но не порядок публикации на сайте без отдельного `site_queue`**. **Не принимать источник, URL которого отсутствует**; сообщить сколько пропущено. Не выдавать такую запись за проверенную.
4. Проверить дубли по **тождеству самой новости**: одинаковые заголовки (после нормализации), уже опубликованные сюжеты или уже утверждённые статьи. **Совпадение URL само по себе НЕ является дублем**: один большой пресс-релиз может содержать несколько самостоятельных новостей. Оставлять каждую такую новость отдельной записью со своим заголовком и ID. Параметры `utm_*` и другие трекеры удалять из URL. Пропустить настоящие дубли из пула, сайта и уже утверждённых материалов. Существующие записи **не перезаписывать и не возвращать из статуса `in_review` / `approved` в `queued`**. При сомнительном семантическом дубле сообщить, не сливать разные новости вслепую.
5. **Только дописывать в конец массива `items`**, никого не переставлять. Каждому новому элементу последовательно присвоить `sequence = максимальный существующий sequence + 1` (1, 2, 3...). Внутри одной подборки сохранять последовательность сверху вниз, между чатами — порядок **фактически успешных GitHub-коммитов**. Всё записать **одним обновлением файла** через GitHub Contents API с текущим SHA. При конфликте параллельных записей заново перечитать, объединить, **пересчитать порядковые номера по свежему максимуму** и повторить безопасно; никогда не перезаписывать чужой пакет по устаревшему SHA. После успешного коммита **перечитать GitHub и проверить ID, `sequence` и порядок**.
6. Отчитаться конкретно: `Добавлено N; номера от X до Y; уже было M; без ссылок K; всего ожидают Q`. Если что-то пропущено, нумерация остальных всё равно идёт подряд, без дыр. Не говорить «сохранено», пока не подтверждён реальный коммит.

**Образец одной записи** (реальные записи добавлять, а не копировать этот пример):

~~~json
{
  "id": "n-<16 hex символов SHA256 нормализованного URL>",
  "sequence": 1,
  "title": "Проверяемый заголовок новости",
  "source_url": "https://example.org/news",
  "summary": "Что разведчик обнаружил; ещё не проверено редактором.",
  "origin": "ХПИИ — добытчик новостей",
  "priority": "normal",
  "status": "queued",
  "added_at": "2026-11-12T07:00:00+00:00",
  "review_started_at": null,
  "closed_at": null,
  "article_id": null,
  "note": ""
}
~~~

**Важно:** для первой новости с новым URL ID генерируется как `candidate_id(url)`; если другой заголовок использует **тот же URL**, его ID генерируется как `candidate_id(url, title)` — это разные новости, а не дубликаты. Существующие ID не переименовывать.

**Обязательный предкоммитный барьер:** новые ID должны быть вида `n-` + ровно 16 шестнадцатеричных символов и вычисляться штатной функцией `candidate_id`. **Нельзя** вписывать временные значения `n-20261115-124-raw`, номера дат и подборок вместо хеша. После формирования всего пакета проверить **весь** итоговый JSON через `python3 scripts/site_news_pool.py --validate --file /путь/к/кандидату.json` (или вызвать `validate(pool)` в Python), затем только записывать его в GitHub с точным blob SHA. Если выполнить валидацию или вычислить ID невозможно, **не делать коммит**: сохранить пакет в сообщении и сообщить о блокировке. После записи сверить содержимое в `main` и зелёный результат workflow `site-news-pool-safety.yml`. Сторож теперь независимо отслеживает ошибки проверки пула и открывает отдельный Issue.
 Функции в [scripts/site_news_pool.py](../scripts/site_news_pool.py). Точное множество полей и переходы статусов проверяются скриптом. Любой помощник может прочитать код/документ, получить текущий файл и сделать запись через подключённый GitHub.


## Неподвижный порядок и даты

Все записи сохраняют неизменный порядковый номер `sequence`, который присваивается при добавлении. **Для редакторской подготовки действуют две очереди:** горячая (`priority: "high"`) и обычная (`priority: "normal"` или `"low"`). Команда `СЛЕДУЮЩАЯ` в первую очередь выбирает самую раннюю `queued` из горячей; если горячих нет — самую раннюю из обычной. Внутри каждого уровня сохраняется FIFO по `sequence`. Занятые, утверждённые и отклонённые пропускаются. При возврате в `queued` исходный номер остаётся прежним. Записи не перемещаются физически, а приоритет влияет только на выбор следующей. Разделение горячих и обычных публикаций сайта действует независимо: после «берём» горячей статье необходимо выставить `site_queue: "priority"` в `editorial-intake`. Параллельные добавления упорядочены моментом **успешного коммита в GitHub**.

Для каждой карточки сохраняются технические поля `added_at` (когда реально записана) и `review_started_at` (когда зарезервирована). В файле даты ISO-8601 с UTC offset, в отчётах — **дд.мм.гггг чч:мм, Усть-Катав/Екатеринбург (UTC+05:00)**. У `queued` нет текущей даты резерва; после возврата этот показатель сбрасывается, но `added_at` и `sequence` остаются исходными. Не выдумывать даты исходной публикации и не путать их с поступлением в пул.

## Протокол редактора: «следующая»

1. Сначала получить **актуальный** пул из `main`. Среди `queued` сначала выбирать `priority: "high"` с минимальным `sequence`; если таких нет, брать любую обычную `queued` (`normal`/`low`) с минимальным `sequence`. Это **горячая редакторская очередь перед обычной**. Не удалять, не переносить и не перенумеровывать элементы. Пометка `high` в сыром пуле **не публикует** материал; после редакторского «берём» он попадёт в горячую очередь сайта только с `site_queue: "priority"`.
2. **До фактчекинга** изменить статус ровно **одной** записи на `in_review`, установить `review_started_at` с часовым поясом и коммитом GitHub с SHA. Перечитать итог. При конфликте повторить выбор по свежей очереди, чтобы два чата не взяли одну запись.
3. Теперь проверить реальную дату события, первоисточники, дополнительные подтверждения, актуальный архив сайта, `editorial-intake`, а при нужной дедупликации — каталог Дзена. Отсутствие доказательств — повод отклонить кандидата или вернуть в пул, а не сочинить статью. Исходный `source_url` — **отправная точка для исследования, а не автоматически доказанный первоисточник**.
4. Подготовить полноценную статью по действующим инструкциям редактора; показать текст пользователю на утверждение. Пока материал не утверждён и не сохранён, запись остаётся `in_review`. **После существенного этапа работы** (проверенные первоисточники, найденная проблема, готовый план текста) дописать короткий проверяемый прогресс в поле `note` (до 1500 символов) через GitHub-коммит с SHA и подтверждением повторного чтения, **не меняя `status`, `review_started_at`, `added_at` или `sequence`**. Записывать факты и следующий шаг, а не секреты/полные неутверждённые тексты. Нельзя отмечать `approved` только за написанный черновик.
5. После явного «берём» и **подтверждённой GitHub-записи** утверждённой статьи указать `status: "approved"`, `closed_at`, реальный `article_id`. Неподходящий/дублирующийся сюжет → `rejected`, краткая причина в `note`, `closed_at`, без `article_id`. Для возврата → `queued`, `review_started_at: null`, `closed_at: null`, `article_id: null`.
6. Если нет `queued`, но есть `in_review`, команда `СЛЕДУЮЩАЯ` не отбирает чужой резерв: показать незавершённые с датами и предложить `ПРОДОЛЖИТЬ` (или вернуть конкретный ID). Команда `ПРОДОЛЖИТЬ` читает самую раннюю `in_review`, не меняя GitHub-файл или первоначальное время резерва; с ID открывает конкретную запись. Если редактор замечает, что другой чат параллельно работает над ней, не записывать конкурирующее решение без проверки актуального состояния. Автоматического снятия резерва по таймеру нет.

`approved` означает **утверждённую статью, сохранённую редактором**, но ещё не выход на сайте. Фактическое опубликование по-прежнему определяет только существующая site-first очередь. Сам пул никогда не пишет в `editorial-intake`, не делает `editor_approved` и не трогает сайт без отдельного подтверждённого процесса.

## Защита при прямой записи из чужого чата

Прямые записи `data/site_news_pool.json` через GitHub Contents API не вызывают функцию `add()` и могут обходить проверку **до** коммита. Поэтому даже при правильных инструкциях есть дополнительный страховочный workflow `.github/workflows/hpii-pool-auto-repair.yml`: после `push` в `main` он независимо перечитывает актуальную очередь и **только** для не взятых в работу записей с временными ID вида `n-YYYYMMDD-SEQUENCE-raw` вычисляет ID штатной `candidate_id()` (для повторных URL — с учётом заголовка).

Он не запускает редактора, сайт или Дзен; не меняет FIFO, статусы, дату, тексты и URL. Нельзя автоматически исправлять уже взятые/утверждённые записи, неизвестный формат ID или коллизии: в этих случаях работа останавливается с ошибкой и остаётся сторожевой Issue. Коммиты внешних чатов **по-прежнему должны** проходить полную проверку до записи. Workflow — страховка после прямого коммита, а не разрешение использовать временные ID. Если его GitHub-токен не сможет сделать защищённый коммит, сбой останется видимым в Actions и стороже.

## Проверка и ручные офлайн-инструменты

- `python3 scripts/site_news_pool.py --validate` — проверка текущей JSON-очереди;
- `python3 -m unittest discover -s tests -p 'test_site_news_pool.py' -v` — локальные тесты;
- `python3 scripts/site_news_pool.py --list` — содержимое очереди с `sequence` и временем поступления/резерва в UTC+05:00;
- `python3 scripts/site_news_pool.py --add /tmp/news.json` — пакетное **локальное** добавление из массива объектов с `title`, `source_url` и необязательными `summary`, `origin`, `priority`;
- `python3 scripts/site_news_pool.py --next` — локальное резервирование первой горячей `queued`, а при её отсутствии — первой обычной (FIFO внутри уровня); 
- `python3 scripts/site_news_pool.py --continue-item [ID]` — **только чтение** самой ранней незавершённой (или указанной) с сохранённой заметкой и датами;
- `python3 scripts/site_news_pool.py --checkpoint ID --note "проверены источники, осталось..."` — локальное сохранение короткого прогресса, **без сброса резерва**;
- `--return-item ID`, `--approve ID --article-id SLUG`, `--reject ID --note "причина"` — локальные переходы.

**Локальный CLI не отправляет ничего в GitHub.** В чатах реальное действие — чтение и SHA-защищённое обновление через подключённый GitHub, затем повторное чтение. Автоматическая проверка GitHub Actions только валидирует файл и не публикует ничего.
