# ХПИИ — маршрутизация решений утреннего сортировщика

## Первое утверждение, 19 ноября 2026

Источник: `data/editorial_triage/approved_2026-11-19.json` (184 решения главреда по 184 `queued` из 320 записей). Полный исходный JSON сохранён без переименования номеров и ID. Активный машинный реестр: `data/editorial_routing.json`.

Результат распределения:
- 72 `long`: 12 горячих, 49 полноформатных, 11 ведущих объединённых сюжетов;
- 48 `short`: отдельная очередь «Новости коротко»;
- 64 `hold`: 18 дополнительных историй к объединениям, 28 отложенных, 3 кандидата на отклонение после проверки, 15 ручных решений.

Реестр меняет **только право на редакционный захват**. Он НЕ утверждает тексты, не назначает `article_id`, не делает сайт/Дзен-публикаций и не меняет четыре исходных состояния `queued/in_review/approved/rejected`. Не путать маршрутизацию с выпуском.

Для историй из данного разбора нельзя использовать `next_item()` или `claim_ordinary()` в обход `scripts/editorial_routing.py`. Оба штатных метода теперь исключают `short` и `hold`. Для ручного редактора горячая очередь выбирается первой; `hot` в утверждённом маршруте имеет эффективный приоритет `high` даже до отдельной записи `priority` в большом JSON. Автономный редактор не имеет права резервировать `hot`.

При этом семь новых приоритетов (№266, 294, 295, 298, 299, 306, 313) в оригинальном `data/site_news_pool.json` **ещё не материализованы**: GitHub-коммит большого файла требует отдельной проверки штатным Python-валидатором. Не заявлять, будто поле `priority` уже изменилось. Критерий маршрутизации для всех редакторов — действующий реестр.

### Как короткий редактор получает «Следующая короткая»

1. Убедиться, что прежняя собственная заметка завершена либо согласовано её продолжение. Перечитать актуальный пул, реестр маршрутов, кандидатов и уже утверждённые короткие публикации. Не брать чужой `in_review`.
2. Создать **один** неизменяемый `data/briefs/claims/requests/<unique>.json` в `main` через GitHub `create_file`:
   ```json
   {"schema_version":1,"action":"claim_short","worker":"hpii-short-editor"}
   ```
   Ни `pool_id`, ни `sequence`, ни утверждение, ни команду публикации сюда добавлять нельзя.
3. Workflow `hpii-short-editor-claim.yml` сверяет маршрут, пул и уже существующие короткие кандидаты, выбирает минимальный свободный `sequence` в короткой очереди, атомарно в одном коммите ставит `in_review`, запоминает `SHORT_EDITOR claim=short; pool_id=...` и создаёт квитанцию `data/briefs/claims/receipts/<то же имя>.json` со статусом `reserved`, `no_short_news` либо `rejected`.
4. Редактор **ждёт/повторно читает только свою квитанцию**. До настоящего `reserved` не писать кандидата, не создавать повторную заявку и не выдавать материал за взятый. При конфликте `main` GitHub Action перечитывает состояние и повторяет выбор: никакого ручного перезаписывания.
5. Из `reserved` берёт только подтверждённые `pool_id`, `pool_sequence`, `title`, `source_url`, проверяет первоисточник и пишет отдельную заметку 180–650 символов в `data/briefs/candidates.json` (`pending_review`) без публикации и без утверждения за человека.
6. После точного утверждения главным редактором остаётся прежний owner-Issue + SHA256 + `approved.json` + независимая проверка/публикация. `sync_briefs_pool.py` разрешает закрытие исходной `in_review` **только при точном маркере SHORT_EDITOR**, никогда чужого резерва. Отклонение/возврат выполняется из общего пула по его прежним правилам.

**Проверка без записи и публикации:** `python3 scripts/editorial_routing.py --validate` и `--next-short`. Тесты: `python3 -m unittest discover -s tests -p 'test_editorial_routing.py' -v`. Запускать их по PR перед объединением. Пустая короткая очередь должна возвращать `null`, а не занимать полный материал.

### Для следующего сортировщика

После нового утверждённого полного аудита создавать новый исходный файл в `data/editorial_triage/`, аккуратно обновлять единый маршрутный индекс с проверкой каждой пары `pool_id/sequence` и отсутствия пересечений. Нельзя затереть прежние маршруты и забрать уже находящиеся `in_review`, `approved`, `rejected`. Будущие новости, отсутствующие в маршруте, пока остаются в обычной длинной очереди по исходному `priority`; новый разбор вправе их маршрутизировать. Для `hold` нужны отдельные решения о возврате или отклонении, никакого автоматического истечения срока.

Большой `data/site_news_pool.json` не редактировать напрямую из чата без настоящей полной проверки `scripts/site_news_pool.py:validate()` и SHA-safe commit. JSON сортировщика — авторитетен для **разделения труда**, не для подмены исходных подтверждений GitHub.
