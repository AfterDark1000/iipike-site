# ХПИИ — автономный редактор: рабочий режим после двух пилотов

**Статус:** регламент для существующей задачи ChatGPT «ХПИИ — Автономный редактор» (`Automation_f94d3153054c819186c8fa7f5ac5b36e`). Отдельный от художника и добытчика исполнитель. Включение самой задачи выполняется средствами ChatGPT; наличие файла не доказывает запуск.

## Зачем

Готовить **полные и проверенные редакционные комплекты** по обычной очереди без ручного написания: статья для сайта/Дзена, Threads/X, VK, перелинковка, источники, сущности, бриф художнику. Главреду остаются решения «утвердить текст / переделать / отклонить» в `/admin/auto-editor/`. В художественную очередь текст попадает **только** после отдельного утверждения главреда. Вручную рисовать и публиковать не следует.

### Обязательные источники каждого запуска

1. `docs/AUTO_EDITOR_INSTRUCTIONS.md` — полный редакционный стандарт, включая раздел 4.1 о содержательной вычитке.
2. `docs/AUTO_EDITOR_STAGE2.md` + `scripts/auto_editor_workbench.py` — схема и атомарный claim обычной новости.
3. `docs/AUTO_EDITOR_REVIEW_PANEL.md`, текущие `data/site_news_pool.json`, `data/auto_editor/requests/`, `data/auto_editor/receipts/`, `editorial-intake/editorial_inbox/auto_drafts/` и `auto_decisions/`. При необходимости сопоставить `auto_covers/`, `auto_cover_decisions/`, `auto_handoffs/` и опубликованные материалы.
4. Проверить источники через доступный поиск, соблюдать актуальные контракты HTML/ссылок, рубрик, реестров и цитат. Не выдумывать ссылки, аккаунты, цифры, цитаты или результаты.

## Рабочий режим, с 18 ноября 2026

**Предыдущее ограничение «строго два пилота за всё время» снимается явным разрешением главреда «авто-редактора выпускать в поля».** Первый Carbon и второй Nick Reid / кроссовок уже имеют `approve_text`; их текст не переписывать и не резервировать повторно. Следующий материал — третий, выбирается **не по заданному названию**, а штатным FIFO-контрактом.

### Антиспам и WIP

- **Один новый request за проход, не чаще одного нового request в 24 часа по `request`-созданию**. Не писать много материалов за один проход даже при пустом времени.
- **Если есть хоть один собственный черновик с `status=drafting` без полного результата либо свежим решением `revise`, сначала закончить его**. При `blocked` — не захватывать новую историю, пока причина не устранена или главред явно не разрешил пропустить.
- **Если есть собственный `ready_for_review` без решения `approve_text` или `reject` для актуальной ревизии — ждать человека**, никаких новых запросов. Если текст утверждён и ожидает художника, это не незавершённый *текст*, поэтому не блокирует третий редакционный черновик.
- **Ограничить хвост из утверждённых текстов без передачи:** одновременно не более **двух** материалов с `approve_text`, у которых нет `auto_handoffs` и для которых ещё нет отдельно утверждённой обложки. Если таких уже два — приостановить новые запросы, чтобы не заваливать художника.
- После последнего человеческого `reject` или успешно завершённого `approve_text` можно брать следующую обычную новость, если WIP позволяет. Не обходить реальные блокировки.
- Каждый проход выполнять один осмысленный шаг; не оповещать повторно о тех же статусах или отсутствии работы. Не выключать свою задачу самостоятельно после третьего материала — режим ограничивается WIP.

### Очерёдность работы

1. Прочитать актуальные решения `editorial_inbox/auto_decisions` по всем собственным черновикам. Решение `revise` по точной ревизии и SHA обрабатывается первым: новая `revision`, тот же `article_id/pool_id/request`, полная проверка всех полей, повторное чтение. `approve_text` и `reject` не переписывать.
2. Продолжить прежний request без receipt или подтверждённый `reserved` receipt без готового черновика. **Никогда не создавать новый request только потому, что receipt ещё не успел появиться.** При отказе резервирования назвать причину.
3. Если открытых текстовых работ нет и WIP допускает, создать **единственный** новый неизменяемый `data/auto_editor/requests/<unique>.json` в `main` с полями:
   ```json
   {"schema_version":1,"action":"claim_ordinary","worker":"hpii-auto-editor"}
   ```
   Ни `pool_id`, ни `priority`, ни `article_id` не задавать; GitHub Action сам выберет самую раннюю `queued normal/low`. **`priority=high` запрещён**. Не изменять `data/site_news_pool.json` напрямую.
4. После подтверждения `status=reserved` тщательно проверить источники, актуальность и дубли. Если история оказалась недостоверной или малопригодной для полноценной статьи, честно установить `blocked` с конкретной причиной и предложить главреду перенаправление на короткие; **не создавать длинную бессодержательную статью ради очередного номера**.
5. Написать полный draft по `draft_template` и `validate_draft` из актуального `scripts/auto_editor_workbench.py`. Создать все необходимые тексты, проверить собственную редактуру, цитаты, первоисточники и фактическое описание. Сохранить в `editorial-intake/editorial_inbox/auto_drafts/<article_id>.json` с `status=ready_for_review` **только после завершения всех частей**. Проверить повторным чтением, текущим SHA и независимой GitHub-валидацией.
6. Ждать главреда. **Автономный художник — отдельная задача**: читает `approve_text` и `docs/ARTIST_AUTONOMOUS_AGENT.md`, обложку создаёт в `auto_covers` и также отдаёт на утверждение, без публикации.

## Инварианты безопасности

- Не писать в `editorial_inbox/stories/`, `editorial_inbox/covers/`, `main/news.json`, боевые публикационные очереди и социальные аккаунты; не запускать выпуск сайта или соцсетей.
- Не утверждать текст, обложку или публикацию за человека. Не создавать `approved_by`, `approved_at`, `editor_approved`, `cover_approved` без настоящих решений главреда.
- Не брать горячие новости и материалы `in_review` другого редактора; не переупорядочивать FIFO; не менять статусы вручную; не обрабатывать новые новости в нарушение человеческой блокировки.
- Не создавать новую ChatGPT-задачу; используем существующую.
- Ограничение «одна новость в 24 часа» — безопасный стартовый режим, а не цель роста. После нескольких **независимых** завершённых циклов можно пересмотреть частоту; до этого не снимать защиту.

**Как считать тест успешным:** именно запланированная задача (а не техштаб в обычном чате) сама создала запрос, получила `reserved`, подготовила и сохранила новый качественный `ready_for_review` в GitHub, а владельцу осталась только редакторская проверка. Следующий шаг — независимая задача художника после решения `approve_text`.
