**Ограниченный производственный запуск Work (23.11.2026).** Новый редактор Work может создавать максимум **5 подтверждённых резервирований за скользящие 24 часа**, но не более одного на один запуск. Реальная защита находится в `scripts/auto_editor_workbench.py:consume`: по `claimed_at` всех существующих `reserved`-квитанций `hpii-auto-editor`. Шестая новая заявка получает неизменяемую квитанцию `rejected` с `AUTO_EDITOR_DAILY_CAP_5`; исходный пул при этом не меняется. Когда окно сдвигается, редактор создаёт **новый** запрос, никогда не отправляет повторно отклонённый. Редактирование r2/r3, вычитка и ожидание решений главреда не являются новыми резервированиями. Лимит обновляет только новую работу, не даёт права самостоятельно утверждать и публиковать. Аналогичный **5 изображений за 24 часа** проверяет художник по свежим `editorial_inbox/auto_covers/*.json` (включая переделки) **перед** вызовом генерации; это ограничение задачи, не лицензия генератора. При исчерпании квоты художник пропускает генерацию и продолжает проверять уже готовые файлы.

**Синхронизация опубликованных автодрафтов (20.11.2026).** После реальной публикации через site-first исходная запись `AUTO_EDITOR claim=...; article_id=...` в `data/site_news_pool.json` должна стать `approved` с точным `article_id`, `closed_at` из `main/news.json.published_at_utc` и ссылкой на страницу. Механизм `scripts/sync_published_auto_editor_pool.py` запускается в конце штатного `site-first-scheduled-release.yml`, не при утверждении текста или обложки. Скрипт сверяет точный article ID, исходный HTTPS URL и существующий опубликованный HTML; при несовпадении останавливается, не изменяя пул. Статусы других редакторов и чужие `in_review` не меняются; повторный проход идемпотентен. Отдельного внешнего cron для синхронизации не нужно. Исторические №44/45/46/49 сверены и закрыты 20 ноября, №58 осталась `in_review`, пока не опубликована.

# ХПИИ — этап 2: обычная очередь, резервирование и черновики

**Статус (18.11.2026):** резервирование GitHub Actions, автономный ChatGPT-редактор и админка пилотно реализованы. Существующая задача может быть активирована отдельно. **Текущий рабочий режим, ограничения WIP и частоты — [AUTO_EDITOR_AUTONOMOUS_AGENT.md](AUTO_EDITOR_AUTONOMOUS_AGENT.md).** Ни наличие кода, ни включение задачи не означают автоматическую публикацию. Единый редакционный регламент: [AUTO_EDITOR_INSTRUCTIONS.md](AUTO_EDITOR_INSTRUCTIONS.md). Старый редактор и боевой выпуск без изменений.

## Неприкосновенное правило горячей очереди

**Автоматическому редактору нельзя брать новости с `priority="high"`.** Никогда — в том числе при пустой обычной очереди, при повторе, при наличии горячих записей в начале списка. Существующее правило **обычного редактора** (горячие первыми) остаётся прежним.

Автоматика берёт **минимальный sequence среди `status="queued"` и `priority` из `normal`, `low`**. Чужие `in_review` не трогает. При пустой обычной очереди — `no_ordinary_news`, ноль изменений в пуле. Запрет зафиксирован не только в тексте, но и в коде/тестах.

Не меняем `scripts/site_news_pool.py` и схему текущего пула. Резерв — прежний `status=in_review`, `review_started_at` и короткое поле `note`. Статусы черновиков и замечаний ведутся отдельно.

## Хранилище

| Компонент | Ветка | Путь |
| --- | --- | --- |
| Новостной пул | main | `data/site_news_pool.json` |
| Запрос на резерв | main | `data/auto_editor/requests/<unique>.json` |
| Подтверждение (receipt) | main | `data/auto_editor/receipts/<unique>.json` |
| Автоматический черновик | editorial-intake | `editorial_inbox/auto_drafts/<article_id>.json` |
| Кандидаты обложек | editorial-intake | `editorial_inbox/auto_covers/<article_id>-r<revision>-v<version>.webp` + `.json` (после утверждения текста) |
| Действующая боeвая очередь | editorial-intake | `editorial_inbox/stories/<id>.json` — только после человеческого утверждения |

Скрипт внутри GitHub Actions изменяет пул и подтверждения **одним коммитом**; при Git-конфликте повторяет расчёт по свежему main, исключая двойное резервирование. Черновики никогда не помещаются в `stories/` до «берём».

**Важно:** GitHub-репозиторий публичный. Неопубликованные тексты в ветке editorial-intake не выходят автоматически на iipike.ru, но видны пользователям GitHub. Никаких секретов, закрытой переписки, персональных данных.

## Протокол для действующей ChatGPT-задачи

**Оптимизация одного запуска (18.11.2026):** подтверждение `receipt` по-прежнему обязательно, но **ждать следующего расписания не требуется**. После создания request можно сразу проверять GitHub и параллельно выполнять предварительный фактчекинг вероятного первого свободного материала, не создавая `article_id` и не сохраняя черновик до настоящего `reserved`. После подтверждения в том же проходе использовать только полученные из receipt `article_id`/`pool_id`, затем сохранить полный `ready_for_review` или восстанавливаемый `drafting`. Подробнее — `docs/AUTO_EDITOR_AUTONOMOUS_AGENT.md`.

### 1. Сначала собственные незаконченные задания

Прочитать [полный регламент](AUTO_EDITOR_INSTRUCTIONS.md), актуальные записи пула, подтверждения и каталог автодрафтов. **Приоритет работы:** человеческие замечания (когда появится канал возвратов) → свои прерванные задания → новая обычная новость.

Если предыдущее резервирование подтверждено, а черновик не сохранился, **восстановить его из receipt**. Не создавать повторный запрос, пока старая работа не доведена до видимого состояния.

### 2. Запрос на новое резервирование

Создать один новый неизменяемый JSON в main, например `data/auto_editor/requests/20261117-120000-auto-editor-001.json`.

~~~json
{
  "schema_version": 1,
  "action": "claim_ordinary",
  "worker": "hpii-auto-editor"
}
~~~

Не передавать в запрос priority, `pool_id`, `article_id`, `status`, `approved_by` или команды публикации. Не изменять уже созданные request-файлы и не объявлять резерв подтверждённым сразу после их создания.

Workflow **HPII — auto-editor ordinary-only reservations** срабатывает на такой push. В ответ создаёт receipt с одним из статусов:

- `reserved` — настоящие `pool_id`, `pool_sequence`, `article_id`, `priority`, `title`, `source_url` и `claimed_at`. Только после этого можно писать полноценный черновик.
- `no_ordinary_news` — обычных новостей нет; не брать горячую.
- `rejected` — неверный запрос, конфликт ID или другая проверяемая ошибка.

В пуле появляется заметка вида `AUTO_EDITOR claim=<имя>; article_id=<slug>`. Это **не** согласие на выпуск. Любая запись `in_review` исключается из обычного выбора редактора.

### 3. Подготовить и сохранить полный черновик

Использовать именно `article_id` из подтверждённого receipt. Это **не** исходный идентификатор сырой новости `n-...`. ID не изменяется вместе с заголовком.

Основа JSON создаётся командой `python3 scripts/auto_editor_workbench.py --draft-template data/auto_editor/receipts/<request>.json` или собирается по точной схеме функции `draft_template()` в этом скрипте.

Обязательные поля:
- `schema_version`, `request`, `pool_id`, `pool_sequence`, `article_id`, `revision`, `status`, `created_at`, `updated_at`.
- `content`: `title`, `dzen_title`, `summary`, `rubric`, `section`, `topics`, `companies`, `products`, `source_url`, `source_title`, `event_date`, `related_dzen_ids`, `site_crosslinks`, **`article_markdown`**, **`threads_text`**, **`x_text`**, **`vk_title`**, **`vk_summary`**.
- `research`: список проверенных источников `sources`, фактчекинг `fact_checks`, заметки `notes`.
- `entity_candidates`: отдельные предложения компаний и продуктов.
- `cover_brief`: `fact`, `hook`, `constraints` для будущего художника.
- `editor_notes`: рабочие примечания.

Статус `drafting` допускает промежуточное сохранение и восстановление (обязательные ключи присутствуют, но текст может быть неполным). Статус `ready_for_review` разрешён только с полным текстом, всеми соцпостами, первоисточниками, корректным Markdown и брифом. `blocked` — существенная проблема, объяснённая в `research.notes` или `editor_notes`. Номер `revision` растёт при правках. Для обновления нужны свежий SHA и чтение результата обратно.

**Нельзя:** `status=approved`, `editor_approved`, `published`, `approved_by` или любое имитированное согласие человека. Никаких записей в боевые очереди до настоящего «берём».

### 4. Что уже технически проверяется

- `python3 -m unittest discover -s tests -p 'test_auto_editor_workbench.py' -v`
- `python3 scripts/site_news_pool.py --validate`
- `python3 scripts/auto_editor_workbench.py --verify-drafts <путь>`

Workflow **HPII — validate isolated auto-editor drafts** проверяет JSON на editorial-intake по подтверждённому receipt из main, **ничего не пишет и не публикует**. Отдельные тесты проверяют: горячая запись не берётся даже при пустой обычной очереди; при `high` перед `normal` резервируется `normal`; обычный `next_item()` оставлен неизменным и по-прежнему берёт горячую первой.
